## Findings

### P2-1 secret-scrub.mjs:714-728 (firstStop, from 5882eb90; not repaired by 3754e58b) — a crafted run of blank lines makes the release 21x slower than benign text, where v6.30.0 is 0.8x

`firstStop(text, run, i, shape)` runs the shape's regex over the run's whole distinct-line index and
calls `lineCore` on every matching distinct line on every call, although it only wants the first stop
at or after `i`. A reading resumes inside the same run after each armor header it stops on, so one
BEGIN calls it up to 17 times per run per pass, and `shape` is rebuilt per BEGIN per pass, so
nothing is reused across the 32 passes.

Input (206,404 chars): the CHAIN of 40 labelled values, then
`</-----BEGIN RSA PRIVATE KEY-----`, then 16 x (`"` line, `</X-b:>` line), a `"` line, then
16,666 distinct lines `</X-b<N>:>`. Every line below the BEGIN is blank with no prefix (tag), and
every `</...>` line is an armor-header stop for the `</` prefix.

`node scripts/repro-stops.mjs t-724be09d t-31dec85a t-5882eb90 t-27493bd0` (best of 3):

| tree | crafted | benign | ratio |
|---|---|---|---|
| 724be09d (v6.30.0) | 36.4 ms | 46.8 ms | 0.8x |
| 31dec85a | 37.2 ms | 46.3 ms | 0.8x |
| 5882eb90 | 1,052.8 ms | 47.8 ms | 22.0x |
| 27493bd0 (release) | 1,038.4 ms | 48.8 ms | 21.3x |
| release under NODE_V8_COVERAGE | 3,787.8 ms | 47.6 ms | 79.6x |

Linear but large: 637 ms at 100k, 2,286 ms at 400k, 4,535 ms at 800k (23-25x benign each).
Instrumented copy (`scripts/count-stops.mjs t-instr2`): 544 firstStop calls (17 per pass x 32),
9,066,848 match iterations, each with a `lineCore`. Output identical to v6.30.0. The shape is not
in tests/secret-scrub-linear.test.mjs, so the harness is blind to it.
Contradicts the release title ("a crafted run of blank lines no longer slows the secret scrubber")
and the bullet heading "a run of blank lines is read once per pass": the run's lines are re-read
through the index once per resumed reading.
Fix direction (not tried): per (run, shape source), compute the sorted stop indices once and
binary-search them for each `i`.

`text[s..]` and the depth (nextLine and lineCore read forward); pruneCarried keeps a run only if it
starts inside the common suffix of consecutive texts, so by induction its suffix equals the one it
was recorded on. Plus the fuzz above.
