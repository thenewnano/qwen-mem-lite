## Findings

### P2-1 — Four unattended LLM prompts in the same daily run still put stored rows inside the instructions, without MEMORY_INPUT_GUARD

Files: `hook-optimize.mjs:287` (re-enrich `scopes` pass), `hook-optimize.mjs:330` (`aliases`),
`hook-optimize.mjs:397` (`concepts`), `hook-optimize.mjs:1605` `buildCompressPrompt` (smart-compress,
called at `:1630`).

424f0909 / c18c2162 / 27f8eccd moved cluster-merge, narrow/wide re-enrich and save-enrich to
`{ system: instructions + MEMORY_INPUT_GUARD, user: stored row }`. The parallel paths of the same
unattended run were not changed: `handleLLMOptimize` -> `optimizeRun(db, { reenrichScope: 'wide' })`
runs the aliases, concepts and scopes side passes after the main scope (`hook-optimize.mjs`
optimizeRun, `findReenrichCandidates(... { scope: 'aliases' | 'concepts' | 'scopes' })`) and
smart-compress every day. Each still builds one string with `Title: ${cand.title}` /
`Narrative: ${cand.narrative}` / `Lesson: ...` between the task text and the JSON contract:

```js
const aliasPrompt = `Generate alternative search terms ... Return ONLY valid JSON, no markdown fences.

Title: ${truncate(cand.title || '(untitled)', 200)}
Narrative: ${truncate(cand.narrative || '(no narrative)', 500)}

JSON: {"search_aliases":[...],"scope":"..."}
```

`grep -n MEMORY_INPUT_GUARD hook-optimize.mjs` -> sites 469 (re-enrich main), 872 (normalize),
1272 (cluster-merge) only. What the model's output does on these paths: aliases are appended to
the row's FTS `text` (retrieval poisoning: a row can be made to match arbitrary queries),
concepts/facts are stored as the memory's own claims, and smart-compress's `should_compress`
decides whether the cluster's members are hidden behind a summary (the D#10 veto; inputs are now
machine rows without lessons, 879f41a2). Not a regression against v6.27.0 (these prompts are
unchanged), but the class the release fixes stays open on 4 of the 7 prompt sites of the daily
run. Not probed with a model.

### P2-2 — A write lock held 1.5–4.5 s now loses the prompt row (and Stop's handoff/summary) that v6.27.0 waited out and recorded

Files: `lib/time-constants.mjs:65` (`HOOK_DB_BUSY_TIMEOUT_MS = 1500`), `hook.mjs:290`
(FIVE_SECOND_HOOK_EVENTS), `hook.mjs:3945` (prompt row), `hook.mjs:1876` (Stop writes).

84d981b7 cut the busy wait of the 5 s hooks from 5000 to 1500 ms. For locks longer than ~4.5 s that
turns a host kill into an exit 0 (the intent). For locks between 1.5 s and ~4.5 s it turns a
successful slow write into a lost one. A/B, back to back, same sandbox store, user-prompt then
stop under a lock of L ms (`p7-shortlock.mjs`):

```
HEAD    lock 2500 user-prompt status=0 ms=1575 prompt rows + 0
v6.27.0 lock 2500 user-prompt status=0 ms=2618 prompt rows + 1
HEAD    lock 3500 user-prompt status=0 ms=1586 prompt rows + 0
v6.27.0 lock 3500 user-prompt status=0 ms=3517 prompt rows + 1
HEAD    lock 3500 stop status=0 ms=1583 err="[ERROR] stop: database is locked"
v6.27.0 lock 3500 stop status=0 ms=3535 err=""
```

On HEAD the prompt row is gone, so its handoff phase is skipped too (`if (recorded)
injectHandoffIfEarly(...)`), and the Stop exception skips the handoff, citation tracking, the fast
summary baseline and the `llm-summary` spawn (`hook.mjs:1876-1903`) for that turn. Who holds a lock
that long in normal operation is not measured here: the daily auto-maintain runs its ops in one
transaction that this release made `.immediate()` (e29baaba), and decay UPDATEs fire the FTS
triggers per row, so a large store is the plausible case. Possible fix: give the prompt-row write
its own longer wait (about 3 s; everything after it already runs at busy_timeout 0), instead of
the one value for every statement.

### P3-1 — Stop under a held lock is still killed at 5 s when the episode buffer holds 2+ sessions' work

Files: `hook.mjs:1868` (flushEpisodeAtStop), `hook.mjs` flushEpisodeGroup -> `saveEpisodeImmediate`,
`hook.mjs:1876`.

Each significant session group's immediate save waits the full 1.5 s, then
markSessionCompletedAndSaveHandoff waits another 1.5 s. `p2-stop.mjs N 9000` (N sessions, 3 Edits
each, Stop under a 9 s lock), without CLAUDE_PID (per-project buffer, as on a host that does not set
it, shared by concurrent sessions of one project):

```
N=1  status=0        ms=3155  (with CLAUDE_PID; same shape)
N=2  status=0        ms=4592  err="[ERROR] stop: database is locked"
N=3  signal=SIGKILL  ms=5009  0 B
```

No episode is lost in production (each group's flush file is written and its worker saves it
later; the probe used CLAUDE_MEM_SKIP_EPISODE_LLM). Not a regression: v6.27.0 is killed under any
lock past ~5 s. tests/hook-db-busy.test.mjs "Stop exits inside its timeout" runs Stop with an
empty buffer, so it cannot see this. Possible fix: after the first busy failure in a flush, set
busy_timeout 0 on that handle (flushEpisode already shares one handle across its groups) and let
the workers save the rest.

### P3-2 — SessionStart under a held lock is still killed at 15 s with no context when a leftover episode buffer and an orphan buffer exist

Files: `hook.mjs:3252-3253` (flushLeftoverEpisode, adoptOrphanEpisodes), `hook.mjs:3326`.

The flushes run before the handler's own connection and open theirs with DB_BUSY_TIMEOUT_MS
(5000): one 5 s wait per flushed buffer, then 5 s for runSessionStartDbMutations, which 918eaad1
now catches. `p5-ss-lock.mjs <source> <orphans> [noleft]` under a 20 s lock (orphan = a buffer
`ep-<project>@h<dead pid>.json`, what a Claude Code process closed mid-turn leaves):

```
compact, no buffers          status=0       ms=5093   context: yes
compact, leftover buffer     status=0       ms=10121  context: yes
startup, 1 orphan            status=0       ms=10113  context: yes
compact, leftover + 1 orphan signal=SIGKILL ms=15018  0 B
```

Not a regression (v6.27.0 exited with 0 B under any such lock). The test covers /clear with no
pending buffer only. Same fix shape as P3-1.

### P3-3 — Every Stop's summary worker now waits up to 275 s on a flush file whose worker is dead, ~82 MB each

Files: `hook-llm.mjs:1588` (default wait = ceil(episodeWorkerMaxMs()/1000) = 275 s, was 15),
`hook-llm.mjs:1643` (pending kept while any file of the stem exists).

The wait does not drop a stem whose claiming pid (`.w<pid>`) is gone, and it does not check
`summarySuperseded` before waiting, although Stop spawns one worker per turn. A dead claimed file
is easy to get: under a 25 s lock the episode worker's write threw, the worker died and left
`ep-flush-1792186904669-fea9b32d.w1183886.json` (`p3-worker-lock.mjs`; recovered correctly later,
see claim 1). With such a file (any project: the snapshot is not narrowed to this one), a summary
worker started by hand was alive after 7 s at RSS 82 420 kB and would stay up to 275 s:

```
node hook.mjs llm-summary sess-x work--invoice-app 1   # RSS 82408 kB at 4 s, 82420 kB at 7 s
```

So each Stop in the ~275 s after a worker death leaves an ~82 MB process for ~275 s (about 14 at
one turn per 20 s). v6.27.0 bounded each at 15 s. Possible fix: filter stems whose claimed pid
`processAlive` says is gone, and test summarySuperseded inside the loop.

### P3-4 — Upgrade window: a v6.27.0 episode worker can outlive the 275 s bound, and its unclaimed file is handed on

Files: `hook-llm.mjs:1099`.

v6.27.0 workers do not claim their file, so only the age gate protects them. Their bound is
longer than v6.28.0's: v6.27.0's keyed-provider fallback gave the CLI a fresh full timeout
(diff of 79e591f1), so 5 s + 2 x (LLM_SEM_TIMEOUT 60 s + 45 s + 45 s) = 305 s plus DB waits, versus
episodeWorkerMaxMs() = 275 s. A v6.27.0 worker still running past 275 s (keyed provider failing,
slow CLI, contended slots) when a v6.28.0 SessionStart runs gets its file handed on, and the event
is saved twice (saveEvent has no dedup). Narrow window; code-derived, not probed. Unclaimed vs
claimed handling itself verified (claim 1).

### P3-5 — A recovered episode from another project is stamped with the recovering session's git branch

File: `hook-llm.mjs:451` (`branch: getCurrentBranch()`).

recoverOrphanEpisodeFlushes hands on flush files of every project (the runtime dir is shared), and
the new worker inherits the SessionStart's cwd. The row's project comes from the file
(`episode.project`), but `getCurrentBranch()` runs `git rev-parse` in the process cwd, so the row
gets project B's branch (or null), which `search --branch` filters on. Code-read, not probed.

## Claims

1. **"An llm-episode worker paused past episodeWorkerMaxMs() keeps its flush file, so SessionStart's
   recovery does not save the episode a second time; a dead worker's file is still handed on once."**
   **True for v6.28.0 workers.** Probe: claimed file `ep-flush-1700000000000-livepid1.w<live pid>.json`
   aged 10 min was skipped while an unclaimed sibling was handed on
   (`handed ["...unclaim1.recovered.json"]`). Dead worker: the file left by the worker that died
   under a lock, aged 10 min, went `.w1183886.json` -> `.recovered.w1253983.json` -> deleted, rows
   5 -> 6 (saved once). `.recovered` names are excluded by `m[2]` (`hook-llm.mjs:1099`). Exceptions:
   v6.27.0 workers during the upgrade (P3-4); a pid read across a PID namespace (container sharing
   the data dir) reads as dead; a worker that dies after its write and before its unlink is saved
   twice (pre-existing window).

2. **"SessionStart under a write lock held past its 5 s busy wait exits 0 with the memory context,
   including after /clear and /compact."** **True without pending episode buffers; false with a
   leftover buffer plus an orphan buffer** (SIGKILL at 15 018 ms, 0 B; P3-2). compact alone 5093 ms
   with context; compact + leftover 10 121 ms with context.

3. **"UserPromptSubmit and Stop no longer reach their 5 s host timeout under a held lock, and the
   prompt-time context is still injected."** **UserPromptSubmit: true** (1592 ms, 345 B, the lesson
   injected, same 345 B as without the lock); user-prompt-search.js 555 ms with its injection;
   pre-compact 77 ms; post-tool-failure 78 ms. **Stop: false with 3 sessions' work in the buffer**
   (SIGKILL 5009 ms), 4592 ms with 2 (P3-1). Separately, the shorter wait loses writes v6.27.0 made
   under 1.5–4.5 s locks (P2-2).

4. **"Cluster-merge, narrow/wide re-enrich and save-enrich send stored rows to the model as data
   (system prompt holds instructions + MEMORY_INPUT_GUARD)."** **True for those four sites**
   (`hook-optimize.mjs:469`, `:1272`, `lib/save-enrich.mjs:135`; the split reaches every leg:
   callModelAPI `body.system`, callOpenRouterAPI `role: 'system'`, callModelCLI/Async and
   execClaudeCliSync via `flattenForCLI` with a per-call boundary marker). **The parallel prompts of
   the same daily run are not covered** (P2-1).

Also checked, no defect found: 79e591f1 deadline (all four keyed->CLI fallbacks use
`fallbackBudget`, `haiku-client.mjs:375/478/533/592`); 6 MB PostToolUse payloads through
post-tool-use.sh (Read 146 ms, Edit 169 ms, tool_name last 153 ms); salvaged Bash command scrubbed
before and after the cut, diagnosis lines scrubbed (`hook.mjs:862` passes `scrub: scrubSecrets`);
NOT_EXCLUDED_HANDOFF_SQL parameter order at all 9 sites (Stage -1/0/2 and pickHandoffToInject,
both arms each, plus the dashboard pointer) and `session_id NOT NULL` in the schema;
restoredExplicit has no human-initiated writer of -1/-2 to undo (every COMPRESSED_AUTO writer is
unattended and now guarded, including search-scoring runIdleCleanup); projectFileKey import order
in SOURCE_FILES (cite-recall-path 104 before record-once 156, so a killed swap cannot leave the new
record-once over the old cite-recall-path); launcher exit-listener heals spawn synchronously.
