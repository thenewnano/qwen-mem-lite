## Report (defects): pre-release defects review of `20d94507..94ae06df` (v6.31.0)

Two P1s, two P2s and two P3s. The worst one: on some damaged WALs, running `doctor` writes the damaged log into the main file and empties the log, and every surface now tells the user to run `doctor`.

I worked on `git archive` copies under `~/.cache/tmp/defrev-631`, with LLM keys unset, `MEM_NO_AUTO_ADOPT=1`, and my own `HOME` and `CLAUDE_MEM_DIR`. That directory is deleted, and the repo was not touched (`git status` clean).

### P1-1: `doctor` writes a damaged WAL into the main file (contract 2a, 2b)
- **Where:** `install.mjs:3138-3160`. Doctor's database check only fails when its read-only query `SELECT … FROM sqlite_master` fails. If that query passes, doctor opens a read-write handle for the FTS integrity check and closes it normally with `rwDb.close()`. With no other session open, that close checkpoints the damaged WAL into the main file and empties the WAL. No `.corrupt` copy is kept.
- **Why it matters now:** this doctor code did not change. What changed is that the WAL is no longer deleted on open, and the server (`server.mjs:258`), the CLI (`mem-cli.mjs:4294`) and the SessionStart notice all send the user to `doctor`.
- **Fixture:**
  - Build the store with ensureDb: 200 rows, `wal_checkpoint(TRUNCATE)`, keep that main file as the pristine copy.
  - Grow a WAL on a raw connection: 40 inserts, `VACUUM`, 1 insert; copy the -wal while the connection is open, then put the pristine main file back.
  - Fill bytes 0..63 of the newest frame of page 34 (the `events_fts_config` leaf) with 0xff, re-sign the checksum chain the way `plantCorruptWal` does, and add a 32 KB zero -shm.
- **Population:** I scanned 100 pages × 6 offsets.
  - 34 of 600 trials failed to open with SQLITE_CORRUPT or NOTADB.
  - In 4 of those 34 (pages 34 and 41) doctor's read-only query still passed. Those are the cases this finding and P2-2 cover.
- **Result, all as printed (`cli.mjs recent` → "Next: run `… doctor`", then `cli.mjs doctor`):**
  ```
  before: db d4afa6aa7d10 (= pristine)  wal 2109472
  doctor: ⚠ FTS5 integrity issues … ✓ FTS5 rebuilt
  after:  db 22ab45e84459  wal 0
  quick_check(main) = SQLITE_CORRUPT; open = SQLITE_CORRUPT; remedy now = set-aside
  ```
- **v6.30.2 on the same fixture:** the hook recovers on its own; the main file passes `quick_check` (ok, 200 rows) and the WAL is deleted.

### P1-2: `scrubHead` stores part of a quoted secret (contract 1a)
- **Where:** `utils.mjs:381-385`. Replacements inside the 14096-character window (one big key) can shrink the text enough to pull the window's edge back inside the 10000 characters that are kept.
- `dropCutTokenAtEnd` only drops back to the last whitespace. A quoted value that contains spaces is left unterminated, and none of the quoted patterns match it.
- **Repro:**
  ```
  node -e "import('<tree>/utils.mjs').then(({scrubHead,scrubSecrets})=>{const key='-----BEGIN RSA PRIVATE KEY-----\n'+('MII'+'Qx7'.repeat(20)+'a\n').repeat(100)+'-----END RSA PRIVATE KEY-----\n';const s='{\"password\": \"correct horse battery staple\"}';const p=key+'note '.repeat(4000).slice(0,14096-30-key.length)+s+' '+'tail '.repeat(600);console.log(scrubSecrets(p).slice(0,10000).match(/\{\"password[^}]*\}/)[0]);console.log(scrubHead(p,10000).slice(-36))})"
  → {"password": "***"}
  → ote note{"password": "correct horse 
  ```
- **End to end:** `hook.mjs user-prompt` on the same kind of prompt stored `{"password": "correct horse ` (row length 7498). v6.30.2 stored `"***"`.
- **Same leak in other shapes:** `DB_PASSWORD="a b c"`, `secret = 'my dog has…'`, and `password = "…"`.
- **Second shape:** a prompt with no whitespace at all (minified JSON with a 4200-character `"privateKeyData"`). `dropCutTokenAtEnd` keeps the cut token, so 29 of the 36 characters of a `ghp_` token are stored. v6.30.2 stored none.

### P2-1: a schema error that comes from the WAL alone can never be cleared
- **Where:** `lib/db-unusable.mjs:169-170`. The `!schema` check skips the `wal` kind, so the `schema` kind prints no command and never mentions the WAL.
- **Fixture:** in the WAL frame, `CREATE TABLE zz_extra(x)` → `(x `, checksums re-signed; main file pristine; one `.bak` snapshot beside it.
- **6.31.0:** "malformed database schema (zz_extra)"; doctor says "Restoring one replaces the database file, so copy the broken file aside first".
- **Following that advice** (`cp db db.broken && cp snapshot db`): the open still fails with the same SQLITE_CORRUPT, because the kept WAL is replayed over the snapshot.
- **v6.30.2:** the open succeeds.

### P2-2: doctor gives no repair step where the server promises one
In the page-41 case (`schema_version` leaf), doctor prints only "⚠ DB schema: could not determine compatibility … (database disk image is malformed)". There is no ✗ Database line and no `mv` command. The server says "Run `…doctor` for the repair step". The cause is the same as P1-1.

### P3
- **-shm changes (contract 2a says it must not):** after `hook.mjs session-start` on the damaged fixture, the -shm hash went `c35020473aed` → `3af9d234ae12`. The db and -wal were unchanged. The tests only compare the db and -wal.
- **The kept copy can be overwritten:** the `wal` command is a plain `mv … -wal.corrupt`. A second incident silently replaces the earlier kept copy, even though the note says it "keeps the log".

### Checked, no defect found
- **Prompts up to 14096 characters:** the same code path as v6.30.2 (`utils.mjs:9`, `:36`, `:383`), so the stored text is byte-identical.
- **Cut-off keys at the window edge:** 11 encodings × 200 trials (LF, CRLF, JSON `\n` and `\r\n`, double-escaped, indented, string concatenation, PGP, OpenSSH, quoted, markdown), plus every edge position across the END line (477 trials): 0 leaks.
- **Private spans:** the hook strips them on the whole prompt before the scrub (`hook.mjs:3600`).
- **CRLF and surrogate pairs:** no regression found.
- **Time at the 256 KiB cap:** at most 95 ms across 12 crafted shapes (load average 30).
- **Shell quoting** of a path containing a space, `'`, `$` and `"`: the command runs and moves the file.
- **Empty or missing WAL** falls to set-aside or restore. Both consumers (`hook.mjs:2786`, `dbCheckRemedy`) handle the new `wal` kind.
- **No automatic delete left:** no remaining code path deletes or moves -wal/-shm on its own, and nothing sets `walRecoveryAttempted`.
- **Concurrent openers:** 8 hooks + 2 CLI processes at once, ×8 runs on each of two fixtures. The db and -wal were byte-identical afterwards every time.
- **Tests:** baseline 36 + 14 + 12 pass, and 4 of the D#522 cases pass. Every mutation was killed:
  - window margin removed;
  - `dropCutTokenAtEnd` removed;
  - `walSize >= 0`;
  - `!schema` removed;
  - remedy deletes the WAL instead of moving it;
  - WAL delete put back into `ensureDbWithWalRecovery`.
