# Pre-tag review (defects): install and doctor area, v6.27.0..c93c370e

Reviewer lens: defects. Scope: install.mjs, adopt-cli.mjs, claudemd.mjs, cli.mjs, lib/hook-prune.mjs,
lib/install-shape.mjs, lib/npx-run.mjs, lib/plugin-key.mjs, lib/db-unusable.mjs, source-files.mjs,
package.json, .claude-plugin/*.json, install-related README (none changed: README diff is
retrieval/FAQ text only; hooks/hooks.json unchanged).

Verdict: no P1. One P2 (update-path recovery), eight P3.

Sandbox for every probe: /run/user/1000/review-install/ (deleted after the review), HOME,
CLAUDE_CONFIG_DIR and CLAUDE_MEM_DIR inside it, MEM_NO_AUTO_ADOPT=1, CLAUDE_MEM_SKIP_UPDATE=1,
ANTHROPIC_API_KEY / OPENROUTER_API_KEY unset, trees from `git archive v6.27.0` and
`git archive c93c370e`, a fake `claude` (Node script: records its args, keeps mcpServers in
`$CLAUDE_CONFIG_DIR/.claude.json`, can fail `mcp add`). Installs used `install --dev` (no network).

Disclosure: one probe (G2/G3, first attempt) ran with a PATH whose node bin directory also holds
the REAL `claude` (2.1.302). It ran `claude mcp remove/add -s user` with CLAUDE_CONFIG_DIR pointing
at the sandbox; the registration landed in the sandbox's `.claude.json` (read back), and
`~/.claude.json` shows no user-scope mcpServers. Re-run with a node-only PATH; only the re-run's
results are used below.

## Findings

### P2-1. A killed update swap from v6.27.0 leaves both recovery paths unable to load (install.mjs and hook-update.mjs)

Files: install.mjs:73, :75, :110-111, :143-144 (named imports of exports v6.27.0's libs lack,
plus a module v6.27.0 does not have); hook-update.mjs reaches the new lib/edit-distance.mjs
through project-utils.mjs:5, and `cjkIndexTerms` through utils.mjs:34 -> nlp.mjs.

What happens: hook-update.mjs swaps files one rename at a time in the NEW release's
SOURCE_FILES order (`buildSwitchablePaths` = SOURCE_FILES + scripts + node_modules). install.mjs
is index 28 of 167, while what it newly imports sits later: lib/npx-run.mjs (43, a new file),
lib/install-shape.mjs (89: `probeRuntimeRootsSdk`, `isUnprovisionedPluginRoot`),
lib/plugin-key.mjs (95: `pluginSettingsScopes`), lib/hook-prune.mjs (105: `ourInstallRoots`,
`unconfirmedDeadPrefilters`). A swap killed after index 28 and before 105 leaves an install.mjs
that cannot load: `repair`, `cleanup` and `install` from the code home all die at link time.
hook-update.mjs (index 17, unchanged) cannot load either for kills after 22..31 and 36..144
(project-utils.mjs new, lib/edit-distance.mjs at 145 not yet in place). This is the exact class
the v6.25.3 pre-ship delta review rated P2 and fixed for lib/proc-lock.mjs with a namespace
import; the guard test (tests/update-residue-faces.test.mjs:924) mixes proc-lock.mjs only, so the
suite cannot see this.

Regression evidence (AST walk of the static import graph at every split point, script kept at
/tmp/claude-1000/-home-ai-dev-claude-mem-lite/b8af40f3-944d-41ee-99fa-709afd7f7f5d/scratchpad/tools/mixed-tree.mjs):
- v6.25.3 -> v6.26.0: install.mjs and hook-update.mjs load at all 168 split points.
- v6.26.0 -> v6.27.0: same, all 168.
- v6.27.0 -> c93c370e: install.mjs fails at 77 split points (i = 28..104), hook-update.mjs at
  119 (i = 22..31, 36..144).

Reproduction (real files, sandbox): old tree overlaid with the new SOURCE_FILES[0..60]:
```
$ node mixed60/install.mjs cleanup --dry-run
SyntaxError: The requested module './lib/install-shape.mjs' does not provide an export named 'isUnprovisionedPluginRoot'   (exit 1)
$ node -e "await import('mixed60/hook-update.mjs')"
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '.../mixed60/lib/edit-distance.mjs' imported from .../mixed60/project-utils.mjs
$ echo '{...SessionStart...}' | node mixed60/scripts/hook-launcher.mjs hook.mjs session-start
[claude-mem-lite] Detected broken install (edit-distance.mjs) — running self-heal
.../mixed60/install.mjs:111  isUnprovisionedPluginRoot, ... SyntaxError ...
```
Controls: the pure v6.27.0 and pure c93c370e trees both run `cleanup --dry-run` with exit 0.

So the launcher's self-heal fires, spawns `install.mjs repair`, and that dies; the 6 h cooldown
then holds. The only way out is manual (`npx claude-mem-lite@latest install`, which cli.mjs's
broken-install message does name for ~/.claude-mem-lite). Trigger: a hard kill or power loss
inside the rename loop (two journal writes per file, sub-second), so the population is small,
but it is a direct-install user of the released v6.27.0 left with dead hooks, CLI and repair.

Fix options: (a) reorder SOURCE_FILES so leaf modules precede the entry points (install.mjs,
hook-update.mjs, hook.mjs, cli.mjs, server.mjs). This takes effect for the v6.27.0 -> v6.28.0
update itself, because the old updater reads the tarball's manifest. (b) In install.mjs, import
the four changed modules as namespaces with fallbacks, and load lib/npx-run.mjs dynamically
(a namespace import of a missing FILE still fails). Extend the update-residue mixed-tree case to
every module whose export set changed since the last tag, not proc-lock alone.

### P3-1. A user's launcher hook that runs one of our entry names is still deleted, and vouches for its own root

File: lib/hook-prune.mjs:91 (`OUR_HOOK_EVENTS.has(m[1]) || OUR_LAUNCHER_SCRIPTS.has(m[2])` returns
true whatever the launcher's root is) and :151 (`ourInstallRoots` then adds that root).

On a machine that never installed the product (home B: no ~/.claude-mem-lite):
```
settings: node "<H>/tools/scripts/hook-launcher.mjs" hook.mjs stop          (user file exists)
          bash <H>/tools/scripts/post-tool-use.sh --notify                   (missing)
          bash <H>/other/scripts/post-tool-use.sh --notify                   (missing)
$ install.mjs cleanup-hooks
  ✓ Removed 2 claude-mem-lite hook configurations from settings.json:
    Stop: node ".../tools/scripts/hook-launcher.mjs" hook.mjs stop
    Stop: bash .../tools/scripts/post-tool-use.sh --notify
```
Same on install over a v6.27.0 install (home A): of 8 user hooks, U6
(`<H>/tools/scripts/hook-launcher.mjs hook.mjs stop`) and U8 (`… scripts/pre-tool-recall.js`)
were removed, the other 6 kept. The update prune drops such a hook when its target is missing
(`scripts/pre-skill-bridge.js` under a user launcher: removed). The removed commands are now
printed, which limits the damage. Only users who copied our layout are exposed (the E2E B16
cases were exactly that), and v6.27.0 deleted more. Suggestion: accept the entry-name anchor only
when the launcher file is gone (the relocated, deleted install it exists for), and require
`isProductRoot` when the launcher exists.

### P3-3. uninstall exits 0 and prints "Done!" with the MCP server still registered

File: install.mjs:1745-1756. With no `claude` on PATH, `uninstall --purge` warns and prints the
manual command, then exits 0. `.claude.json` still registers `mem-lite` to
`<H>/.claude-mem-lite/server.mjs`, which --purge has just deleted (home U, read back). install now
exits 3 for the mirror case, so a script running `uninstall && …` reads a leftover registration as
success. Suggest a non-zero exit when `claudeMissing || stillRegistered.length`.

### P3-4. "not on PATH" warning is false when ~/.local is a symlink

File: install.mjs:753 (`resolve(d) === localBin` is lexical). Home L: `~/.local -> real-local`,
PATH holds `<H>/real-local/bin`:
```
  ✓ CLI: <H>/.local/bin/claude-mem-lite → …
  ⚠ <H>/.local/bin is not on PATH, so the command is not found yet — add it: export PATH=…
$ command -v claude-mem-lite  ->  <H>/real-local/bin/claude-mem-lite
```
Compare with realpath (or `sameDir`) on both sides.

### P3-5. cleanup-hooks on a mixed machine with a clone an earlier release emptied: zero hooks, and a remedy that skips the known fix

Files: install.mjs cleanupHooks (calls no restoreMarketplaceHooksManifest), install.mjs:322.
4edef815 makes cleanup-hooks doctor's orphan repair on plugin machines. Home M (plugin + direct,
clone emptied by the v6.27.0 install):
```
$ install.mjs cleanup-hooks
  ✓ Removed 11 claude-mem-lite hook configurations from settings.json:
  ⚠ The enabled plugin's hooks/hooks.json registers none — every hook is now unregistered … Repair: no usable
    marketplace copy to restore from — reinstall the plugin (/plugin uninstall then /plugin install), then restart Claude Code
clone after: [ M hooks/hooks.json]
```
install puts the clone back (`git checkout -- hooks/hooks.json`) and doctor names that fix, but
this path tells the user to reinstall the plugin. I could not check whether a reinstall rebuilds
the cache from git objects or from the dirty working tree. If it uses the working tree, that remedy
does not restore the hooks. Suggest calling restoreMarketplaceHooksManifest here, then
re-evaluating the hint.

### P3-6. On Windows the SessionStart self-heal never sees install-managed hooks, so the "one session" duplicate window has no end there

File: plugin-cache-guard.mjs:112 (unchanged, outside my list, made load-bearing by 8d47cf8f).
`hasInstallManagedHooks` looks for `.claude-mem-lite/` in `JSON.stringify(settings.hooks)`. A
Windows settings path serialises with backslashes:
```
command: node "C:\Users\u\.claude-mem-lite\scripts\hook-launcher.mjs" hook.mjs session-start
install.mjs ownership (isMemHookCommand): true
self-heal gate hasInstallManagedHooks:   false
```
Before 8d47cf8f the emptied clone file was carried into new cache versions whenever the pull
succeeded. That is uncertain, because whether Claude Code copies the working tree is not
observable here. Now only the self-heal clears new versions, and on Windows it never runs, so a
Windows plugin+direct machine registers both hook sets after every plugin update until the next
manual `install`. README lists Windows as "Installs, not CI-covered". Suggest making the gate
separator-agnostic, or reusing lib/hook-prune's predicate.

### P3-7. A v6.27.0 code home's own repair reads the v6.28.0 installer's exit 3 as "Repair failed"

File: v6.27.0 install.mjs:3905 (`execFileSync(..., [tarballInstaller, 'install'])`, no status
check). runRepairInstaller only helps once the repairing code is v6.28.0. The launcher heal on a
v6.27.0 direct install runs v6.27.0's repair, which downloads the latest tarball (v6.28.0). If that
child exits 3, the old repair prints "Repair failed" plus the curl fallback, and the launcher does
not retry its import, although the files were resynced. Narrow: exit 3 needs no `mem-lite`
registration that runs SERVER_PATH AND `claude` unusable. With claude missing but the registration
present, install exits 0 (probe G2). Not fixable on the old side. Listed so the CHANGELOG upgrade
note can mention it.

### P3-8. doctor reads an older cache version whose first-start npm install failed as "not installed yet"

File: lib/install-shape.mjs:313-320 `isUnprovisionedPluginRoot`. The `.npm-install-failed` marker is
written only by the v6.28.0 launch.mjs. A cache version ≤ 6.27.0 whose npm install failed (no
node_modules, no marker) still gets the ⚠ "installs its dependencies on first start" and stays out
of the ✗ count. That is the 191ced11 false pass, still reachable when the active plugin cache is
older than the tree doctor runs from. From reading the code only; not probed.

## Claims

1. **install never writes the marketplace clone; restores hooks/hooks.json only when it is
   exactly the emptied file; doctor names the edit.** TRUE (probe, home M). The v6.27.0 install
   emptied it (`M hooks/hooks.json`). The c93c370e doctor printed "Cause: hooks/hooks.json was
   emptied by an earlier claude-mem-lite install. Fix: git -C … checkout -- hooks/hooks.json".
   The c93c370e install printed "put back hooks/hooks.json", the clone status was then empty,
   and the cache copy was still cleared. No other write to `plugins/marketplaces` in install.mjs,
   hook.mjs, hook-update.mjs, lib/ or scripts/ (grep). Two nuances. "Exactly" means `_note` text
   plus empty `hooks`, not a byte compare (`description` and other keys are not compared), and
   `git checkout --` restores the INDEX version. uninstall and cleanup-hooks do not restore (P3-5).
2. **A hook is ours only when the product's root or one of our entries anchors it; a user's own
   post-tool-use.sh / hook-launcher.mjs hooks survive install, uninstall, cleanup-hooks and the
   update prune.** PARTLY FALSE. True for the prefilter cases (existing, missing elsewhere,
   relative, `~`) and for user launchers running non-matching entries, on install, cleanup-hooks
   (homes A and B) and the prune (pruneDanglingMemHooks probe). False for a user launcher that runs
   `hook.mjs <one of our 7 events>` or `scripts/<one of our 5 scripts>`: removed on all four faces.
   Such a launcher also vouches for a dead prefilter-named hook beside it (P3-1). The first half of
   the claim, "one of our entries anchors it", describes that behaviour accurately. The survival
   half does not hold for those names. No duplicates after a v6.27.0 -> c93c370e install
   (11 entries per run before and after; the entry shapes of all 237 launcher-era tags are in
   OUR_HOOK_EVENTS / OUR_LAUNCHER_SCRIPTS, checked with git show over every tag).
3. **An unwritable config home (or symlinked settings.json whose target dir is unwritable) is
   refused before install, uninstall or cleanup-hooks changes anything.** TRUE for an existing
   config home and for the symlink target's directory (home D: exit 1 on all three, settings.json
   and .claude.json hashes unchanged, 0 calls to claude, CLI link kept). FALSE for an absent config
   home under an unwritable parent (P3-2).
4. **install exits 3 when only the MCP registration failed, unless a mem-lite entry already runs
   this install's server; repair treats exit 3 as success with a warning.** TRUE. Probes: add fails
   with nothing registered -> exit 3. No claude, existing registration -> exit 0 with "already
   registered" warning. No claude, no registration -> exit 3. runRepairInstaller against real
   child processes: exit 0 -> {mcpRegistered:true}, exit 3 -> {mcpRegistered:false}, exit 1 ->
   throws. No other in-tree consumer of the installer's exit status (grep: hook-update does not
   spawn install; the launcher spawns `repair`, which now exits 0 for this case). Old v6.27.0
   repair code: P3-7.

Tests run (single files, c93c370e working tree): tests/is-mem-hook-r3, install-flag-guard,
mcp-legacy-name-ownership -> 67/67 passed; tests/install-e2e -> 48/48 passed.

## NOT CHECKED

- Copy-mode (non --dev) install with a real `npm install`, and `npx claude-mem-lite` from the npm
  cache. isNpxRun was checked as a function against npm 11.19.0's libnpmexec/run-script source
  (`event: 'npx'`, `npm_lifecycle_script` = the single-quoted bin name) and 6 path/env shapes.
- `repair` and `self-update` end to end against GitHub (network, signed tarball). Only
  runRepairInstaller and the exit-code arms were read and probed.
- Real Claude Code behaviour: how a plugin cache version is materialised from the marketplace
  clone (working tree vs git objects), how often, and whether `/plugin install` repairs an emptied
  clone. This decides how large P3-5 and P3-6 are.
- Windows and macOS execution (Windows reasoning in P3-6 is from code plus a Linux probe of the
  string test). Symlinked ~/.claude directory as a whole.
- hook.mjs, scripts/hook-launcher.mjs, plugin-cache-guard.mjs and the bash prefilters beyond
  their interaction with install (another reviewer's area). The mixed-tree walk also lists hook.mjs,
  server.mjs and mem-cli.mjs failing in killed-swap windows, as every release with new exports
  does. The launcher's swap barrier covers the live swap, not a killed one. Not graded here.
- status/doctor `--json` shapes, `adopt --all` / `unadopt --all`, adopt's stray-sentinel refusal
  beyond reading the code (repo CLAUDE.md, README and findings.md give no false strays).
- Dynamic imports in the mixed-tree walk (static graph only). For example finishInterruptedSwaps
  -> hook-update.mjs adds to P2-1 rather than changing it.
