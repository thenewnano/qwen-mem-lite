## 结论

**问题出在安全性描述上。**

## 发现

### P1-1 自动重建会覆盖空闲页表里登记的在用表页，observations 的行被毁

**位置**
- `schema.mjs:2020-2023`，docblock 原文："The rebuild writes the indexes only, never a table … count(*) reads an index"。
- `schema.mjs:2064-2112`：只要检查结果不是 `ok`，就无条件执行 `BEGIN IMMEDIATE` 加 `rebuildIndexes`。错误行属于空闲页表或页引用类损坏时也一样。
- `install.mjs:3196-3198`，原文："As above, only indexes are rebuilt"。
- 还有 `CHANGELOG.md:13-15`、`CHANGELOG.md:26-27`、`README.md:961`、`README.zh-CN.md:736`。

**谁受影响**：库的空闲页表登记了一个仍属于某张表的页（`2nd reference to page N`），同时检查失败的用户。检查失败的原因可以就是
SQLite 报出的这条空闲页表损坏。
- 用户跑 doctor 是为了诊断，v6.30.9 却在一个写入明显不安全的文件上重写所有索引。
- 被重复引用的那一页被当作空闲页分配给索引，observations 那一页的行就没了。之后读出来的是被当成表行的索引单元。
- doctor 随后打 ✗ "not repaired by rebuilding the indexes"，读起来像是原有的损坏没修好。
- 同时 `DB stats` 打 ✓ "550 observations"。`fell` 列表为空，因为计数是上升的。
- 库能打开时，doctor 不给恢复命令。
- v6.30.8 的 doctor 在同一个文件上什么都不写。

**复现**：`scripts/prod-doctor.mjs`。
1. 用产品自己的 opener（`ensureDbWithWalRecovery`）建库，写 300 条 observation。
2. 建一张填充表再 DROP，制造空闲页。
3. 把空闲页 trunk 的第一个 leaf 项改成一个 observations 叶子页的页号。
4. 两份字节相同的副本分别跑两个版本的 doctor：

```

  [ok] FTS5 integrity: all indexes healthy
  [ok] DB stats: 0.8MB, 300 observations, 0 sessions
after: observations 300 rows, 300 with an intact title, sha1 2137772857

=== v6.30.9 doctor
  [warn] Database integrity issues detected:
      *** in database main ***
      Tree 5 page 5 cell 0: 2nd reference to page 65
      Page 101: never used
      wrong # of entries in index idx_obs_epoch_project
      Rebuilding the indexes...
  [fail] Database integrity: not repaired by rebuilding the indexes
      *** in database main ***
      Tree 5 page 65 cell 262: Rowid 263 out of order
      Tree 33 page 33 cell 0: 2nd reference to page 65
      Page 101: never used
      NULL value in observations.project
```

- 300 条真实行里丢了 13 条（300 − 287），另外多出 263 条垃圾行。
- 用的是默认页缓存，库只有 0.8 MB，所以触发这个问题不需要缓存淘汰。
- **另一种形状**：`scripts/freelist-doctor.mjs index` 和 `scripts/freelist-doctor.mjs fts-order`。用 writeStoreSnapshot 生成的库，
  即 VACUUM INTO 形状，加上同样的空闲页项改动。这时 SQLite 的检查只报索引那一行，没报空闲页表，原因见 P2-2。结果相同：
  v6.30.9 之后是 550 行、287 条完好；v6.30.8 不变。
- **相关观察**：如果空闲页表登记了多个在用页，SQLite 自己会拦下来。REINDEX 和 COMMIT 都抛 `SQLITE_CORRUPT`，事务回滚，表不变
  （`scripts/freelist.mjs 300 default all index`）。只登记一页时，这道检查拦不住。

### P2-1 回归集上，新步骤改动了普通表读得出的行；CHANGELOG 的"行数不变"看不到

**位置**：`CHANGELOG.md:26-27`，原文："Counted without an index, the observations table holds as many rows after the rebuild as

### P2-2 SQLite 3.53.4 在 VACUUM 过的库上跳过空闲页表和 "never used" 检查，doctor 打 ✓

**位置**：`schema.mjs:2037-2064`（`check()`），doctor 打 ✓ `Database integrity: ok` 的 `install.mjs:3205`。`CHANGELOG.md:10` 和
`README.md:959-961` 都没提这个局限。

**复现**：`scripts/prodshape2.mjs`。用 opener 建库、写 300 条，然后准备三份，都做同样的空闲页项改动：(a) 原样；(b) VACUUM INTO
出来的副本，也就是 `lib/db-backup.mjs:154` 做备份的方式；(c) VACUUM 之后的库，也就是 `lib/maintain-core.mjs:972` 的结果。

```
as opened:        ["*** in database main ***\nTree 5 page 5 cell 0: 2nd reference to page 65\nPage 101: never used","wrong # of entries in index idx_obs_epoch_project"]
VACUUM INTO copy: ["ok"]
after VACUUM:     ["ok"]
```

- `scripts/freelist-doctor.mjs null`：v6.30.9 的 doctor 打 `[ok] Database integrity: ok`。
- 同一个文件用 sqlite3 3.46.1 的 CLI 检查，会报出 `2nd reference to page 63` 和 `Page 101: never used`。
- 在副本里删掉 `CREATE VIRTUAL TABLE` 那几行 schema 记录后，3.53.4 也能报出这两条。

**机制**（读的是 `node_modules/better-sqlite3/deps/sqlite3/sqlite3.c`）：
- `tableSkipIntegrityCheck`（145201 行）只跳过 imposter 表。
- 虚表 `HasRowid` 为真，所以 146568 行的 `aRoot[++cnt] = pTab->tnum` 会把它放进根页列表，而它的根页号是 0。
- 如果哈希遍历时第一张表就是虚表，btree 层在 84392-84397 行看到 `aRoot[0]==0`，就当作部分检查：设 `bCkFreelist=0`，不检查空闲
  页表；只在 `!bPartial` 时才做的 "never used" 遍历也跳过。
- "VACUUM 改变了哪张表排第一"是我的推断。我只做了 A/B 对照，没有打印遍历顺序。

**后果**：在这类库上，P1-1 的空闲页损坏对检查是隐形的。之后任何一条索引错误都会触发重建，进而覆盖在用页。

## "not checked" 和"不重建"各在什么时候出现

| 条件 | 打印 | 是否重建 |
|---|---|---|
| FTS 检查时库被占用 | ⚠ `not checked — the database is in use…` | 否 |
| `dbWriteBlocked`（库更新，或另两个原因） | ⚠ `not checked — <reason>` | 否 |
| 检查抛出 CORRUPT / NOTADB 以外的错误 | ⚠ `not checked — <message>` | 否 |
| 检查抛出 CORRUPT / NOTADB | 当作检查失败 | 是 |
| 检查失败，**任何一条错误行都算**，包括 `2nd reference`、`never used`、`Freelist` | 列出前几行，然后 ✓、⚠ fell 或 ✗ | **是**（P1-1） |
| 重建遇到锁、磁盘满、IO 错误、只读、内存不足 | ⚠ `indexes not rebuilt`，不计 issue | 回滚 |
| `BEGIN IMMEDIATE` 遇到其他错误 | ⚠ `indexes not rebuilt`，不计 issue | 否（P3-4，doctor 走不到） |
| 库里没有 `observations_fts` | **没有任何 "Database integrity" 行** | 否（P3-3） |
| FTS 步骤外层 catch 捕获异常 | `FTS5 integrity check failed: …`，没有 integrity 行 | 否（只读了代码，没构造出来） |
