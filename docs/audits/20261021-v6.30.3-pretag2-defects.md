### Findings

**P3-1: key lines stored after overlapping BEGIN markers (leak direction, regression).** Location: `secret-scrub.mjs:813-818`, where `KEY_BEGIN_RE.lastIndex = end` was removed.
- **Mechanism:** a cut can end inside a BEGIN marker q whose trailing dashes start another BEGIN p. The candidate visits q, and q's match swallows p, so p is never read. v6.30.2 resumed at the cut end and found p.
- **Input:** `-----BEGIN ` + `-----BEGIN RSA PRIVATE KEY-----\n` + `-----BEGIN A×40 PRIVATE KEY-----BEGIN RSA PRIVATE KEY-----\n`, then 3 × (`-----BEGIN A×40 PRIVATE KEY` + `MII`+61 base64 + `\n`), then `after`.
- **v6.30.2:** `"-----BEGIN ***PEM_KEY*** PRIVATE KEY***PEM_KEY***"`. Pass-1 visited [11,106], cuts [11,94) and [106,527).
- **21f9ecd6:** `"-----BEGIN ***PEM_KEY*** PRIVATE KEY-----BEGIN RSA PRIVATE KEY-----\n-----BEGIN AAAA… PRIVATE KEYMIIG+fWdGWBsp9cr8o6x…"`, with all 3 key lines stored. Pass-1 visited [11,43]. In pass 2, p's line prefix has become `-----BEGIN ***PEM_KEY*** PRIVATE KEY`, so its prefix shape no longer strips the body lines.
- **When it happens:** a grid of 3,840 texts gave 252 leaks. Every one needs body lines prefixed `-----BEGIN <40+ char label> PRIVATE KEY`. With plain body lines the second pass erases them (0 leaks).
- **Adversary-only.** By the project's D#131 rule such shapes are accepted gaps, but this one is new in this release.

**P3-2: key lines erased by v6.30.2 only in a later pass are now stored (leak direction).** This is the archive's "14 windows" class. My population shows it keeps whole key lines, not only the header values and fragments the archive lists.
- **Example (JSON form):** `"-----BEGIN PRIVATE KEY-----\\\\\\\\nProc-Type:-----BEGIN PRIVATE KEY BLOCK-----\\r\\nComment:\\\\\\\\nlqKZhuMSC43WaY8I\\\\\\\\n-----BEGIN PRIVATE KEY-----\\\\nX-C:-----BEGIN PRIVATE KEY-----\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\nX-C:\\\\n\\rYQ9q…IzGa\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\\n4+F1/…PnRxV\\\\n4WINy6WIsCcBE7KBPJO4pI0N6hmvtCUi5vDuJkt/"`
- **v6.30.2:** `"***PEM_KEY***\\\\\\\\n***PEM_KEY***"`
- **21f9ecd6:** `"***PEM_KEY***\\\\n4WINy6WIsCcBE7KBPJO4pI0N6hmvtCUi5vDuJkt/"`
- **Mechanism:** the grown cut [108,240) erases BEGIN@108, which was invalid in pass 1. In v6.30.2 that BEGIN became valid in pass 2 and erased the 40-character line.
- **Population:** 40,000 nested texts gave 21 such texts and 43 kept lines:
  - 14 are 40+ characters, 20 are 16–39, 9 are under 16;
  - 15 start with `MII` or `b3Bl`;
  - 35 sit on their own line in the output.
- A second example kept `b3BlbnNzaC1rZXktdjExM/KCFxoE14` on its own line.

**P3-3: prose erased where v6.30.2 kept it.** The nested key's armor-header line past the outer key's end is now erased whole. That includes text after the outer key's cut run, which v6.30.2 kept under its rule that a cut line's base64 goes and the rest stays.
- **Input (JSON form):** `"-----BEGIN PRIVATE KEY-----\\\\\\\\\\\\\\\\nX-A:-----BEGIN PRIVATE KEY BLOCK-----\nProc-Type:\\\\\\\\\\\\\\\\nMItJ…7rZ\\qnbgr vgwh ewjdz\rPGnn+3+kKxHZV6so"`
- **v6.30.2:** `"***PEM_KEY***\\qnbgr vgwh ewjdz\rPGnn+3+kKxHZV6so"`
- **21f9ecd6:** `"***PEM_KEY***"`
- **Counts over 20,000 nested texts:**
  - 342 texts lose a standalone prose token. 340 of them lose it in pass 1, on a line the nested key reads as an armor header (95 at depth 0, 245 at an escaped depth). The other 2 lose it in a later pass.
  - Comment values were lost in 112 texts and X- header values in 177.
- No other class appeared. Every difference comes from a text where a cut grew or a BEGIN was skipped; there were 0 differences anywhere else.

**P3-4: the CHANGELOG overclaims (`CHANGELOG.md:14-15`).**
