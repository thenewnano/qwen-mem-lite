## P1

### P1-1 A snapshot whose only damage is its FTS5 index is called `bad`; doctor sets the store aside or names an older, smaller snapshot
lib/db-unusable.mjs:147 (`DAMAGE_CODE_RE` takes SQLITE_CORRUPT_VTAB), :179-180 (`PRAGMA integrity_check`
runs FTS5's integrity check and any FTS row makes the verdict `bad`); CHANGELOG.md:13-18.
Origin: the integrity gate came in with 7b0adf11 (before this delta). `checkSnapshot` keeps it
unchanged, and v6.30.5 ships it.

The module's own rule (:137-139, `isDbUnusableError`): "a damaged index is a HEALTHY FILE, and every
remedy below is wrong — and destructive — for one." doctor rebuilds a damaged FTS index without
losing anything (install.mjs doctor's FTS5 block). The snapshot walk does the opposite and treats such
a snapshot as damage.

Evidence on the D#553 corpus. snapfts.mjs uses snapcheck3's harness: same plants, same
`delete 5 --confirm`, and every snapshot that is not `ok`. It runs `PRAGMA integrity_check(200)`,
then the shipped `rebuildFTS`, then integrity_check again, all in memory:
```
rejected snapshots: 461 (456 bad, 5 unchecked)
every integrity_check row names FTS5:             102
pass integrity_check after rebuildFTS:            136  (132 bad + 4 unchecked)
  of those, observations == the population's undamaged template count:  136/136
  (241/241: 29, 1195/1195: 38, 1495/1495: 69)
```
Compare the 200 `ok` snapshots: 55 of them hold fewer rows than the template (doc's
passBelowTemplate). So for 136 of 661 snapshots (20.6%), v6.30.5 turns down a snapshot that holds
every row and points at a fresh empty store, or at an older snapshot with fewer rows.

Rendered (install.mjs doctor, garbage db plus plant p75-v10's snapshot, 241 rows, integrity_check:
`fts5: corruption found reading blob ... from table "observations_fts"`):
```
v6.30.5  ✗ Database: file is not a database
         None of the 1 backup snapshot(s) beside the database passes SQLite's integrity check and holds an
         observations table. Once every Claude Code session is closed, set the broken file aside so a fresh
         store is created on the next session: rm -f …-wal …-shm && mv …claude-mem-lite.db …claude-mem-lite.db.corrupt
v6.30.4  Restore the newest of 1 backup snapshot(s) once every Claude Code session is closed: rm -f … && cp …pre-delete-….bak …claude-mem-lite.db
```
Restoring that snapshot by hand and running `install.mjs doctor` gives "FTS5 integrity issues
detected … ✓ FTS5 rebuilt", then `observations` = 241 and `integrity_check` = ok.
With an older 200-row snapshot beside it (fixture869 pristine.db, mtime older), doctor says: "The newest one of the 2 …
fails SQLite's integrity check or holds no observations table; the next one passes …" and names
the 200-row file.
Repro: `rv-delta-probes/keep.mjs p75-v10 <dir>` (run from a worktree's tasks/d553 with
D546_WORK set), then `rv-delta-probes/scen.sh <wt> s1 "<bak>=claude-mem-lite.db.pre-delete-2026-10-20T00-00-00-000Z-1-0.bak@2026-10-20"`.

The doc and the CHANGELOG present "names … none of the other 461" as the result, and leave this out.
The measurement doc reports how many passing snapshots lack rows (55) and does not report the
converse (136 rejected snapshots that hold every row).
