## D#591：重建前的页检查

### 做法（`ruler.mjs`）

每个样本在私有副本上：

1. 新旧两棵树的产品打开器各跑一次（各自一份副本），记下打开器的 FTS 重建分支有没有触发。
2. s0 = 新打开器跑完的状态。在 s0 的副本上跑四臂：旧 / 新 × doctor 的 FTS 步骤（`checkFTSIntegrity`，不过就
   `rebuildFTS`）/ `rebuildIndexes`（`fts-check rebuild` 跑的那个）。每臂记：主文件和 `-wal` 的 sha1 前后是否相同；跑完后
   SQLite 还能读出的真值行（`plants.mjs` 的 `readable()`，所有普通表，按真值 rowid 和值比对）。
3. 新树的 `checkStorePages` 在 s0 另一份副本上的判定；`sqlite3` 3.46.1 的 `integrity_check` 有没有页级行。

### 事先登记的判定（写在跑之前，见 `tasks/specs/d591-page-gate.md`）

- ① 新把关拒绝的样本，库和 `-wal` 字节不变。
- ② 旧那一步让 s0 能读对的真值行变少或变值的样本，新的全部拒绝。
- ③ 新把关放行且重建了的样本，真值行和 s0 相比 0 丢 0 改。

### 结果

| | 结果 |
|---|---|
| ① 拒绝了却写了 | 0 |
| ② 旧那一步写了、丢或改了真值行 | 81 个样本，新把关在这 81 个上全部是 `damaged` |
| ③ 新的写了、丢或改了真值行 | 0 |

②按"那一步写了（主文件和 `-wal` 的 sha1 变了）"计（`sum2.mjs`）。`sum.mjs` 按事先写的代码还多报 2 个样本（log23-774、
two22-263）：这 2 个上旧 doctor 那一步**根本没写**（FTS 是好的，没有重建，sha1 和 s0 一样），`readable()` 却读出和 s0 差
1–2 行。同一份字节读两次结果不同，这是 r1 defects P3-6 记过的现象（坏页上的读不确定）。没写却读得不同的臂一共 97 个，落在
48 个样本上，差得最多的是 2 行；它们全是"读不出"，没有一个是"读出的值不同"。这 2 个样本的新把关也都是 `damaged`。

分臂（只算写了的臂）：

| 臂 | 写了的样本 | 写了且丢 / 改真值行的样本 | 丢 / 改的行 |
|---|---|---|---|
| 旧 doctor FTS 步骤 | 1,465 | 78 | 498 / 10 |

旧那几臂两次跑不一样：第一次是 72 个样本 494 / 10 行（doctor）、75 个样本 497 / 10 行（`rebuildIndexes`）。逐个比对
（`tasks/d591/cmp.mjs`、`stable.mjs`、`changed.mjs`、`arms.mjs`）：

- 两次都一样的只有两类：main21 的 10 个样本，两臂都把 1 行的值改了（main21-113 是第 667 条观察，r1 核对过）；log23 的
  8 个样本（log23-74、-145、-195、-350、-390、-495、-534、-664），两臂都让 54 行读不出来（log23-74 上是生成器建的
  `zz_noindex` 表，r1 核对过；其余 7 个也正好 54 行，没有逐表核对）。合计 18 个样本、每臂 442 行。
- 其余的都是"写了以后少读出 1–2 行"，两次跑各有二三十个样本进出，s0 本身两次读出的行数也差 1–3 行。这和上面没写的臂的
  读噪声一样大，所以不算到重建头上。CHANGELOG 只引两次都一样的 18 个，其余写成"54 到 60 个样本少读出一两行，不归给重建"。

（拒绝得比"必须拒绝"宽）。FTS 坏、页没坏的 508 个照旧重建。

打开器：两棵树的 FTS 重建分支在 2,769 个样本上都没触发（0 / 0）；这个人群到不了那条路，那条路只有单元测试
（`tests/store-pages-gate.test.mjs` 的 opener 一例）。

## D#592：doctor 对能打开的库

### 做法（`ruler592.mjs`）

每个样本在私有副本上：发版树的产品打开器跑一次得到 s0（打开器关闭时做过 checkpoint，s0 没有 `-wal`）；在 s0 的副本上按
doctor 的顺序跑数据库那一段：FTS5 自检（`checkFTSIntegrity`，不过且没被锁就 `rebuildFTS`），然后 `checkStoreIntegrity`。
记每一步前后的 sha1、`checkStoreIntegrity` 的结果和耗时，跑完后和 s0 比真值行。

事先登记（写在跑之前）：(a) 每个写了的步骤（sha1 变了），真值行和 s0 相比 0 丢 0 改；(b) `checkStoreIntegrity` 报 `damaged`
时，这一步不写。

### 结果

- (a) 0，(b) 0。2,755 个能打开的样本没有一个抛错。
- 结果：`ok` 1,234，`rebuilt` 30，`unrepaired` 52，`damaged` 1,439，`unchecked` 0，没有一个是被锁（这次跑没有别的连接）。
- `rebuilt` 30 个的首行：索引缺行（`row N missing from index …`）26 个，`non-unique entry in index …` 1 个，
  `row not in PRIMARY KEY order for observations_fts_idx` 1 个，检查在索引条目上抛 `database disk image is malformed` 2 个
  （这 2 个在第一次跑里是 `unchecked`，促成了 `22486ace`）。
- `unrepaired` 52 个，重建前后首行一样：检查抛 `database disk image is malformed` 48 个，`CHECK constraint failed in observations`
  3 个，`NULL value in observations.decay_seen_count` 1 个。重建跑了（库写了），真值行 0 丢 0 改，doctor 报 ✗。
- 写了的：FTS5 那一步 508 个（和 D#591 的新 doctor 臂一致），完整性那一步 82 个（`rebuilt` 30 + `unrepaired` 52）。
- `checkStoreIntegrity` 在这些小库上的耗时：p50 3 ms，p90 10 ms，p99 19 ms，最大 44 ms。

第一次跑（`2b8807e0`）是 `ok` 1,234 / `damaged` 1,439 / `unrepaired` 52 / `rebuilt` 28 / `unchecked` 2，(a) 0、(b) 0。

## 代价（合成库，发版树代码，`tasks/d591/cost4.mjs`）

每个数各在一个新的子进程里量，三次；峰值内存是 `process.resourceUsage().maxRSS` 减去只打开库不做事的那个子进程（59–60 MB）。
`checkStoreIntegrity` 是 doctor 新加的那一步（页检查 + `integrity_check`，库是好的所以不重建）。机器负载约 1。

| 库 | 页检查 | `integrity_check` | `checkStoreIntegrity` | 峰值内存（页检查） |
|---|---|---|---|---|
| 20 MB（7,000 条观察） | 35–42 ms | 79–81 ms | 108–109 ms | +40 MB |
| 145 MB（50,000） | 230–232 ms | 538–552 ms | 770–786 ms | +173 MB |
| 577 MB（200,000） | 854–962 ms | 2,167–2,292 ms | 3,011–3,236 ms | +613 MB |

`integrity_check` 单独跑的峰值内存只比只打开多 17–18 MB；`checkStoreIntegrity` 的峰值和页检查一样，内存来自 `serialize` 复制
整库。6.30.8 的 doctor 已经在跑的 FTS5 自检在 577 MB 库上是 2.1–2.2 s（`tasks/d591/cost3.mjs`，同一天），不在上表里。

锁字节页：1.12 GiB 的库（294,849 页，锁字节页 262145），页检查 `ok`，1,037 ms（`2d4739b6` 上量的，页检查之后没改过）；
去掉记锁字节页那一行 → `page 262145: never used`。
