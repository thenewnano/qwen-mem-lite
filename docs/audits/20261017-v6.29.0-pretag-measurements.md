# v6.29.0 pre-tag measurements

The readings behind the v6.29.0 release notes, with the tree, date and corpus of each. All on this
machine (Ubuntu 26.04.1, Node 26 unless stated), 2026-10-17 UTC. LLM keys unset and
`CLAUDE_CODE_PATH=/nonexistent` everywhere except the two A/Bs, which ran real `claude -p` legs.
Raw rows that hold whole model replies are not committed.

## FTS errors on this machine (not attributed to this release; D#424)

In the runs from 14:30Z to 15:47Z (the short-open signature below also once at 12:47Z, in the
`a3781349` matrix; one replay fault in the claims review at 16:10Z), writes through the FTS5
triggers on the large synthetic store above failed now and then with `SQLITE_CORRUPT_VTAB` ("database disk image is malformed") or `SQLITE_MISMATCH`,
or ended with the content-comparing `integrity-check` failing, on both trees and without this
project's code:

- v6.28.1 (`c5122c2f`), first opens: 2 of 8 threw plain `SQLITE_CORRUPT` after about 0.3 s (no
  stack captured) and 2 others ended after 1.2–1.3 s instead of about 8.5 s (a traced repeat of such
  an open logged `malformed` from the one-transaction glued pass, which rolled back); in two later
  loops of 16, none threw and 2 of the second 16 ended at 1.2–1.3 s; with the matrix's one throw,
  3 of 43 threw. `1a6085f7`, right after the first loop: 0 of 8.
- `1a6085f7`, one process per open as the hooks run it: 0 of 30 first opens; three complete fills
  logged `malformed` in 6 of 109, 7 of 110 and 3 of 106 opens, and each ended with both FTS indexes
  passing `integrity-check` (the failed batch rolls back and a later open writes it again).
- `1a6085f7`, the pass run to the end of the fill in one process on one connection (a loop of
  budgeted calls, or one call with no budget; a hook or the server runs one 250 ms call per open,
  though the server keeps its connection writing through the same triggers): 8 of 20 runs had
  errors or ended with the observations index failing `integrity-check`, 7 the latter, 2 of them
  with no error raised (14:58–15:33Z); then 0 of 10 single unbudgeted calls (15:37–15:47Z).
- The same writes replayed as plain SQL, no code of this project (per batch of 37 rows: `BEGIN
  IMMEDIATE`, a read of the row and the append, the cursor upsert, `COMMIT`; 166,666 rows),
  interleaved, 5 rounds on ext4 and on tmpfs (15:37–15:47Z): better-sqlite3 13.0.3 (SQLite 3.53.4)
  3 of 10 runs (two ended with the index failing `integrity-check`); Python's `sqlite3` (SQLite
  3.46.1) 1 of 10, a batch of appends of at most 45 bytes refused with "string or blob too big";
  `node:sqlite` (SQLite 3.53.4) 0 of 10.
- A minimal program on a fresh database (the schema, then 2,000 or 20,000 rows, then 50-row
  update batches, no pass) failed in 11 of 24 runs at 15:10Z, 2 of the next 31, then 0 of 54 to
  15:31Z; its Python twin (SQLite 3.46.1), run from 15:13Z only, 0 of 21.
- The 1000 concurrent-first-open trials above (morning) had no corruption.

Machine checks, none of which found anything: 8 processes writing and verifying a 1200 MiB pattern
for 900 s (10,493 passes, 0 mismatches); 7 processes hashing the 354 MB store in memory or
re-reading it for 300 s (11,405 digests, 0 mismatches); 664 copies of it to ext4 and tmpfs (0
mismatches). None of them ran while an SQL failure was being observed. The kernel log of this VM
(QEMU/Incus, host CPU Intel Core i9-14900K, microcode 0x133) shows Python processes killed by
general protection faults or segfaults on 2026-10-14, 10-15 and 10-16, and on 10-17 at 15:36:27Z
and 15:40:04Z (container Pythons, during the replay rounds).

Reading: not specific to this release (6.28.1 and a replay without its code hit it on SQLite
3.53.4; one Python run on 3.46.1 had a batch of appends of at most 45 bytes refused as too big, a
different symptom), and one deterministic program gave different outcomes run to run, so the
cause is below the SQL: this machine, or a memory-safety defect under the SQL layer. Which of the
two is not settled; the same replay on another machine would settle it (D#424). What it did to
the data: a batch failed and rolled back (rows compared with the seed after one such replay, in
the claims review: 166,629 appended, nothing else changed), or the FTS index was left inconsistent
with its rows (rows not compared in those runs). `fts-check rebuild` rebuilds an index from its
rows: on a 2,000-row store whose observations index was made inconsistent by rewriting 666 rows
with the trigger dropped, `fts-check check` exit 1, `fts-check rebuild` exit 0, then `check` exit
0, `integrity-check` ok, rows unchanged and all 666 found by the new term. `isFtsCorruptionError`
routes the `SQLITE_CORRUPT_VTAB` form to that remedy; a plain `SQLITE_CORRUPT` escaping `ensureDb`
(as 6.28.1's three throws were) takes `ensureDbWithWalRecovery`'s WAL/SHM deletion instead (D#427). A backup copy of this
machine's live store (15:54:55Z) passed `integrity_check` and all four FTS `integrity-check`s.

**Measured later the same day (17:14–19:24Z): the evidence points below the program (this CPU,
the hypervisor or a kernel), not at SQLite, the binding or this project's code; the same runs have
not been made on another machine.** Two probe rounds on this machine, arms interleaved in the same
minutes, 20,000 rows per run with fixed inputs, a run counted bad on an error, a failed FTS or
`PRAGMA integrity_check`, a non-zero exit or a database file other than the arm's usual one
(raw rows, local: `tasks/fts-corrupt-20261017/probe-2/`):

- A C program linked with the SQLite 3.53.4 amalgamation better-sqlite3 ships, no Node, run with
  address randomisation off (`setarch -R`), SQLite's random generator seeded and one thread: 50
  of 513 runs bad, all 50 files different from each other, while the 463 clean runs wrote one
  identical file. Its errors include "datatype mismatch" on INSERTs of literal values (21 runs,
  23 messages). Fixed inputs alone do not settle it: under `setarch -R` the pid, the clock and
  AT_RANDOM still vary. The case rests on that together with the next two points: which builds
  fail, the bursts in time, and faults in unrelated programs.
- The same fault in every GCC `-O3` build of SQLite 3.53.x tried without AddressSanitizer: better-sqlite3 13.0.3 as
  published (30/323) and rebuilt here with GCC 15 (26/323), the C program with better-sqlite3's
  defines (21/324) and with FTS5 alone (8/324), better-sqlite3 12.11.1 with SQLite 3.53.2
  (29/313). None in `node:sqlite` 3.53.4, built into the node binary (0/324 here, 0/523 in the
  first round), nor in the same GCC `-O3` build with AddressSanitizer (0/323, 0 reports), nor in the system `sqlite3` CLI and Python
  3.46.1 (0/594, first round). Every bad run was caught by an error or a check; none was silent.
- The kernel log, all boots retained since 2026-08-12: no fault line before 2026-10-11 15:41Z,
  then 9 segfaults or general protection faults to 10-17 16:29:57Z in processes unrelated to
  SQLite (container Pythons, the system python3.14, rustc).

What these do not separate: this CPU (Raptor Lake instability is known to be code-specific)
or the hypervisor or a kernel corrupting a process's register state. That needs the host: the C
program pinned per physical core there, outside the VM, and a per-core stress test. Nothing in
claude-mem-lite is implicated.
