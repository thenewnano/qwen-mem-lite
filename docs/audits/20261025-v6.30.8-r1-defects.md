## F1 · P2 · schema.mjs:1724 (sweepMoveCopies), 1784-1806, 1744 (`new Database(copy)`): a mover's private copy removed while it is being written gets replaced by an EMPTY store, and the old store is then deleted

Chain:
1. Opener A runs `VACUUM INTO` into `DB_DIR/.unhidden-move-<pidA>-<hex>`.
2. Opener D starts its own move and calls `sweepMoveCopies()`. That keeps a copy only if `process.kill(pid, 0)` succeeds AND its mtime is under 1 h old (line 1802). So D removes A's live copy whenever D cannot see A's pid (another PID namespace or another host on a shared HOME/NFS data dir), or when A's copy looks more than 1 h old (an NFS server clock behind the client, a clock jump).
3. A's VACUUM INTO keeps writing to the unlinked inode and reports success. Then line 1744 `new Database(copy)` (no `fileMustExist`) creates a NEW EMPTY database at the copy's path. `journal_mode = WAL`, fsync, then `linkSync(copy, DB_PATH)` puts the empty file in place. Lines 1770-1775 then delete the old db, -wal and -shm.
4. D's VACUUM fails with SQLITE_IOERR_FSTAT (its source was unlinked). Its fallback finds nothing, and it opens the empty store.

Nothing checks that the file being linked is the file VACUUM wrote. The lossy window is the whole VACUUM duration, not only the reopen.

Evidence (all runs: old store with rows only in its -wal, same filesystem):
- D with a preload that makes `process.kill(other, 0)` throw ESRCH (simulating another PID namespace); A paused 2 s after VACUUM INTO (`scripts/pause-after-vacuum.mjs`, `scripts/foreign-pidns.mjs`). Result: 500 observations → `{"observations":0,"integrity":"ok"}`, old dir `[]`. Both openers then failed their insert with `FOREIGN KEY constraint failed`: the sdk_sessions row is gone too.
- Same pid namespace, A's copy `touch -d '2 hours ago'` while A is paused: 500 → 0, old dir empty.
- No pause at all: a 410 MB / 60000-row store, the copy `rm`-ed by hand at 69599232 bytes, while VACUUM was running: `[shim] VACUUM ok`, `linkSync … ok`, `{"observations":0}`, old dir `[]`.

v6.30.7, same two openers (with the foreign-pid shim): no copies, no sweep; the rename moved the store, 502/502 rows.

Suggested direction: open the copy with `fileMustExist: true` and check it is still the inode VACUUM wrote (fstat before and after); do not sweep a copy whose owner cannot be shown dead.

## F2 · P2 · schema.mjs:1736-1737 (`catch { return false; }`) with migrateUnhiddenStore's fallback at 1695-1697: any VACUUM INTO failure falls back to v6.30.7's two-step rename, which neither checks for a store already placed nor moves the files as one

Contract B3 limits the fallback to "SQLite cannot read the old store", and B2 says a store already placed is left alone. But the catch returns false for every VACUUM INTO error, and the rename loop never checks DB_PATH. Two triggers:

(a) **The data dir has less free space than the store** (VACUUM INTO needs a full copy's worth of space; a rename never did). It fails SQLITE_FULL, and the fallback renames db, then -wal, then -shm. An opener that opens between the first two renames writes without the log, and the old log is then replayed over its writes (the r2 P2-1 shape the range set out to retire). Forced with `SLOW_FAIL=1` (VACUUM throws SQLITE_FULL) plus a preload that runs another opener (insert "between") the moment the db file lands by rename:
  - 5353ab86: `{"observations":50,"integrity":"*** in database main ***\n2nd reference to page 64"}`; the "between" row is lost and the store is corrupt.
  - v6.30.7: identical output. So this is not a regression; contract B3/B5 still do not hold whenever the data dir is short of space.

(b) **Another opener's removal mid-move.** B opens the old store; A links its copy and removes `src`; B's VACUUM then fails with SQLITE_IOERR_FSTAT (observed). B's fallback skips the missing db but renames the old `-wal` and `-shm` next to A's placed VACUUM copy. Forced timing: A paused 2.5 s between `rmSync(src)` and `rmSync(src-wal)` (`scripts/rm-pause.mjs`); B's VACUUM delayed 1.1 s. B logged `renameSync …/claude-mem-lite/claude-mem-lite.db-wal -> …/.claude-mem-lite/claude-mem-lite.db-wal ok`.
  - With ensureDb (the test harness's opener), both openers exit 1 with `SqliteError: database disk image is malformed` at ensureDb's first pragma.
  - With ensureDbWithWalRecovery (the product's opener), B logs "DB corruption detected, attempting WAL recovery" and deletes the -wal. The final store holds 2002/2002 rows. A connection that had committed into the placed store's -wal before the rename would lose those commits; that variant was not reproduced.
  - Without forced timing: 40 trials × 8 concurrent openers gave 0 VACUUM failures and 0 fallback renames. So (b) needs narrow timing.

v6.30.7 runs the rename loop on every first open, so the same class of failure has a wider window there.

Suggested direction: in the VACUUM catch, return `!existsSync(src) || existsSync(DB_PATH)` as the open catch does. In the fallback loop, stop once DB_PATH exists, and never move a -wal or -shm whose db did not move in the same pass.

## F3 · P3 · schema.mjs:1762 → 1770-1779: a mover killed between its link and its removals leaves the old store behind for good, and a second hard link to the live store

DB_PATH exists from the link on, so no later open calls migrateUnhiddenStore, and nothing removes either file. Reproduced with SIGKILL right after `linkSync` (`scripts/pause-link.mjs`). After two later opens:
- `~/claude-mem-lite` still holds db, -wal and -shm;
- the data dir holds `.unhidden-move-254006-e04e566e` and `claude-mem-lite.db` with the same inode, `nlink` = 2.

Contract B1 (old files removed) fails in this case. The window is a few syscalls.

v6.30.7: no copy. A kill between its renames leaves the -wal behind instead (the r2 P2-1 state).

## F4 · P3 · schema.mjs:1724 / 1784: a mover killed mid-VACUUM while another opener completes the move leaves a full-size copy in the data dir for good, readable by others

The sweep runs only inside a later move, and none comes once DB_PATH exists. Reproduced: the "server" opener (VACUUM delayed 1.5 s) completed the move; the "hook" opener (copy written, paused) was SIGKILLed. After three later opens, the data dir still held `-rw-r--r-- 765952 .unhidden-move-389800-1fc34943` beside the 778240-byte store.

The copy takes the process umask (0644), not 0600. setup.sh creates DB_DIR with a plain `mkdir -p` (0755 under umask 022). So on a multi-user host the copy (and, until ensureDb's chmod, the placed store) can be read by other users.

Trigger: a hook killed at its timeout (2-15 s) during VACUUM. A 410 MB store moved in 0.86 s here, so it needs a large store or slow disk. Contract B4/B5 ("nothing left behind") fails in this case.

v6.30.7: nothing to leave behind.

## F5 · P3 · schema.mjs:1750-1775: the old files are removed before the new directory entry is durable

The copy and DB_DIR are fsynced before `linkSync`, and DB_DIR is not fsynced after it. The old db, -wal and -shm (in `~/claude-mem-lite`, possibly on another filesystem) are then unlinked straight away. With the data dir on another filesystem, a power loss within the journal commit interval can persist the unlinks but not the link, and then neither copy exists.

Not reproduced (reasoning only). v6.30.7 never removed anything; it renamed within one filesystem and failed across filesystems.

## F6 · P3 · install.mjs:204-213: the cross-filesystem claude-mem backup can be left partial, and later installs then skip it for good

The db backup is renamed into place first. A kill before the -wal is copied leaves `claude-mem-lite.db.legacy-backup-<ts>` without its -wal. Every later install returns `{"action":"skip"}`, because any `claude-mem-lite.db.legacy-backup-*` counts as done.

Reproduced (SIGKILL when the -wal copy starts, `scripts/kill-on-wal-copy.mjs`; data dir on tmpfs): the backup alone holds `{"observations":0}` of the 40 in the source; the second run gives `{"action":"skip"}`.

The source is left intact, so no data is lost. But the docblock's "a killed copy leaves no partial backup" holds per file, not per backup set.

v6.30.7: EXDEV thrown on every install, no backup at all.

## F7 · P3 (latent, not reproduced) · lib/db-unusable.mjs:239 with lib/snapshot-probe.mjs main(): the probe runs the product opener with the user's real HOME

checkSnapshot's child inherits HOME; only CLAUDE_MEM_DIR points at the private directory. main() checks `existsSync(DB_PATH)`, but ensureDb (schema.mjs:1824) checks again a moment later. If the private dir is removed in between (only F1's kind of sweep, here sweepSnapshotChecks run from another pid namespace or a stale clock, can do that), ensureDb runs migrateUnhiddenStore against the real `~/claude-mem-lite`. It would copy a pre-2.0.0 store left there into the private dir, delete the originals, and the parent then removes the private dir.

Race-only. Setting HOME to the private dir in the child's env would close it.
