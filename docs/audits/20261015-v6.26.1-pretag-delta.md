## Findings

### F1 — P2 — rulers.md:36: "would have on the hook's input too (no main-thread `toolUseResult` over 64 KiB)" is unsupported; the commit message's unqualified form is false

The transcript's `toolUseResult` is itself cut. On the frozen corpus's main thread, 114 Bash
results carry `persistedOutputPath`/`persistedOutputSize`: their `content` is the 2 KB
`<persisted-output>` preview and their `toolUseResult.stdout` is cut to ≤30,000 chars. These are
exactly the audit's "114 longer than content". 85 of them had a full output over 65,536
(84 between 64 KiB and the prefilter's 256 KiB head cap, scripts/post-tool-use.sh:52), max
1,347,605. Nothing in the repo measures whether the hook's `tool_response` carries the cut
or the full output, so "0 on the hook's input" cannot be read off the transcript. If it
carries the full output, the window would have fired on up to 84 main-thread calls.
Separately, 5f2011e8's "no toolUseResult over 64 KiB either" is false as written: 4 subagent
WebFetch `toolUseResult`s exceed 64 KiB (normalized max 90,459). The hook computes
`workerEntryFields` (hook.mjs:785-790) before it drops a subagent call (hook.mjs:859-869),
so the window path runs for those calls, although their entries never reach a gate. This
also bears on D#337's planned fix: reading `toolUseResult` would not give the hook's input
for these 114 calls either. Fix: drop the "would have on the hook's input too" clause, or
state that the transcript stores ≤30k chars, cite the 85, and say the hook's side is
unmeasured. Same caveat for the D#332 audit:64-68 sentence that pairs `tool_response` ↔
`toolUseResult`.
Repro: `C=<scratchpad>/d332/corpus; for f in "$C"/*.jsonl; do grep -o '"persistedOutputSize":[0-9]*' "$f"; done | awk -F: '{n++; if($2>65536)b++; if($2>65536&&$2<=262144)w++; if($2>m)m=$2} END{print n,b,w,m}'`
→ `114 85 84 1347605`. Subagent count: stream `<session>/subagents/*.jsonl`, map
tool_use id → name, JSON.stringify each non-stdio `toolUseResult` → 4 WebFetch > 65536.
