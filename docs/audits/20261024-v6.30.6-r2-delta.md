## Report

Review of release candidate f818bed7, covering f9b01ee1 and f818bed7, plus a mechanical check of 2791ceb3 and ffa2561e.

**Verdict:** I found no P0 or P1. The repaired check in `migrateUnhiddenStore` refuses every store-family file name the product writes. It lets the move through for every backup name `install` and `setup.sh` write, and it meets acceptance criteria 1–7 and 9. The delta does introduce one P2: backups pile up when the store cannot be moved. One older P2 is only partly disclosed. The rest are P3s, mostly about wording and test gaps.

### Findings

**P2-1 (delta): with the plugin, one full backup per session start, with no limit, when the move fails across filesystems.**
- `scripts/setup.sh:154-155` copies `~/.claude-mem/claude-mem.db` to `$DB_DIR/claude-mem-lite.db.legacy-backup-$(date +%s)` on every session start while `claude-mem-lite.db` is missing from the data dir.
- f9b01ee1 stops counting that backup as a store file. So with `CLAUDE_MEM_DIR` on another filesystem, a pre-v0.5 database in `~/claude-mem-lite` and `~/.claude-mem-lite` already present, every open now attempts the move. Each attempt throws EXDEV, so `claude-mem-lite.db` is never created and the backup step runs again at the next start.
- I ran setup.sh followed by an open three times, sleeping 1.1 s between rounds, with a 200,000-byte original claude-mem store:
  - **f818bed7:** `open EXDEV` ×3, and the data dir held 3 × 200,000-byte copies (`…legacy-backup-1792822745/46/47`).
  - **98285e20:** one copy, then the open succeeded on an empty store.
  - **3dda02a8 (6.30.5):** the data dir was deleted at every open.
- No data is lost, but the disk grows by the size of the claude-mem store at each session start.

**P2-2 (older, D#568, partly disclosed): plugin plus `CLAUDE_MEM_DIR` leaves the store in the code dir and the user on an empty store, with no notice.**
- `setup.sh:129` moves the whole `~/claude-mem-lite` into `~/.claude-mem-lite`, which is the code dir and not the relocated data dir.
- The open then finds no old dir and creates an empty store in `CLAUDE_MEM_DIR`. My sandbox run printed `opened …/reloc/claude-mem-lite.db { c: 0 }` while the old store sat at `~/.claude-mem-lite/claude-mem-lite.db`.
- The CHANGELOG and README disclose the move, but not that under relocation nothing ever reads the moved store. setup.sh is unchanged since 3dda02a8.

**P3-1 (delta wording): "until the database is moved (there) by hand"** (README:215, CHANGELOG:22-23).
- If a user moves only `claude-mem-lite.db`, the open succeeds without the rows that are only in its `-wal`. My probe read 0 of 50 rows in the opened store, and a 1,660,392-byte `-wal` stayed in `~/claude-mem-lite`.
- README:221 then says "A database still in `~/claude-mem-lite/` has not moved … the command below deletes it". A `-wal` on its own does not look like a database, so the user can delete those rows.
- Suggested wording: name `-wal` and `-shm`, and say to move them before any session opens the store.

**P3-2 (98285e20): the move is two separate renames, not one.**
- Concurrent first opens throw ENOENT on `schema.mjs:1679`.
  - 4 processes, 20 iterations, same-millisecond start: 59 of 80 opens failed at f818bed7, 21 of 80 at 3dda02a8.
  - With 0–20 ms jitter: 2 of 80 on both trees.
  - 8 processes, 30 iterations, same-millisecond start: 168 of 240 opens failed at f818bed7.
  - 0 rows lost in 70 iterations at f818bed7.
- If the MCP server loses that race it exits for the whole session (`server.mjs:255-265`, `process.exit(1)`), and the hooks fail silently.
- A crash between the database rename and the `-wal` rename gives the same result as P3-1. I simulated that state; I did not reproduce an actual crash.

**P3-3 (98285e20, test gap): several parts of the store-file check are untested.**
- These mutations pass 8/8:
  - M2: drop the `claude-mem.db` prefix.
  - M6: also exclude kept copies (`.corrupt*`).
  - M7: count only `.bak` files.
  - M8: also exclude `-wal`, `-shm` and `-journal`.
- Under M2, a probe overwrote a current `claude-mem.db` store in the data dir with the old one (`CUR:0, LEG:1`).
- Cases 1 and 7 (clone beside a set-aside data dir) return at the `if (!name)` guard, so they never reach the check. Only the snapshot (`.bak`) part and the backup exclusion are guarded.

**P3-4 (98285e20): "only a database moves" checks the file name, not the content.**
- A non-SQLite file `~/claude-mem-lite/claude-mem-lite.db` is moved into the data dir, and every open then fails with `SQLITE_NOTADB`.
- The contract says "only when the old dir really holds a database". 6.30.5 moved the whole directory, so the effect there was worse.

**P3-5 (delta and 98285e20): "every backup snapshot" claims and an unrealistic fixture.**
- CHANGELOG:14 says "After the set-aside command, that removed the kept file and every backup snapshot". The same idea is in `schema.mjs:1667` and the test header at line 4.
- The set-aside command is printed only when no snapshot holds data (`lib/db-unusable.mjs:177-196`, probe-verified), and it deletes the `-wal` itself. So only empty `.bak` files can be there.
- The `writeSetAside` fixture (test:132, "the kept file and its log, and a snapshot") is the shape of the withdrawn 3b50d96d command (`.corrupt-<ts>`, `-wal`, non-empty `.bak`), not what the shipped command leaves. It does not hide anything here, because both shapes start with the same prefix.

**P3-6 (older, repeated by the delta): "before v0.5".** No 0.x version ever existed. `package.json` was 1.0.0 at the first commit and 2.0.0 when the hidden dir arrived (b71d292b, 2026-02-13).

**P3-7 (98285e20): README step 5 and the "From claude-mem" bullets describe `install` only.** Under "All installation methods", the plugin's setup.sh copies only `claude-mem.db` (no `-wal`/`-shm`), keeps the source, and stamps the name in seconds. Under `CLAUDE_MEM_DIR` the backup goes into the relocated dir, not `~/.claude-mem-lite/`.

**P3-8 (older, D#569): the cross-filesystem failure gives no usable notice.** Session start is silent (exit 0; the error is only in `runtime/hook-errors/*.jsonl`). doctor prints `Database: not found (will be created)` (`install.mjs:3195`) even though every open fails.

**P3-9 (98285e20, by contract):** when the check refuses the move, the pre-v0.5 store stays in `~/claude-mem-lite` and an empty store is created. Nothing reads `~/claude-mem-lite` apart from `schema.mjs` and `setup.sh`, so no notice is given.

**P3-10 (older):** an orphan `-wal` in the data dir, with no main database, is deleted at the first open. A real 53,592-byte WAL disappeared both with and without a legacy dir present.

**P3-11:** v6.30.5..f818bed7 also contains a dev-dependency bump (#48: coverage-v8, eslint, knip) that the CHANGELOG does not mention. It is dev-only.

### Q1: which names the check refuses
- **Refuses the move:**
  - a `claude-mem.db` in the data dir; that store stays and is renamed
  - `-wal`, `-shm`, `-journal`
  - canonical, empty and hand-made `.bak` snapshots (`lib/db-backup.mjs:149`)
  - `.corrupt` (`db-unusable.mjs:193`) and `.corrupt-<ts>`
  - `…legacy-backup-<ms>-wal`, which exists only if a user opened the backup by hand
- **Moves:**
  - install's backups of the database, `-wal` and `-shm` (`install.mjs:192,196`)
  - setup.sh's `…legacy-backup-<s>`
  - files outside the family: `backups/*.json` (verify-apply), `runtime/`, `metrics/`, `errors/`, `settings.json`
- `git log -S legacy-backup` finds only these two name forms. Versions before 2.51.0 copied directly to `claude-mem-lite.db`, which means the migration never runs for them.
- The check does not miss any backup name and does not let in any family file the product writes.
