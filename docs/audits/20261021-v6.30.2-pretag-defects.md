## Findings

### F1 — P1 — Concurrent recoveries still write the damaged WAL frame into the main file (data loss)
schema.mjs:1983 (`chmodSync(wal, 0)`), schema.mjs:1761-1763 (closeWithoutCheckpoint guard),
schema.mjs:1999-2006 and 2061/2067 (lock check, mode restore, `lock.close()`).

What is wrong: moveWalAside makes the WAL unreadable (mode 0) to every process, not only to itself.
When the WAL is damaged, every opener goes through the recovery at about the same time: the server,
SessionStart, parallel PreToolUse hooks and so on. The mode-0 window of one recoverer breaks the
no-checkpoint guarantees of the others in two ways:
- (a) Another process's failed open runs closeWithoutCheckpoint. Its read-only guard cannot open
  the mode-0 WAL (SQLITE_CANTOPEN), so it holds no lock. The failed connection's `db.close()` is then the
  last close, and it checkpoints the damaged frame into the main file.
- (b) A recoverer probes the WAL as unopenable (schema.mjs:1992). Another recoverer's `finally` then
  restores the mode (schema.mjs:2061). The EXCLUSIVE-mode lock connection now opens and reads the
  damaged WAL, gets SQLITE_CORRUPT and returns null, and `lock.close()` checkpoints the frame.

The result is the D#506 outcome this release claims to fix: the main file is damaged, the store does
not open, and no copy of the WAL is kept.

Evidence (all run):
- Natural race, N recoverers started together on a fresh damaged-WAL fixture, no other holder.
  The main file is checked on its own (copied without its WAL, then quick_check). Machine load 0.4–1.6.
  - N=2: 0/25 corrupted.
  - N=3: 3/20 corrupted.
  - N=4: 1/20 corrupted, and 2/15 in a second run.
  - N=6: 6/20 corrupted, plus 1/20 F2.
  - Old tree, N=6, back to back: 12/20 corrupted.
  - So this is better than 5443e879 but not fixed. `probes/race.mjs <tree> <N> <iter> none`.
- Attribution for (a): schema.mjs was instrumented to log the guard's error and the lock code
  (tree2, N=4, 15 iterations). Both corrupted iterations (2 and 12) show exactly one
  `guard=SQLITE_CANTOPEN`. None of the 13 clean iterations shows a guard failure. All lock codes
  were BUSY or CANTOPEN, so (a) caused these two.
- Deterministic replay of (b): `probes/interleave.mjs <tree> restore` hooks fs.openSync to restore
  mode 0644 right after the probe. Result: `"result": "ERR SQLITE_CORRUPT walRecoveryAttempted=true
  walMovedTo=null"`, main file 262144 → 266240 bytes, `mainQuickCheck: SQLITE_CORRUPT`, WAL 0 bytes,
  no `.corrupt-*` copy.
- CHANGELOG/README claims are false under concurrency: "A failed open no longer writes a damaged
  WAL frame into the database file" and "never removed while another session holds the store".

Suggestion: serialise recovery across processes (for example an O_EXCL lock file beside the store
taken before the chmod), and do not let any other opener's close run while the WAL is unreadable.

### F2 — P1 (regression) — A recovery can leave the WAL at mode 000; the store then never opens again
schema.mjs:1981 (saved `mode`) and schema.mjs:2061 (`finally { chmodSync(wal, mode) }`).

What is wrong: process B can stat the WAL while process A holds it at mode 0. B saves mode 0, and B's
`finally` "restores" 0 after A has already restored the real mode. B can end with
CLAUDE_MEM_STORE_IN_USE, which promises "every file left as it was", or with any other non-moving
path. Every later open then fails with SQLITE_CANTOPEN. That is not a corruption error, so
ensureDbWithWalRecovery never runs the recovery again. The effects:
- Hooks silently return null.
- The server exits with "Left WAL/SHM intact (not a corruption error)… retry or reinstall".
- The CLI prints "Cannot open database: unable to open database file".
- doctor prints only "✗ Database: unable to open database file" and does not name the WAL or its mode.

The data is intact but stays unreachable until someone runs `chmod 600 <db>-wal`. 5443e879 never
changed the mode.

Evidence (run):
- Race, no holder, N=6: 1/20 iterations ended with `walmode=0 … freshAfter=ERR SQLITE_CANTOPEN`
  (load 0.4), and 1/5 in an earlier run under load 22. In that earlier run, two consecutive fresh
  `ensureDbWithWalRecovery()` calls both printed `ERR SQLITE_CANTOPEN unable to open database file`,
  and `stat` showed `0 12392 …db-wal`.
- With a read-only holder and N=3: 1 of 23 iterations ended with every recoverer reporting
  STORE_IN_USE while the WAL was at mode 0. After the holder was killed, a fresh open still failed
  with SQLITE_CANTOPEN.
- Deterministic replay (`probes/interleave-zero.mjs`: A's chmod lands before B's stat, A's restore
  lands before B's lock check, a reader holds the store):
  `{"B":"ERR CLAUDE_MEM_STORE_IN_USE","walModeAfterB":"0","walModeAfterHolderGone":"0","freshOpenAfter":"ERR SQLITE_CANTOPEN"}`.
- doctor on such a store (WAL chmod 0): `✗ Database: unable to open database file` and no remedy line.

Suggestion: never restore a saved mode of 0 (restore to 0o600). Treat a WAL found at mode 0 as
"another recovery is running", which means in use.

### F3 — P2 — "The database file does not open" while the damaged WAL is still in place; doctor's remedy then sets aside an intact database
server.mjs:265, schema.mjs:1983 (any chmod/stat failure → `return null`) and 2006 (lock code neither
BUSY nor CANTOPEN → `return null`), install.mjs:483 (doctor remedy).

What is wrong: when moveWalAside gives up and returns null, the damaged WAL stays where it is. The
server then says the database file itself does not open and sends the user to doctor. For exactly
that state, doctor prints:

`rm -f <db>-wal <db>-shm && mv <db> <db>.corrupt — memories in that file are not recoverable without a backup`

But the main file is intact. 5443e879 said "Try: rm <wal> <shm>", which would have recovered the store.
It also recovered this state on its own, since rmSync needs no chmod. The trigger is rare: a WAL this
process cannot chmod (owned by another user in a writable dir), or a lock code outside BUSY/CANTOPEN.
The user-run remedy loses the whole store.

Evidence (run):
- `probes/chmod-eperm.mjs` makes chmod of the WAL throw EPERM, then server.mjs is started. Its output:
  `[claude-mem-lite] FATAL: Database cannot be opened: database disk image is malformed` /
  `[claude-mem-lite] The database file does not open. Next: run \`… doctor\`.`, exit 1.
  The main file was byte-unchanged, and copied alone it gives `quick_check: ok`.
- doctor (new tree) on the same damaged-WAL state printed the `rm -f … && mv … .corrupt` line quoted
  above. 5443e879's doctor prints the same remedy (pre-existing), but before this release the server
  did not route the user to it.

Suggestion: when `walRecoveryAttempted` is set and `walMovedTo` is null with a `-wal` still present,
name the WAL as the suspect and do not route the user to the set-aside remedy.

### F4 — P3 — Concurrent recoverers report "in use" to each other, and the server never retries
server.mjs:196 (retries only `isDbBusyError`), schema.mjs:2005 (storeInUse message).

What is wrong: two recoverers with no other session present see each other's EXCLUSIVE lock as
"another process" and throw CLAUDE_MEM_STORE_IN_USE. The message says to "close the other Claude Code
sessions", but there are none. An opener that lands in another process's mode-0 window gets
SQLITE_CANTOPEN. The server treats neither as transient and exits for the whole session, even
though the store opens milliseconds later.

Evidence (run):
- Race, no holder, N=6: typical result `{"CLAUDE_MEM_STORE_IN_USE":5,"opened":1}`. One iteration
  gave `{"SQLITE_CANTOPEN":3,"CLAUDE_MEM_STORE_IN_USE":3}`.
- `probes/server-holder.mjs`: a reader held the store for 1.5 s, and server.mjs exited 1 after 427 ms
  with the in-use message. 5443e879 also failed in that probe (`disk I/O error`), so this is not
  worse in that case.

Suggestion: retry STORE_IN_USE and CANTOPEN inside SERVER_OPEN_BUSY_RETRY_MS, the same way busy is
retried.

### F5 — P3 — Kept WAL copies are never pruned when CLAUDE_MEM_DIR ends in "/"
schema.mjs:2086 `DB_PATH.slice(DB_DIR.length + 1)`. DB_DIR keeps the raw env value, while DB_PATH is
`join`-normalised, so the prefix loses its first character and matches nothing.

Evidence (run): 4 old `.corrupt-*` copies plus one recovery:
- `CLAUDE_MEM_DIR=<dir>/` leaves 5 copies (DB_DIR printed with the trailing `/`).
- The same dir without the slash leaves 3.

Suggestion: use `basename(DB_PATH)`.

### F8 — P3 — On the hook face, STORE_IN_USE is silent and its error is not deduped
hook-shared.mjs:717 versus 704.

CLAUDE_MEM_STORE_IN_USE does not match UNUSABLE_RE, so openDb takes the generic branch. That branch
records a full hook error on every fire, without the once-per-project-per-hour dedup, and sends no
SessionStart notice. Meanwhile every fire repeats two failed opens and a chmod-0 window, which is
what feeds F1 and F2. The README's "the message says to close the other sessions" never reaches the
user through hooks. (Code read only.)

## Reasoned, not reproduced
- schema.mjs:1981/2019: `size` is read before the lock check. Suppose a holder appends frames and
  dies before the exclusive check: the `size === 0` branch then rmSyncs a WAL that holds frames. As
  root, with no check at all, the window is the whole function.
- Windows: the saved-mode race of F2 should apply with the read-only attribute (stat → 0o444 saved
  and restored). Not executable here.
