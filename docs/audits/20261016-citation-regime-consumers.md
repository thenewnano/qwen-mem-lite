## 1. 引用信号本身：变了什么（已有结论，本次只核对）

[2026-10-07 readout](20261007-d104-d111-readout.md) 已经把下跌分解清楚了，本次逐项对过原文：

- **模型切换**：同一份 verdict 引导语下，opus-5 的 pretool 引用率是 89/191（46.6%），opus-5-5 是 16/91（17.6%），比值 2.65 倍，区间 [1.47, 5.15]。
- **v6.17 的软提示**：在 opus-5-5 上，verdict 对 ack 是 7.03 倍，p = 0.00005。
- **盲评**：verdict 时期被引用的 11 对里，两位评审都判"适用"的是 **0/11**；软提示下，适用的教训被引用的召回只有 1/9 到 2/13。readout 自己的结论是："在两种提示下，引用都不是可靠的'采纳'信号。"

本次在同一次遍历里按 2026-09-22 切开（185 个会话，`citation-live-replay --dump`，09:06Z）：pretool 47.3% → 5.1%，fyi 25.0% → 6.0%，error_recall 21.0% → 3.2%，ups 11.1% → 6.5%。

在 live 行的累计计数上（每次判定被引用的比例，口径 `cited_count / decay_seen_count`）：
- 9-22 之后写入的行：35/1058 = **3.3%**；
- 9-22 之前写入的行：165/1112 = 14.8%。这里混入了这些老行在 9-22 之后的判定，所以它们在旧时期内的真实比例更高。

## 2. 消费者一：PreToolUse 选条（影响最大）

### 2.1 机制

`scripts/pre-tool-recall.js:773-777` 对每个文件的 observation 排序：有没有教训正文 → **`citeFactor` 降序** → 写入时间降序；取 1 条（Read）或 2 条（Edit），另加去重的余量。

`citeFactor` 的公式在 `scoring-sql.mjs:264`：`clamp(0.4, 3.0, 1 + 0.2·cited_count − 0.25·uncited_streak)`。在这里它是**排序键**，不是乘到分数上的系数，所以大小无所谓，只要不相等就决定先后。

### 2.2 测量

- **探针**：`pretool-cite-displacement.mjs` / `pretool-cite-why.mjs`，09:31Z。
- **候选池**：线上的 WHERE 条件（importance ≥2、live、60 天回看、有教训正文），按存储的文件名分组。这个池是 Edit 实际候选池的子集。

| | 文件数 | 候选多于 K 条的 | 结果与"按写入时间"不同的 | 被挤掉的里面 9-22 之后写入的 | 胜出的里面 9-22 之前写入的 |
|---|---|---|---|---|---|
| Read（K=1） | 431 | 132 | **73** | 50 | 47 |
| Edit（K=2） | 431 | 57 | **47** | 43 | 29 |

按原因拆分（"赢家 × 输家"组合）：
- **Read**：只因引用加分赢 22，只因连续未被引用扣分输 29，两者都有 22；
- **Edit**：分别是 14、27、31。

例：`mem-cli.mjs` 上，9 月初的 #65、#44（`citeFactor` 1.30）压过了 10-08 写的 #495、#494（1.00）。

### 2.3 更正 2026-10-07 readout 的一个推论

readout 写的是："本机库里……因子 ≥ 2.0 的只有 4 条……verdict 时期留下的高引用数在排序里的分量很小。"

- **分布这一半是对的**：高引用数确实少。
- **推论是错的**：在 pretool 选条里，`citeFactor` 是排序键，`cited_count = 1`（1.20）就足以压过 1.00；`uncited_streak = 1`（0.75）就足以排到一条从没展示过的行后面。判断影响要看**决策**（上表的 73 和 47），不能看分布。这是本仓测量规则 4："计数是烟雾报警器，名单才是证据。"

### 2.4 哪一部分会自己消失，哪一部分不会

- **会消失的：跨时期的偏差**。pretool 有 60 天回看，9-22 之前写入的行（最早的是 2026-09-05）会在 2026-11-04 到 11-21 之间陆续退出这个池。
- **不会消失的：扣分**。11-21 之后，池里全是新时期写入的行，引用几乎没有，`citeFactor` 基本只剩 `uncited_streak` 的相位：1.00 → 0.75 → 0.50 → 归零重来。这是**按曝光次数轮换**。readout 的盲评说明，适用的教训在软提示下也大多不被引用，所以这个轮换和"有没有用"无关。

### 2.5 建议：先做盲评对照，再决定

**做法**：沿用 readout 已经写进文档的抽取代码和固定种子（`20261007-d104-d111-readout.md` 第 155–300 行），换一个问题来问：
- 在 opus-5-5 会话里，取真实的 `PreToolUse:Edit|Write` 事件；
- 只取线上选中的和按写入时间选的**不同**的决策；
- 两位评审只看编辑内容，盲判"哪一条更适用于这次编辑"。

**预先登记**（双侧符号检验，α = 0.05）：

| 分歧决策数 | 判定线（多数一方至少） | 对 70:30 偏好的功效 |
|---|---|---|
| 40 | 27 | 0.70 |
| 50 | 33 | 0.78 |
| 60 | 39 | 0.84 |

- 取 **50 个**分歧决策。
- 按写入时间那一方显著胜出 → 改成"教训正文 → 写入时间"，`citeFactor` 只作最后的平局裁决（L3，先写 spec）。
- 线上那一方显著胜出 → 保留。
- 都不显著 → 不改，11-21 之后在新时期内部重做一次。

**样本够不够**：本机库里 Read 有 73 个、Edit 有 47 个文件存在分歧，再加上同一个文件会被多次编辑，凑够 50 个真实的分歧事件是可行的。凑不到 50，就照实报告功效，不下结论。

## 3. 消费者二：两条"引用 → importance"的写入路径

### 3.1 机制

- **`demote_pinned`**（`lib/maintain-core.mjs:555`，默认会自动跑）：`injection_count ≥ 8 AND cited_count = 0 AND importance > 下限` → 把 importance 降到 2，没有教训正文的降到 1。
- **`boost`**（`lib/maintain-core.mjs:523`）：`access_count > 3 AND importance < 3 AND importance_set_at IS NULL` → importance 加 1。`access_count` 的来源包括被引用时的计数（`bumpCitationAccess`，`lib/citation-tracker.mjs:560`），这一点 D#206 已经指出过。
- **`importance_set_at` 只在事后修改 importance 时才会打上**（`lib/observation-write.mjs:260`）。保存时指定的 `--importance 3` 不算人手设置。live 库里 76 条显式保存的 importance=3 记录，这一列都是空的。

`importance` 是各注入池的准入门槛：提示词相关的面要求 ≥1 或 ≥2，Key Context 分档要求 ≥3。所以这两条路径改的是**谁能进池**，正是 D#179/D#198 当初移除"衰减改 importance"的同一个理由。

### 3.2 测量

- **曝光相同的条件下比较两个时期**（按 `decay_seen_count` 分档）：

| 被判定次数 | 引用乘数均值（后 / 前） | `access_count > 3` 的行（后 / 前） | importance=3 的行（后 / 前） |
|---|---|---|---|
| 6–10 | 0.80 / 1.08 | 0/42 / 6/28 | 7/42 / 18/28 |
| 11+ | 0.84 / 1.23 | 2/20 / 21/42 | 3/20 / 23/42 |

  9-22 之前写入的行里，importance=3 的高曝光行大多正好也是 `access_count > 3`（11+ 档：23 行里有 21 行）。这个形状和"`boost` 用引用攒下的访问次数把它们提到了 3"一致；但本次没有逐行核对历史，所以不排除有其他来源。

- **`demote_pinned` 的判断条件已经失去区分力**：按每次判定的平均引用率算，一条普通记录 8 次注入都没被引用的概率：
  - 旧时期约 20% → 0.8^8 = 17%；
  - 新时期 3.3% → 0.967^8 = **76%**。

  更糟的是，被注入越多的行（也就是被检索判为越相关的行）越容易满足这个条件。

- **眼下的影响**：完整条件下，当前会被降级的是 **0 行**。新时期的行平均只被注入过 1.0 次，还没攒到 8 次。

### 3.3 建议

方向是把 D#179/D#198 的结论推广到这两条路径：
- `demote_pinned` 去掉 `cited_count = 0` 这个条件（或者直接退役）；
- `boost` 只计显式读取（`get` / `timeline` / `recall`），不计引用带来的访问次数。

改的是已发布插件的默认维护行为，属于 L3。眼下影响为 0 行，**不急**；建议立成待办，带一个触发条件：`demote_pinned` 预估会降级的行里，9-22 之后写入的达到 5 行，就开始做。

本机想立刻关掉 `demote_pinned`，有现成的开关 `CLAUDE_MEM_SKIP_DEMOTE_PINNED=1`。它要写进用户级的 `settings.json`，需要你授权；按现在 0 行的影响，我不建议现在动。

## 4. 消费者三：D#105（B3 的 60 天截断读数）

### 4.1 问题

`benchmark/cutoff-reach-probe.mjs` 把"仍在使用"定义为**这条边被引用过**（`last_cited_session_id` 不为空，而且这一列从不清空）。

- 按 D#105 的安排，读数在 2026-11-04 之后那一周。那时截断删掉的是最早写入的一批行（2026-09-05 起，截至 09-11 的有 40 条 importance≥2 的 live 行），**全部属于旧时期**。
- 当前 live 库里，旧时期写入、被注入过的边，有 71%（100/140）被引用过；新时期写入的只有 7.5%（20/267）。

所以 11-04 之后的那次读数，量的是**旧时期的引用习惯**，回答不了"按最后一次使用来计时"这个新规则，在今后的新时期行上能改变什么。

### 4.2 建议的读数口径（11-04 之前写进 D#105）

1. 按写入时间是否早于 2026-09-22 把边拆成两组，分别报告。
2. 决定 B3 的总体是**新时期写入的边**，它们最早在 2026-11-21 才到 60 天。所以真正有用的读数在 11-21 之后那一周。
3. **预先登记**：按最后一次使用计时，只会改变"被引用过"的那部分边的命运。如果新时期里到达截断线的边被引用过的不到 10%，那 B3 对超过九成的边不起作用，就不做。按今天的数（7.5%），预计结论是不做。
4. 由于 §1 的盲评结论，"被引用过"只能叫"被提到过"，不能写成"仍在使用"。

## 6. 局限

- **时期边界用的是写入时间（09-22）**：它和"在哪个模型、哪种引导语下被判定"不是一回事。比如一条 9-20 写入的行，它在 10 月的判定都属于新时期。所以两组比较的是"写入时期"，这正是排序里实际起作用的东西（累计计数）。
- **§2 的分组近似**：按存储的文件名分组，近似线上按路径边界匹配；同一个文件名在不同项目里分开计。这个池比 Edit 的实际候选池小（只算有教训正文的），所以分歧数是下限。
- **§3 的 importance 来源**：importance=3 的来源没有逐行追溯历史，"由 boost 提上来"是和数据一致的解释，没有证实。
- **单人 / 单机**：这台机器、这一位用户的语料；其他用户的模型和引导语组合可能不同。

## 8. 盲评结果（§2.5 的实验，2026-10-16 执行）

### 8.1 做了什么

- **预先登记**：判定规则在 2026-10-16T09:57:43Z 写定，早于任何标签。原文和数据冻结在 `benchmark/results/pretool-order-judge-20261016/`（该目录被 gitignore，不入库）。
- **材料**：
  - 来源：本机 transcript 里 5,174 次 Edit/Write/MultiEdit 调用。每个（会话, 文件）只取第一次，排除本会话。
  - 候选池：线上的 `fileMatchClause`，只取**编辑发生时已经存在**的教训（`created_at < 编辑时间`，60 天回看），排序用今天的计数。
  - 筛选：85 个事件的候选多于 2 条，其中 **63 个**线上取的前 2 条和按写入时间取的不同，涉及 26 个文件、55 种教训组合；同一组合最多取 2 次。
  - 每个事件对比两条教训：一条只出现在线上排法的前 2 里，另一条只出现在按写入时间排法的前 2 里。
  - 前一方有 40 条写于 9-22 之前，后一方只有 7 条。
- **盲化**：题目顺序、X/Y 对应哪一方，都用种子 20261016 打乱；去掉 id、日期和引用数据。
- **评审**：两个互相独立的子代理，只读材料文件，用 2026-10-07 readout 的 A/B/C 标准（A = 教训的规则或事实约束了这次编辑改动的内容）给每条教训打标签。两份输出我都核对过：63 行、id 按顺序、取值只有 A/B/C。

### 8.2 结果（10:03Z）

| 项 | 读数 |
|---|---|
| 规则 1：A 与非 A 的 kappa（126 个标签） | **0.753**：两位都判 A 15 个，只有评审一判 A 1 个，只有评审二判 A 7 个，都不判 A 103 个 → 研究有效 |
| 规则 2，主判定（两位都判 A） | 只有一边适用的 13 个事件：**按写入时间 10、线上排法 3**；双侧精确符号检验 p = **0.092** |
| 规则 3，敏感性（任一位判 A） | 17 对 4，p = 0.0072（只报告，不作裁决） |
| 每一方的适用率（两位都判 A） | 线上排法 4/63（6.3%），按写入时间 11/63（17.5%）；任一位判 A 时为 5/63 对 18/63 |
| 两条都不适用 | 49/63（主判定口径） |

**裁决（按规则 2）**：分歧事件 13 个 ≥10，但 p = 0.092 不小于 0.05 → **不改**。11-21 之后重跑（D#356）。

### 8.3 怎么读

- **方向一致**：主判定和敏感性分析都偏向"按写入时间"。事先写明的偏差（今天的计数里含有编辑之后才发生的引用）本来是帮线上排法的，结果却朝相反方向。
- **功效不足**：按观测到的 77:23，13 个分歧事件的功效只有 **0.40**。所以 p = 0.092 是"没测出来"，不是"没有差别"。要达到 0.80，需要约 25 个分歧事件，按这次的比例（13/63）约 120 个事件。
- **重跑的数据来源**：Claude Code 会删掉 30 天前的 transcript，一个 30 天窗口大约只产生 63 个这样的事件。所以重跑时把这次冻结的 63 个和新的事件合并，协议不变。合并时要分层：2026-11-21 之后，所有候选都属于新时期，比较的只剩"连续未被引用的扣分"这一项。
