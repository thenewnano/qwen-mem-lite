## DEFECTS

### P2-1: across filesystems the store and its log still arrive in two renames; an opener that opens the store between them has the old log replayed over its writes, or strands the log's rows

- **Where:**
  - schema.mjs:1749: the placing loop (rename the store, existsSync of the log, rename the log).
  - schema.mjs:1750-1756: the sources of the files placed so far are unlinked.
- **Chain:**
  1. Opener A copies both files across and renames the store into place.
  2. Before A checks for and renames the log, opener B passes `!existsSync(DB_PATH)` and opens the store without its log. B can be the other session-start opener, whose own copy found the store present and stopped, or any other opener.
  3. Outcome (a), B writes, checkpoints and closes: its -wal is deleted. A finds no log at the destination and renames the old one in. The old frames replay over pages B rewrote.
  4. Outcome (b), B still holds the store open: A finds B's -wal and stops with placed=1. A then unlinks the old store and leaves the old -wal alone in ~/claude-mem-lite.
- **Evidence, forced** (A paused 1.5 to 3 s right after its store rename; B started 0.5 to 1 s after A):
  - **(a), release tree, 4/4 runs:**
    - integrity_check: "*** in database main *** 2nd reference to page 64";
    - 50 observations, of which B's rows: 0 of 20;
    - `stats` exits 0;
    - doctor: "✓ FTS5 integrity: all indexes healthy" and "✓ DB stats: 0.3MB, 50 observations, 0 sessions".
    - 06dfd69b gives the same. So does one filesystem, which is the disclosed D#578.
  - **(b), 3/3 runs:**
    - the data dir has 0 observations, integrity ok;
    - ~/claude-mem-lite holds only claude-mem-lite.db-wal (1845792 B, all 50 rows), and its store file was unlinked;
    - nothing reports it.
- **Natural timing:**
  - 30 trials: 2 or 3 openers each writing 20 rows, on 50-row and 3000-row stores.
  - In 23 trials, two or more openers copied at the same time (logged copyFileSync calls).
  - 30/30 were correct: right count, integrity ok, old dir empty, no private copies, no errors.
  - So the window is the gap between two consecutive renames, as on one filesystem.
- **How this relates to r1 P2-1:** it is the same harm through the other interleaving (the placer is paused, not the copier). r1's own interleaving is fixed: with B's second fsync delayed 25, 200, 400 and 1500 ms, 4 runs each, 06dfd69b gave 5/16 not ok and the release 0/16.
- **v6.30.6:** across filesystems, opens 1 and 2 both fail with "Cannot open database: EXDEV: cross-device link not permitted, rename …". Nothing moves: the bytes stay intact and memory is off.
- **Repro** (R=~/.cache/tmp/rv-6307-r2):
  ```
  PAUSE_MS=3000 DELAY_S=1 $R/scripts/race.sh $R/wt f1 xfs A-pause-B-write
  PAUSE_MS=3000 DELAY_S=1 HOLD_MS=4000 $R/scripts/race.sh $R/wt f2 xfs A-pause-B-hold
  ```

### P2-2: check-then-rename lets a slower opener replace a store another opener placed; forced, the migrated rows and the other opener's writes are all lost

- **Where:** schema.mjs:1716-1720 placeUnlessPresent (existsSync, then renameSync, which replaces its target), called at 1749.
- **Chain:**
  1. Both openers copy across. Only this path has two independent copies of the store.
  2. B's existsSync(store) says no file is there.
  3. Before B's rename, A places the store and the log, unlinks the sources and opens the store.
  4. B's rename puts its copy of the old main file, which lacks the log's rows, over A's store. B then finds A's log and stops.
  5. A's connection still holds the unlinked inode. Its writes, and the checkpoint on close, go there, and the -wal is reset.
- **Evidence.** B was paused 2 s between existsSync and renameSync. A, standing in for the MCP server: ensureDb, wait 3.5 s, 20 inserts, wal_checkpoint(TRUNCATE), close.
  - Next open: "Total: 0 observations". integrity_check is ok.
  - ~/claude-mem-lite is empty, and the data dir holds only claude-mem-lite.db.
  - The 50 legacy rows and the 20 new ones are gone, and nothing reports it.
  - Variant where A writes and closes before B's rename: 50 observations, A's 20 rows gone, integrity ok.
- **Natural window:** two adjacent syscalls on one path. It was not hit in the 30 natural trials.
- **History:**
  - r1 claims P3-2 reasoned this for a -wal; the store is the costlier case.
  - b768c61c's body says it of cf947d50's title, but CHANGELOG:16-17 says the opposite (claim C2).
- **Possible fix:** `linkSync(private copy, dest)` fails with EEXIST atomically, so it would close this window. It is the shape CLAUDE.md already prescribes for `wx`. It does not close P2-1.
- **v6.30.6:**
  - Across filesystems, no open succeeds.
  - On one filesystem, the rename moves the only copy. A second opener's rename then gets ENOENT (6.30.6 fails that open) and cannot replace a store that is already placed.
- **Repro:**
  ```
  PRELOAD=$R/scripts/pause-before-place.mjs
  XENV="PAUSE_MS=2000 PAUSE_SRC=.unhidden-move-" MEMDIR=<tmpfs dir> $R/sbx <case> \
    node --import file://$PRELOAD $R/wt/cli.mjs stats &
  sleep 0.5
  XENV="WT=$R/wt WAIT_MS=3500" MEMDIR=<same> $R/sbx <case> node $R/scripts/hold-write.mjs
  ```
  The case needs the fixture first: `mkcase` in scripts/lib.sh.

### P2-3: on one filesystem, a read-only ~/claude-mem-lite makes every open fail (outside the delta's diff; contract item 1 fails for this input)

- **Where:** schema.mjs:1705 calls placeUnlessPresent, whose renameSync throws EACCES. That error is rethrown at 1707 (it is not EXDEV) and again at 1711 (it is not ENOENT).
- **Evidence** (chmod 555 on the old dir, data dir on the same ext4):
  - Opens 1 and 2 both fail: "[mem] Error: Cannot open database: EACCES: permission denied, rename '<HOME>/claude-mem-lite/claude-mem-lite.db' -> '<data>/claude-mem-lite.db'".
  - The data dir stays empty, and the old files are unchanged.
- **Asymmetry:** across filesystems the same directory is copied (50 rows). dbe441ee's fix covers only that branch, and README.md:216's "(they stay there when that directory is read-only)" is scoped to it.
- **Recoverable:** the message names the rename, and `chmod u+w` on the old dir fixes it.
- **v6.30.6:** identical, with the same message on both opens.

### P3
- **P3-1. One filesystem, 0444 store files: the store opens read-only.**
  - The -wal arrives in the data dir still mode 0444. ensureDb chmods only DB_PATH (schema.mjs:1809).
  - Every write fails: `cli.mjs save` prints "[mem] save failed: attempt to write a readonly database" and exits 1.
  - doctor prints "⚠ FTS5 integrity issues detected: observations_fts: CORRUPT (attempt to write a readonly database)" for each of the 4 tables. That reports as damage what is only a mode bit.
  - Reads work (50 rows). v6.30.6 behaves the same. The delta's chmod covers only the cross-filesystem copy.
- **P3-2. The new chmodSync(tmp, 0o600) at schema.mjs:1740 has no try/catch.**
  - On a data-dir filesystem that refuses chmod with EPERM, every cross-filesystem open would fail. By contrast, ensureDb's own chmod at :1809 is in a try/catch.
  - Reasoned only: no such filesystem is available here.
  - Against 06dfd69b this is a regression. Against 6.30.6 it is not, since there every cross-filesystem open failed anyway.
- **P3-3. A read-only old dir brings the store back.**
  - After the cross-filesystem copy, removing `<data>/claude-mem-lite.db*` (a user starting fresh) makes the next open report "Total: 50 observations" again.
  - With a writable old dir, the same steps give a fresh, empty store.
  - This is not documented.
- **P3-4. r1 P3-1 (deferred), re-observed on the release tree.** Cross-filesystem kills at 8 points:

  | Killed after | Result |

  | either copyFileSync, or either chmod | The next open completes the move (50 rows). The private copies stay forever: 258048 B, plus 1845792 B when both files were copied. |
  | placing the store | Every later open reports 0 observations, and nothing says so. Both old files stay, plus a 1845792 B private copy of the log. That is recoverable by hand; 06dfd69b had unlinked the old store at this point. |
