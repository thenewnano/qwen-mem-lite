## Findings

### F1 — P2 — install.mjs:188-192 docblock and commit 0eae0593
Claims:
- docblock: "so a copy killed partway leaves no backup of the store, and the next install makes it whole"
- 0eae0593: "a kill during the copy leaves only private files, which the next install removes"

Verdict: FALSE in a reachable case. migrateLegacyClaudeMemData returns `skip` at install.mjs:198
(`if (existsSync(targetDb))`) before the sweep (:209) and before the copy. So once anything has created
claude-mem-lite.db after the killed run, the next install neither removes the private file nor makes a
backup. install configures the hooks (configureHooks) before backupLegacyClaudeMemData, and a
SessionStart in an empty data dir creates the store (measured below). That makes this order reachable:
Ctrl-C during the copy, start Claude Code, run install again.

Evidence: scratch/nextinstall.sh arm 2. The data dir holds `.legacy-backup-copy-999999-…` and
`claude-mem-lite.db`. The next install prints `skip` and leaves `.legacy-backup-copy-999999-1700000000000`
in place. Only setup.sh sweeps that prefix, and it runs for plugin installs only (`git grep
legacy-backup-copy`: install.mjs:209, scripts/setup.sh:166).

Separately, `hook.mjs session-start` on an empty data dir created `claude-mem-lite.db`
(scratch/F/data after the run).

Impact: none on data. The source stays in ~/.claude-mem. A direct install keeps a full-size private copy
for good.

Correction: in the docblock, delete ", and the next install makes it whole". The commit message cannot be
changed.

### F2 — P3 — scripts/setup.sh:151-155 comment, and the setup.sh half of commit f338daf4
Claims:
- setup.sh comment: "a session start killed partway leaves no backup and the next one copies again"
- f338daf4: "the next session start removes the private files and copies again, 40 of 40 rows"

Verdict: UNSUPPORTED outside the test's conditions. setup.sh copies only while
`! -f "$DB_DIR/claude-mem-lite.db"` (setup.sh:174). hook.mjs session-start runs in the same SessionStart
event and creates that file in an empty data dir (measured, scratch/F). The test never lets a store
appear between the two runs.

Whether the store appears in a real kill depends on whether hook.mjs could open it in that session (for
example, deps present). I did not reproduce that under Claude Code.

The sweep half of the claim is TRUE: it is unconditional (setup.sh:173 calls sweep_legacy_copies before
the guard).

Correction: delete "and the next one copies again", or say "copies again while no store exists yet".

### F3 — P3 — CHANGELOG.md:16-18 (D#539 bullet) and doctor's runtime sentence "The broken file and its log are kept as X and X-wal"
Claim: "The restore and set-aside commands keep the broken file and its `-wal`".

Verdict: MISLEADING by juxtaposition. The commands keep whatever -wal exists. But every product open on
the damaged store deletes the -wal first (D#557), and the session start that shows the user the notice
is such an open.

Measured (scratch/S1, a copy of fixture A with a 109-byte -wal):
- after `hook.mjs session-start`, the data dir holds only `claude-mem-lite.db` and `runtime`;
- running doctor's printed command then keeps `…corrupt-2026-10-25T12-01-49-897Z-wal` at 0 bytes, made
  by the command's `touch`;
- doctor still says "The broken file and its log are kept".

Contrast: run on an untouched store, doctor alone does not delete the -wal. In fixture A the kept -wal
hash was 015db9250b6edc9a, identical before and after. cli.mjs doctor also kept it (scratch/D).

The CHANGELOG discloses D#557 under "Still as in 6.30.7", so the reader can piece this together.

Correction: none needed in the CHANGELOG, or append "(the open has often deleted it already, see D#557
below)". The runtime sentence could drop "and its log" when the -wal is absent. That is code, outside
this lens.

### F4 — P3 — install.mjs:207 comment
Claim: "A copy killed partway left its private file; install runs one at a time (install.lock)."

Verdict: MISLEADING as a safety argument. The sweep removes every `.legacy-backup-copy-*` with no pid
check. setup.sh writes private files under the same prefix in the same dir, and setup.sh's own comment
promises "another session starting at the same time keeps its own".

Evidence: scratch/sweeptest.sh. A file `.legacy-backup-copy-<pid of a live sleep>-1792929999` is
present. The cross-filesystem install prints `copied`, and the file is gone afterwards.

Impact: a concurrent setup.sh copy fails its `mv` and retries next session.

Correction: say the sweep also removes a concurrent plugin session start's in-flight copy, or delete the
"install runs one at a time" clause.
