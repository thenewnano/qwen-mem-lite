Reviewer: blind pre-release claims reviewer. Taken 2026-10-22, Linux, 12 cores, Node 26.8.1, better-sqlite3 13.0.3
(SQLite 3.53.4), system sqlite3 3.46.1. Trees from `git archive`: `tree` = 78eda8b4 (release), `tree630` = main d3de9748
(v6.30.3), `tree1` = 1b23dcc2 (round-1 tree, for its commit message only), `treemut` = 78eda8b4 again (mutations only, so no
ruler read a mutated tree). node_modules symlinked to the repo's. Every child ran under `scripts/env.sh` (HOME, TMPDIR,
CLAUDE_MEM_DIR, CLAUDE_PROJECT_DIR in the sandbox; MEM_NO_AUTO_ADOPT=1, CLAUDE_MEM_SKIP_UPDATE=1, CLAUDE_MEM_SKIP_MAINTAIN=1,
CLAUDE_MEM_SKIP_SAVE_ENRICH=1; key/proxy/TOKEN/CLAUDECODE/CLAUDE_CODE_*/CLAUDE_PID/CLAUDE_MEM_METRICS unset; PATH =
sandbox bin holding node/npm/npx only, then /usr/bin:/bin, no `claude`). The archived rulers were extracted from the two
measurement docs into `tasks/d550/` and `tasks/d546/ruler/` of each tree (r2 doc overrides r1 for same-named files) with
D546_WORK inside the sandbox. Sandbox: `~/.cache/tmp/d550-r2-cl-20Og` (deleted at the end).

## Verdict

No P0. The release's central claims re-derive: the read-only check fails 285 of the 869 log plants as found and
doctor 6.31.0 prints a ✗ on all 285 and leaves main file and log unchanged on all 285 (two full runs); the 40 stores
6.30.3's rebuild healed are the same 40 ids; the README recovery run verbatim reproduces 1,641 / 101 / 1,540 / 157 and
3,285 rows exactly in one run (3,286 in the other); D#551 holds (0 empty `.bak` from 6.31.0 on 1,641 damaged stores,
against 639 from 6.30.3); timing is within 3% (1,210 → 1,853 ms vs 1,198 → 1,891); the mutation record reproduces (5/5,
8/9, same survivor). Falsified: **(P1)** on a store doctor cannot open (`✗ Database:`), doctor and the SessionStart notice
say "memories in that file are not recoverable without a backup" and offer set-aside/overwrite with no pointer to the
new README section, while that README recovery placed 3 such stores with 2,915–3,827 intact rows each (pre-existing text,
restated in the D#551 diff); **(P2)** "on all 1,540, doctor's database and search-index lines then passed" (README EN/ZH,
CHANGELOG; "passed twice" in the r2 doc) is false on 6 of 1,540, where the first doctor after placing printed ⚠ on DB
schema and on FTS5 integrity; **(P2)** the CHANGELOG's 40-store sentence omits that the README recovery stops on 4 of those
40. Several P3s, chief among them that SQLite reads of these damaged pages are not deterministic on this host, so the
6.30.3-arm counts move by 2 between runs and no doc says so.
