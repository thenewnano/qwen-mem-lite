## 备注（不是范围内的缺陷）

- **N1 分支分叉**：主仓库 `main` 的 HEAD 是 `64a8f412`，那是另一个 v6.26.0 发版提交，标题是 "background LLM calls…"，**不在** `ship/v6.26.0` 的历史里（`git branch -a --contains 64a8f412` → 只有 `main`）。`c860fd27` 的作者时间 20:26:43 早于它的父提交（21:06），说明它是重排过的。如果在 `c860fd27` 打 tag，`main` 需要先指到 `c860fd27`，否则推上去的 main 和 tag 的 CHANGELOG 不一致。
- **N2 OpenRouter 结构化输出的路由**（不确定，没有实测）：`anthropic/claude-haiku-5.5` 的 10 个 endpoint 中，有 4 个（Amazon Bedrock ×3、Claude Platform on AWS）的 supported_parameters 列了 `response_format`，没列 `structured_outputs`。OpenRouter 默认不要求 provider 支持全部参数，所以 rewrite 的 json_schema 约束在这些路由上可能被丢掉，"React" 那种散文反问就会复现。replays 没有记录是哪家 provider 应答的。说不准，是因为没有确认 OpenRouter 在只有 `response_format` 时对 json_schema strict 怎么处理。可以考虑在 strict slug 且带 jsonSchema 时加 `provider: { require_parameters: true }`。
- **N3 网关 fallback**：CHANGELOG:48-49 说网关不支持时 "falls back to `claude -p`"，这没错。但 fallback 子进程继承同一个 `ANTHROPIC_BASE_URL`（S3c `baseUrlSet: yes`）。model-config 文档说 "`ANTHROPIC_BASE_URL` changes where requests are sent, not which model answers them"，所以 `--model haiku` 多半还是把 `claude-haiku-5-5` 发到同一个网关，fallback 很可能一样失败。可以补半句。
- **N4 改名的 5.5 部署**：CHANGELOG:50-52 只说 temperature 0 会被拒。如果网关的 400 文本里同时出现 `` `temperature` `` 和 deprecat / unsupported / not support，haiku-client.mjs:652-668 的重试会去掉 temperature 再发一次。这时调用能成功，但 thinking 是开着的，也没有 schema，正是 strict body 要避免的那种情况。r1 P3-2 记过这一点；现在的建议（把部署改名为 `claude-haiku-5-5`）仍然是对的。
