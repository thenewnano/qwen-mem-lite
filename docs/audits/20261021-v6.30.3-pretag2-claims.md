### The non-TRUE ones

**Detail 1 — C5, A1, E1: the fix is not about escape depth.**
- Of the 8,166 texts whose output changed, 155 had only same-depth growth events. In 136 of those, v6.30.2 stored a 16-character window that v6.30.3 erases.
- Shrunk minimal case, all at `\n` depth 1, with different line prefixes:
  - Input: `Comment:-----BEGIN PRIVATE KEY-----\nVersion:-----BEGIN PRIVATE KEY-----\nComment:IPgJ5ApHXanQYSln"X\nMIIVXYr4GV2AXKOv`
  - v6.30.2: `Comment:***PEM_KEY***"X\nMIIVXYr4GV2AXKOv`
  - v6.30.3: `Comment:***PEM_KEY***`
- Fixes:
  - CHANGELOG: delete "When the two keys are written at different escape depths (`\n` and `\\n`, say),".
  - Code comment: delete "at another escape depth". It is P2 because a maintainer could narrow the branch to different depths and silently bring back the same-depth leak; no test covers that case.
  - Commit subject: only fixable by rewriting history.

**Detail 2 — A10, F7: the "header values and fragments" picture describes the shrink target, not what the texts keep.**
- The shrinker targets only the first kept window of each text.
- Unshrunk, the 14 texts keep 371 windows in 30 base64 runs. These include:
  - seed 4 text 2737: `MII2Mawozh/w8v003wsIyAXIKy8nPl/E` (32 chars), the third body line of a depth-4 key. Shrunk, it became "a run of 15 characters glued to a BEGIN".
  - seed 5 text 828: `b3BlbnNzaC1rZXktdjERJgvinyiCWwww0685Q54u8XJ` (43 chars, OpenSSH key magic).
  - seed 2 text 2900: a 105-character run starting `lQ8Du7II…` that contains `b3BlbnNzaC1rZXktdjE`.
- Both first passes store these lines; v6.30.2 erased them only by accident in a later pass. So v6.30.3 newly stores key-body-shaped lines in some fuzz texts.
- Fix: in the doc, delete the sentence "Shrunk with shrink.mjs (all 14 below), the kept text is: …". The commit message would need a history rewrite.

**Detail 3 — C10, B2, E2, E3, E5: who loses writes depends on close order.**
Probe on a healthy WAL store: an old session holds 200 committed rows in its WAL with autocheckpoint off; the exact command runs; then a new session writes 50 rows.

| Mode | Old session closes last | Old session closes first |
|---|---|---|
| `rm -f` only | old rows kept, new session's 50 lost | old session's 200 lost |
| restore | old session's pages written over the restored file (snapshot-only row gone), new session's 50 lost | old session's 200 lost |
| set-aside | old session's 200 lost | old session's 200 lost |

The advice to close every session is right in every case; only the stated consequence is narrower than what happens. Fix: delete the "which loses…" clause, keeping "Both commands start by deleting the database's -wal and -shm files."
