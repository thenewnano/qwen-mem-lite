## Findings that do not hold

### E9. P2 FALSE: an unreadable snapshot is reported as failing SQLite's integrity check
- Location: lib/db-unusable.mjs `dbUnusableRemedy` builds two sentences, and doctor prints both through install.mjs
  `dbCheckRemedy`:
  - `None of the ${count} passes SQLite's integrity check${skipped}.`
  - `The newest ${..} of the ${count} fail${..} SQLite's integrity check; the next one passes.`
- Cause: `snapshotPassesIntegrityCheck` returns false for any throw, including EACCES on readFileSync. The JSDoc says so:
  "Any failure (unreadable, not a database, damaged) is 'does not pass'". The user-facing sentence is the problem.
- Evidence: a good `writeSnapshotFixture` snapshot, chmod 000, beside a garbage `claude-mem-lite.db`, run through the
  be5c42b9 `install.mjs doctor`:
  ```
  ✗ Database: file is not a database
      None of the 1 backup snapshot(s) beside the database passes SQLite's integrity check. Once every Claude Code
      session is closed, set the broken file aside so a fresh store is created on the next session: rm -f …-wal …-shm
      && mv …claude-mem-lite.db …claude-mem-lite.db.corrupt
  ```
  A direct call returns `snapshotPassesIntegrityCheck(<chmod 000 good snapshot>) → false`.
- Why it matters:
  - The snapshot was never checked, and it is good. The user is told to start a fresh store when fixing the
    permission and restoring would recover everything.
  - It is not destructive: mv keeps the file and the snapshot stays where it is.
  - It folds "could not look" into "looked and it failed". That is the collapse dbCheckRemedy's own JSDoc forbids
    ("three different situations … collapsing the last two ends the reader's search with a fact nobody checked").
    That JSDoc is unchanged lines and now lists three outcomes where there are four.
- Same class, reasoned and not reproduced: a snapshot over 2 GiB, where readFileSync throws ERR_FS_FILE_TOO_LARGE.

### E7. P3 FALSE: "The in-memory copy is writable, which is what makes integrity_check evaluate CHECK constraints"
- Location: lib/db-unusable.mjs, `snapshotPassesIntegrityCheck` JSDoc.
- Evidence (CHECK `a IN ('x','y')`, row 'z' inserted with `ignore_check_constraints`):
  ```
  file, readonly:true            → ['ok']
  file, read-write               → ['CHECK constraint failed in t']
  new Database(buffer)           → ['CHECK constraint failed in t']
  new Database(buffer,{readonly:true}) (INSERT throws SQLITE_READONLY) → ['CHECK constraint failed in t']
  ```
  A read-only in-memory copy evaluates CHECK constraints too. What skips them is a file connection opened read-only,
  not a copy that cannot be written.
- Mutation: changing the code to `new Database(image, { readonly: true })` leaves the 'evaluates CHECK constraints'
  test green (3/3). So writability is not what produces the behaviour, and no test pins it.
- The parenthesis "(a read-only connection skips them)" holds for file connections.
