## P2

### P2-1 A snapshot the check could not read is reported as failing SQLite's integrity check, and doctor prints set-aside
lib/db-unusable.mjs:167, :175-176, :254 (also the comment at :157-158)

`snapshotPassesIntegrityCheck` turns every failure into `false`: the read, the open, a missing
function, and real damage alike. `dbUnusableRemedy` then prints "None of the N backup snapshot(s)
beside the database passes SQLite's integrity check" and returns set-aside. "I could not check
this file" and "this file failed the check" come out as one outcome, which is the conflation the
three-outcome rule exists to stop (the "could not look" case gets its own outcome only for the
directory read). In every case below, 6.30.4 printed a restore command naming the file.

- **Healthy snapshot over 2 GiB (regression).** `readFileSync` throws `ERR_FS_FILE_TOO_LARGE`
  above 2 GiB on this Node (`File size (2306867200) is greater than 2 GiB`). The repro was a
  2,204,897,280-byte VACUUM INTO snapshot:
  - read-only `PRAGMA integrity_check(1)` on the file → `ok` (475 ms);
  - `snapshotPassesIntegrityCheck` → `false` (0 ms);
  - `dbUnusableRemedy(...).found` → `"None of the 1 backup snapshot(s) beside the database passes SQLite's integrity check."` and kind set-aside.

  So the user is told the only good backup is damaged and is steered to start an empty store.
- **Unreadable file (EACCES).** chmod 000 on a healthy real-schema snapshot. The shipped doctor
  printed:
  `✗ Database: file is not a database` /
  `None of the 1 backup snapshot(s) beside the database passes SQLite's integrity check. Once every Claude Code session is closed, set the broken file aside ...: rm -f <db>-wal <db>-shm && mv <db> <db>.corrupt`.
- **`.bak` symlinked to a directory.** stat size 4096 > 0, so it is counted; `EISDIR` is then
  reported as "The newest one of the 2 ... fails SQLite's integrity check".
- **Index on a function the checker does not register.** "no such function" is reported as an
  integrity failure. The real store has no UDF index, so this case is only theoretical.

Repro: run from the worktree root with the sandbox env set.
```
D=$(mktemp -d -p "$TMPDIR"); node --input-type=module -e "
import Database from 'better-sqlite3'; import {writeFileSync,chmodSync} from 'node:fs';
import {dbUnusableRemedy} from './lib/db-unusable.mjs'; import {writeSnapshotFixture} from './tests/test-helpers.mjs';
const db='$D/claude-mem-lite.db'; writeFileSync(db,'garbage');
chmodSync(writeSnapshotFixture(db+'.pre-delete-2026-10-01T00-00-00-000Z-1-1.bak'),0);
console.log(dbUnusableRemedy(db,new Error('file is not a database'),{Database}).found)"
# → None of the 1 backup snapshot(s) beside the database passes SQLite's integrity check.
```
For the >2 GiB case: build a WAL store, insert 2100 rows of `zeroblob(1048576)`, run `VACUUM INTO`
`<db>.pre-maintain-...bak`, then call the same function. Observed output is quoted above.

### P2-2 A snapshot that passes the check but holds no store is named over an older snapshot that holds rows
lib/db-unusable.mjs:150-154 (the comment's claim), :252

`integrity_check` says "ok" for a structurally sound file that holds nothing. Two inputs show it:

- A hand-made backup of a live WAL store taken before a checkpoint: `cp db x.bak` plus
  `cp db-wal x.bak-wal`. The main file is 4096 bytes and every row is in the `-wal`.
- Any empty valid SQLite file (8192 bytes, zero tables) → passes.

Doctor names the newest passing file, so it picks this one over an older real snapshot. The
command `cp`s the main file alone, overwriting the damaged database, and the restored file has
no tables: `select count(*) from observations` → `no such table: observations`.

The comment at :150-154 describes exactly this hand-made WAL copy as handled ("the main file's
content is what a restore yields and what is checked"). That is true, and the content is empty.
The pattern predates this release (6.30.4 named any non-empty file). This release adds the
"passes SQLite's integrity check" endorsement to it.

Repro (shipped doctor, sandboxed). The data dir held:
- the garbage db;
- an older real-schema VACUUM INTO snapshot with 30 observations, mtime 2023;
- `claude-mem-lite.db.before-upgrade.bak` (4096 B) and its `.bak-wal` (30 rows).

`node install.mjs doctor` printed:
```
✗ Database: file is not a database
    The newest of the 2 backup snapshot(s) beside the database passes SQLite's integrity check. Once every Claude Code session is closed, restore it: rm -f .../claude-mem-lite.db-wal .../claude-mem-lite.db-shm && cp .../claude-mem-lite.db.before-upgrade.bak .../claude-mem-lite.db — move the broken file aside first ...
```
A possible direction: require the snapshot to contain the `observations` table, and/or say the
snapshot's row count or age.

## P3

- **P3-1 The tie-break on equal mtimes orders by tag, not by the ISO stamp**
  (lib/db-unusable.mjs:220-224). This predates the release. `a.path < b.path` compares the whole
  name, so the tag decides first ('pre-maintain' > 'pre-delete'). Two passing snapshots with an
  equal mtime: the command names `pre-maintain-2026-09-01` over `pre-delete-2026-09-07`. The
  comment says the name "carries an ISO stamp", which holds only within one tag. Untested (M10).
- **P3-2 `dbCheckRemedy` sends every unlisted kind to the restore sentence** (install.mjs:492-495).
  'unchecked' (reached only if `Database` were undefined) prints
  `2 backup snapshot(s) exist beside the database. Once every Claude Code session is closed, restore it:  — move the broken file aside first ...`.
  Nothing reaches it today.
- **P3-3 The check's memory is 2× the snapshot size, with no cap.** `readFileSync` takes one copy
  and better-sqlite3's deserialize (`sqlite3_malloc64` + `memcpy`) takes another. For a
  1,994,911,744-byte healthy snapshot: 1541 ms, peak RSS 3884 MB. For 5 damaged 490 MB snapshots:
  1776 ms total, peak RSS 2039 MB. Doctor being OOM-killed on a small host is reasoned from these
  numbers, not reproduced.
- **P3-4 Exported `snapshotPassesIntegrityCheck` reads unbounded streams.** Called on a `.bak`
  symlinked to /dev/zero, the probe process was killed (exit 137). `dbUnusableRemedy` is shielded
  only by its caller's `size > 0` filter: stat follows the link and devices and FIFOs report 0.
  The JSDoc claims "Any failure ... is 'does not pass'".
- **P3-5 The fixture's damage offset assumes pages under 64 KiB** (tests/test-helpers.mjs:46).
  `readUInt16BE(16)` is 1 for 64 KiB pages, so `page3` would be 2 and the header would be garbled
  instead of page 3. Not triggered: the default page size is 4096.
- **P3-6 The restore arm still overwrites the broken file, and the keep-it advice comes after the
  command** (install.mjs:493-494). This predates the release. D#554 now says such a file can hold
  readable rows (200 of 241). With D#553 the named snapshot can also be older than the newest
  (the date is visible only in the file name).
- **P3-7 The SessionStart 'unchecked' note promises that doctor "names the newest one that passes"**
  (lib/db-unusable.mjs:249). When none passes, doctor prints set-aside instead.
- **P3-8 A directory symlink counts as a snapshot** (see P2-1). snapshotCount and the "N backup
  snapshot(s)" sentence include it.
