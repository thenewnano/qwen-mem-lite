### Findings

**P1**
- **Claim 2 is false, and the code behind it regressed from 6.30.2.** A long CJK paragraph or base64 blob now loses most of the stored row: 10,000 → 8 characters in one case. Chinese text with no spaces is a likely trigger for this user. The fix belongs in the code (`dropCutTokenAtEnd` in `scrubHead`, `utils.mjs`), not only in the CHANGELOG wording. The fuzz needs whitespace-free runs added to catch it.

**P2**
- **The "5 of 6" figure pools two different setups** (CHANGELOG and the `schema.mjs:1843` comment). It adds the `wal_autocheckpoint=0` arm that an earlier review had already corrected to the default-setting arm. That comment also cites `#696`, a memory row a fresh clone cannot see.
- **New README bullet "A damaged full-text index is rebuilt on open" is false** (zh: "打开时发现全文索引损坏会自动重建"). On the shipped SQLite 3.53.4, with a damaged `events_fts` structure record, the open succeeds with no recovery message. A MATCH query then throws `SQLITE_CORRUPT_VTAB`, and a second open does the same. This matches the release's own D#524 finding (FTS5 reads the record at query time, not at connect). The index actually gets repaired by `fts-check rebuild` or doctor.

**P3**
- **-shm is rewritten.** "Leaves every file as it is", "left as they are" and the doc's "change no file" all overstate it: main and WAL stay byte-identical (10/10 with 6 concurrent openers), but -shm changes 10/10.
- **"Up to 2.3 s" is one run's median, not a bound.** The doc's in-process figure is 2,633 ms, the `utils.mjs` comment says 2.0–2.6 s, and commits c5e4654a and 97e2e1d5 give 2.0–2.3 and 1.9–2.1. "The slowest" means the slowest per-shape median, measured on c5e4654a.
- **The "19,679 fragments" for the unscrubbed variant cannot be reproduced.** The archived script gives 20,167 for seed 1 × 300 and 345,546 for the stated 5,300 prompts. It also counts secrets that leaked at least one fragment, not fragments.
- **The fuzz samples fragments at stride 6,** so a leaked run of 12–16 chars could go unseen.
- **Commit 97e2e1d5 generalises too far.** "Not reached by WAL damage" goes beyond what was tested: single, newest-frame damage only.
- **README's upgrade step omits an exception.** It does not say that a "malformed database schema" error with a WAL beside it gets no command; the CHANGELOG does.
- **"Characters" are UTF-16 code units.**
