# v6.31.0 (D#550 / D#551) blind pre-release defect review: `main...78eda8b4`

Taken 2026-10-22, Linux, Node 26.8.1, better-sqlite3 13.0.3 (SQLite 3.53.4), system sqlite3 3.46.1.
Trees: `git archive 78eda8b4` (the release) and `git archive main` (d3de9748, v6.30.3) in
`~/.cache/tmp/d550-r2-def-sF0H`, node_modules symlinked to the repo. Every child ran through
`run.sh` (Appendix): HOME, TMPDIR, CLAUDE_MEM_DIR, CLAUDE_PROJECT_DIR inside the sandbox;
MEM_NO_AUTO_ADOPT/SKIP_UPDATE/SKIP_MAINTAIN/SKIP_SAVE_ENRICH=1; key, token, proxy, CLAUDECODE,
CLAUDE_CODE_*, CLAUDE_PID variables unset; PATH = sandbox bin (node only), /usr/bin, /bin. The
repo's git state was not touched (`git status` clean at the end). Sandbox deleted at the end.

## Verdict

The contract's narrow claims hold. doctor never changed a byte of the MAIN file of a store that
failed its check (the four layouts I hashed). `snapshotDb` leaves no file after a failed VACUUM INTO.
The restore command skips 0-byte snapshots. But four P1s hurt a user who follows the output:
- (1) The README recovery prints `ok` and then places a store with 0 of 241 (or 12 of 300)
  observations. doctor is all ✓ afterwards.
- (2) Search-index damage that 6.30.3's doctor healed now ends at "restore a snapshot". The
  lossless `fts-check rebuild` heals it and is named nowhere on that path, while the CLI's own
  error text still says doctor rebuilds it.
- (3) and (4) are older (also in 6.30.3). On the `✗ Database:` (store will not open) path, the
  restore command names a damaged snapshot that the product itself wrote. The set-aside text calls
  a main file "not recoverable" when it passes integrity_check with 200 of 241 rows.

## Findings

### P1-1. The README recovery prints `ok` and places a store missing the whole observations table; doctor is green afterwards
- **Files:** README.md:1027 ("Only when all it prints is `ok`, put the recovered database in
  place") and README.zh-CN.md:797. The only gate is `PRAGMA integrity_check` on `recovered.db`.
  README.md:1039-1047 discloses `lost_and_found` and constraint drops. Its measured claim counts
  only "rows SQLite could still read from the damaged database".
- **Defect:** `integrity_check` says `ok` when `.recover` sent every row of a table to
  `lost_and_found`, or dropped them all with `INSERT OR IGNORE`. No step compares row counts, so
  block 2 places the store and doctor goes green.
- **(a) Log frame of the observations root (interior page).** Layout: the archive's 869 shape
  (200 checkpointed, 40 in the log, VACUUM, 1 more = 241 observations). The newest log frame of
  page 5 (the observations root) is garbled with 64×0x41 at offset 8 and the log re-signed.
  - doctor: ✗.
  - Block 1 verbatim: `ok`.
  - recovered.db: `observations`=0, and `lost_and_found` holds 241 rows with nfield=41.
- **(b) Log frame of sqlite_schema page 10, offset 3000.** The stored observations DDL loses a
  column (`cited_count INTEGER AAAA…emoted_at INTEGER`).
  - doctor: `✗ Database integrity: NULL value in observations.decay_seen_count …`.
  - The damaged copy reads 241/241 observations by rowid.
  - Block 1: `ok`; recovered.db: 0 observations, no lost_and_found.
  - Block 2 placed it. Then doctor printed `✓ Database integrity: ok`,
    `✓ FTS5 integrity: all indexes healthy` and `✓ DB stats: 0.3MB, 0 observations, 0 sessions`;
    `cli.mjs search alpha` printed `No results for "alpha"`.
  - One product open of the damaged store instead (what README.md:1004 forbids) leaves 241
    readable.
- **(c) Main-file root (interior) page of observations, 300-row store.**

  | Damage | Readable by rowid | Placed | In lost_and_found |
  |---|---|---|---|
  | cell pointers garbled | 12 | 12/300 | 288 |
  | offset 4000 garbled | 183 | 192/300 | 108 |
  | page zeroed | 0 | 0/300 | 300 |

  doctor's `DB stats` line said "300 observations" before (count(*) through an index) and
  "12 observations" with ✓ after.
- **Rate:** I swept every page that has a log frame in the 869-shaped store, at offsets 8 and

### P3 findings
- **P3-1. doctor writes -wal/-shm on a ✗ store.** The README (README.md:247 and :1003, "doctor
  changes nothing in the database") and contract 1 ("nothing to … its -wal/-shm") both claim

  - A leftover -shm is rewritten (sha 5c00fedd → 002d5165).
  - The main file was byte-identical in every run. tests/doctor-integrity.test.mjs hashes main and

- **P3-2. The `✗ Database integrity` line is one long line with a wrong count.** SQLite returns

- **P3-3. doctor says no snapshot exists when an empty one does.** install.mjs:486 says "No backup

- **P3-5. The session doctor ran in can undo "changes nothing".** The ✗ output does not say to

## NOT CHECKED
- **Other sqlite3 versions.** Only 3.46.1 was run, though the README says 3.29+. The 3.29–3.39
  `.recover` is a different implementation, and before 3.44 integrity_check does not check FTS5
  tables. Not checked either: macOS's sqlite3, zsh and fish paste, Windows (unlinking a target a
  handle may still hold).
- **Real ENOSPC and permission errors.** I used RLIMIT_FSIZE instead; permission errors in the
  middle of a VACUUM and network filesystems were not tried.
- **Large stores.** The largest was 6,000 rows (4 MB). Not run: a SQLITE_NOMEM from integrity_check
  on a sound but huge store, which would read as damage.
- **The archive's populations.** I did not run main:21:800, two:22:300 or log:23:800. My only
  sweep was the 869 shape (196 log-frame plants) plus hand-built layouts.
- **A real Claude Code session.** The Stop hook was simulated with a synthetic event.
- **Daily auto-maintain.** Whether it writes damaged pre-maintain snapshots was not checked; only
  the delete path was run.

```js
// usage: node gen.mjs <dir> [rows=300] [walRows=0]
// A store through the tree's initSchema; `rows` checkpointed, then `walRows` more left in the log
// (the process exits without closing, so the -wal stays; -shm removed afterwards to model a closed crash).
import Database from '/home/ai/.cache/tmp/d550-r2-def-sF0H/tree/node_modules/better-sqlite3/lib/index.js';

const walRows = Number(walArg);
if (walRows > 0) {
```

### dmg.mjs
```js
// usage: node dmg.mjs <db> <mode> — plants damage.
//  leaf-idx : 64 bytes of 0x41 into the first leaf of idx_obs_project_live (main file)
//  leaf-obs : 64 bytes of 0x41 at offset 3000 of the 3rd leaf page of observations (main file)
//  wal-obs, wal-obsptr : like wal-idx, on the newest log frame of an observations leaf, at offset 3000 or 8
//  wal-idx  : the db must have a -wal; garbles the newest log frame of an index leaf and re-signs the log
import Database from '/home/ai/.cache/tmp/d550-r2-def-sF0H/tree/node_modules/better-sqlite3/lib/index.js';
import { openSync, writeSync, closeSync, readFileSync, writeFileSync, copyFileSync, mkdtempSync, rmSync } from 'node:fs';
import { join } from 'node:path';
const [p, mode] = process.argv.slice(2);
function pagesOf(dbFile, name) {
  // dbstat on a COPY of main+wal so the store itself is never opened
  const d = mkdtempSync(join(process.env.TMPDIR, 'dbstat-'));
  copyFileSync(dbFile, join(d, 'x.db'));
  try { copyFileSync(dbFile + '-wal', join(d, 'x.db-wal')); } catch {}
  const db = new Database(join(d, 'x.db'), { readonly: true });
  const r = db.prepare(`SELECT pageno FROM dbstat WHERE name = ? AND pagetype = 'leaf' ORDER BY pageno`).pluck().all(name);
  db.close(); rmSync(d, { recursive: true, force: true });
  return r;
}
function plant(file, pageno, offset, bytes) {
  const fd = openSync(file, 'r+');
  writeSync(fd, Buffer.from(bytes), 0, bytes.length, (pageno - 1) * 4096 + offset);
  closeSync(fd);
}
function walChecksum(buf, s0, s1, be) {
  for (let i = 0; i + 7 < buf.length; i += 8) {
    const a = be ? buf.readUInt32BE(i) : buf.readUInt32LE(i);
    const b = be ? buf.readUInt32BE(i + 4) : buf.readUInt32LE(i + 4);
    s0 = (s0 + a + s1) >>> 0; s1 = (s1 + b + s0) >>> 0;
  }
  return [s0, s1];
}

else if (mode === 'leaf-obs') plant(p, pagesOf(p, 'observations')[2], 3000, Array(64).fill(0x41));
else if (mode.startsWith('wal-')) {
  const wal = Buffer.from(readFileSync(p + '-wal'));
  const be = wal.readUInt32BE(0) === 0x377f0683;
  const frames = [];
  for (let o = 32; o + 24 + 4096 <= wal.length; o += 24 + 4096) frames.push({ o, pg: wal.readUInt32BE(o) });
  const inLog = new Set(frames.map((f) => f.pg));

  if (!leaf) { console.error('no leaf in log'); process.exit(2); }

  wal.fill(0x41, target.o + 24 + ({ 'wal-obs': 3000, 'wal-obsptr': 8 }[mode] ?? 1000), target.o + 24 + ({ 'wal-obs': 3064, 'wal-obsptr': 72 }[mode] ?? 1064));
  let [s0, s1] = walChecksum(wal.subarray(0, 24), 0, 0, be);
  for (const f of frames) {
    [s0, s1] = walChecksum(wal.subarray(f.o, f.o + 8), s0, s1, be);
    [s0, s1] = walChecksum(wal.subarray(f.o + 24, f.o + 24 + 4096), s0, s1, be);
    wal.writeUInt32BE(s0, f.o + 16); wal.writeUInt32BE(s1, f.o + 20);
  }

  console.log('page', leaf);
```
