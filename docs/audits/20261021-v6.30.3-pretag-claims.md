### Findings

**P1-1: following the WAL step with a live session damages the database file (commit a58f552f title and body; install.mjs:478-481 comment; the remedy text at install.mjs:513-516).**

The claim is that the first step keeps the database file. It does so only if the log survives until the `mv` runs. A WAL with frames sits beside the store mainly while a Claude Code session holds it open. The step's precondition is "with every Claude Code session closed". Closing a session cleanly makes server.mjs run `wal_checkpoint(TRUNCATE)` and `db.close()` (server.mjs:2332-2341, SIGTERM/SIGINT), or close the database on exit after stdin EOF. Either way the damaged frames are written into the database file and the log is deleted.

Reproduced on plant 2:8 (a qc-fails, opens-ok plant), new tree, with a real `server.mjs` holding the store:
- doctor #1 prints the ✗ Database line and the WAL step; main is still pristine and the WAL is 2,286,632 B.
- After SIGTERM to the server: the main file changed, a main-only quick_check fails with `Offset 65535 out of range`, and there is no -wal.
- The printed step fails with `mv: cannot stat …-wal: No such file or directory`.
- doctor #2 prints "No backup snapshot exists … Set the broken file aside so a fresh store is created".

Stdin EOF gives the same result. Only SIGKILL, which skips the shutdown, leaves the log, and then the step keeps the file pristine and doctor #2 reads healthy.

The base tree fails the same way in the same sequence: on session close the file is damaged, and its doctor #1 had printed "✓ FTS5 integrity: all indexes healthy". So this is not a worse outcome than v6.30.2. What is wrong is the safety claim and the remedy's ordering.

Corrected statement: the step keeps the database file only when no process holds the store open. A session that closes cleanly first writes the damaged log into the file, after which the re-run's restore or set-aside step is the remedy.

**P2-1: install.mjs:536-537 "an FTS5 error arrives after theirs"; doc l.40 "runs FTS5's own check last".**

FTS5's xIntegrity does run after the b-tree and table checks. But preparing the PRAGMA connects every FTS5 table first (sqlite3.c:146977). A constructor error is therefore thrown by `prepare`, before any row: 34:0, 34:8 and 34:4032 give `vtable constructor failed: events_fts` with 0 rows, and the b-tree finding for page 34 is never reported. The gate still flags these because the code is SQLITE_CORRUPT. A constructor SQLITE_NOMEM would reach the RW FTS check with no page check run (not observed in the sweep).

Corrected: "FTS5's integrity method runs after the b-tree and table checks; its constructor runs when the PRAGMA is prepared, so a constructor error arrives with no rows."

**P2-2: commit dcd0389f "every other shape within -3% to +3%".**

The commit names only f6EscAx, depthsNoRun and quoteComma, so "every other shape" includes f6EscAbBsx (1679 → 100, −94%) and f6EscAbCx (1866 → 101, −95%). It also includes escaped, which is 823 → 795 (−3.4%) in the doc's own table. The commit's "−3%" also disagrees with the doc's "−1%".

Corrected: "f6EscAbBsx 1679 → 100 and f6EscAbCx 1866 → 101 ms as well; escaped 823 → 795; the other 14 shapes −1% to +3%, inside run-to-run noise (this review: −2.5% to +2.7% medians, ±7.5% per run on shapes the change cannot reach)."

**P2-3: commit a58f552f "the database file was damaged after doctor in 143 on HEAD and in 0 with this change"; doc l.63 "the normal checkpoint of a sound WAL".**

"Damaged" here means "fails quick_check". That ruler cannot see damaged record content. In 11 of the 275 qc-ok plants the 0xff bytes land in an `observations` row. Both trees checkpoint that garbled row into the database file and rebuild FTS over it. Those are exactly the 11 "FTS rebuilt" in that class. This does not change the A/B, but the prose overstates what "0" covers and calls the WAL sound.

Corrected: "0 of 474 fail quick_check on the database file after doctor (143 on HEAD). In 11 more, whose damage is inside an observations row and passes quick_check, both trees write the row into the database file."
