## Q1. SQLite itself

### 1a. What the two integrity_check messages mean

**"wrong # of entries in index X"** compares b-tree entry counts. It is not a row-by-row check.

- `OP_IntegrityCk` walks every table and index b-tree page by page. On each leaf page (and on index interior pages) it adds the
  page's cell count to `nRow` (sqlite3.c:84157-84158, `if( pPage->leaf || pPage->intKey==0 ) pCheck->nRow += nCell;`). It
  then stores one count per tree in a register (sqlite3.c:84465-84477, `sqlite3MemSetArrayInt64(aCnt, i, sCheck.nRow)`; the
  call passes `&aMem[pOp->p3]`, and pragma.c passes P3=8, sqlite3.c:~146583).
- The pragma code compares each index's count with its table's count and emits `"wrong # of entries in index " || name` when
  they differ (sqlite3.c:146591-146618).
- **The message does not say which side holds more.** It is skipped for partial indexes (`if( pIdx->pPartIdxWhere==0 )`,
  in the same block).
- This block runs before the `isQuick` branch and is not inside it. **quick_check therefore emits it too.** Observed below on
  both 3.53.4 and 3.46.1.

**"row N missing from index X"** comes from a per-row scan of the table.

- For each row that a table cursor reaches (`OP_Rewind iDataCur`; reg[7] counts the rows, sqlite3.c:~146645-146656), it builds
  the expected index key and looks it up with `OP_Found`/`OP_IFindKey`. If the key is absent it emits `"row " || rowid ||
  " missing from index " || name` (sqlite3.c:~146866-146888).
- This means **the table has the row and the index lacks it**. The direction is fixed.
- The scan sits inside `if( !isQuick ){ /* Omit the remaining tests for quick_check */` (sqlite3.c:~146857), so **quick_check
  never emits it**.

**Taken together**, in a full integrity_check:

| What integrity_check prints | What it means |
|---|---|
| "wrong # of entries in index X" and **no** "row N missing from index X" lines | The index holds more entries than the table has rows. The table lost cells, or the index holds stale extras. |
| "wrong # of entries" **plus** per-row "missing from index" lines | The index is missing entries for rows the table still has. |

The official page lists only "Missing or surplus index entries" among what integrity_check looks for. It also says
integrity_check returns "at most N errors before the analysis quits, with N defaulting to 100". On quick_check, the page says it
"does not verify UNIQUE constraints and does not verify that index content matches table content". Index **content** is skipped;
the entry **count** is still compared (https://www.sqlite.org/pragma.html#pragma_integrity_check, #pragma_quick_check).

### 1b. VACUUM INTO copies index b-trees as-is

`sqlite3RunVacuum` (sqlite3.c:161602) copies in this order:

1. It creates every table, then every index, in the destination (`SELECT sql … WHERE type='index'`, sqlite3.c:~161757-161769).
2. Then, for each table, it runs `INSERT INTO vacuum_db.T SELECT*FROM main.T` (sqlite3.c:~161772-161782).

With `DBFLAG_Vacuum` set, that INSERT takes `xferOptimization` (insert.c, sqlite3.c:141891-142290):

- The comment says "The xfer optimization transfers raw records from tab2 over to tab1. … Raw index records are transferred
  in the same way. … This optimization is particularly useful at making VACUUM run faster."
- **Table copy loop:** `OP_Rewind`/`OP_RowCell`/`OP_Next` over the source **table** cursor.
- **Index copy loop, run separately:** for each destination index it opens the compatible **source index b-tree**
  (`OP_OpenRead … pSrcIdx->tnum`), then `OP_Rewind` / `OP_RowCell` / `OP_IdxInsert` / `OP_Next` over that index. It does not
  derive index keys from the copied table rows (sqlite3.c:~142228-142285).
- So **the table's contents are whatever the table walk can reach, and the index's contents are whatever the index walk can
  reach.** A table b-tree that has lost cells, next to an intact index, carries that mismatch into the snapshot.
- The docs say only that the output "will contain the same logical content as the original database". The page does not cover
  a corrupt source, and it says nothing about checking the output (https://www.sqlite.org/lang_vacuum.html).

**Measured this session.** `lossy-probe.mjs` used better-sqlite3 13 / SQLite 3.53.4 on a scratch DB:
`t(id INTEGER PRIMARY KEY, epoch, body)`, an index `t_epoch(epoch)`, and 410 rows over 22 table leaf pages. It then set the
cell count of 21 of the 22 table leaves to 1, the same shape as the measurements doc's "ncell1" implant.

| Database | quick_check | integrity_check | `count(*)` | `count(*) … NOT INDEXED` |
|---|---|---|---|---|
| Damaged source | 21 "Fragmentation … reported as 0" lines + "wrong # of entries in index t_epoch" | same, **no** "missing from index" | 410 | 40 |
| `VACUUM INTO` snapshot (succeeded, no error) | "wrong # of entries in index t_epoch" only | same only | **410** | 40 |
| Snapshot after `REINDEX` | — | **ok** | 40 | — |
| Control: an index leaf truncated instead (2000 rows) | "Fragmentation …" + "wrong # …" only | "Fragmentation …" + "wrong # …" + "row N missing from index t_epoch" lines, cut off at **100 rows** (the cap) | — | — |

- On the source, `count(*)` is answered from the index, which is why it reads 410 while the table scan reads 40.
- System sqlite3 3.46.1 prints the same single line for both pragmas on the snapshot.
- This matches the measurements doc (docs/audits/20261023-v6.30.6-d558-a3-measurements.md, correction 4): 73/73 lost-rows
  snapshots carry the ncell1 implant, their `NOT INDEXED` count equals the snapshot's rows, and `count(*)` is answered by the
  covering index `idx_obs_epoch_project`.

**Same mechanism, my inference (UNCONFIRMED by a run):** in-place `VACUUM` runs the same `sqlite3RunVacuum` and the same xfer
path, so it would preserve the mismatch the same way. `REINDEX` erases it. So does any rebuild that derives the index from the
table, as Firefox's clone does (below).

### 1c. What SQLite recommends for verifying a backup

I found **no official recommendation to verify a backup** on these pages:

- **Backup API** (https://www.sqlite.org/backup.html): the destination is "a bit-wise identical copy of the source database as
  it was when the copying commenced", with "a consistent and up-to-date snapshot". No checking is described. A page-for-page
  copy carries source corruption over unchanged.
- **VACUUM INTO** (https://www.sqlite.org/lang_vacuum.html): an "alternative to the backup API"; "transactional in the sense
  that the generated output database is a consistent snapshot". It warns only that an interrupted run "might be incomplete and
  corrupt". No checking is described.
- **sqlite3_rsync** (https://www.sqlite.org/rsync.html): the replica is "a fully-consistent snapshot of ORIGIN", and "All of the
  table (and index) content will be byte-for-byte identical in the replica". No integrity check is mentioned. Corruption in the
  origin replicates.
- **Recovery / `.recover`** (https://www.sqlite.org/recovery.html): "the results will always be suspect", "It is best to think
  of the recovery API as a salvage undertaking", and "some rework and testing should be performed prior to returning the
  recovered database to service". Constraints "may not be valid after recovery". This is the only text that asks for testing
  before reuse.

UNCONFIRMED: whether SQLite developers recommend `PRAGMA integrity_check` on backups in forum posts. I did not search the forum.

## Q2. How established tools choose which backup to restore

| Tool | Verify at backup time | Verify at restore time | Who picks | "Smaller than expected" notion |
|---|---|---|---|---|
| Firefox places.sqlite (DB itself) | No | Corrupt DB is cloned table by table, with indexes rebuilt afterwards; no check of the result | Automatic | No |
| Firefox bookmark JSON backups | No source check found; a new file only when the content hash changes | Startup imports the **newest** file, no check | Automatic at startup; **user** in the Library menu | **Item count stored in the filename and shown in the Restore menu** |
| Firefox session store | — | First file in a fixed order that reads, parses and has a known version | Automatic | No |
| Chromium `sql::Recovery` | No backups kept (in `sql/`) | Salvage in place with sqlite3_recover; data loss accepted | Automatic | No |
| Litestream v0.5 | LTX file checksum / ordering checks | Optional `-integrity-check quick\|full`; on failure deletes the output and errors, **no fallback** | Newest (or a user TXID/time) | No |
| Litestream v0.3 `validation-interval` | Periodic: restore the replica and compare its CRC with the primary | — | Newest | No |
| restic | No source check | `check` (structure), `--read-data` (packs); separate commands | User (snapshot ID) | "Size" column (≥0.17), shown to the user only |
| borg | Interrupted runs are marked as checkpoint archives | `check` (not read this session) | User | — |
| pgBackRest | `--checksum-page` validates source pages, records bad pages in the manifest; `--checksum-page-error` aborts the backup | `verify` (separate command) | Newest by default (`--set latest`) | — |

### Firefox (mozilla-central @ 4190c69a7dd5)

**The places.sqlite database itself** (`toolkit/components/places/Database.cpp`):

- When a database opens as `NS_ERROR_FILE_CORRUPTED`, or schema init fails, `BackupAndReplaceDatabaseFile` runs (:643-651,
  :689-707, :837+). It keeps **one** `places.sqlite.corrupt` copy ("Ensure we never create more than one corrupt file", with a
  24 h throttle, :860-884) and removes the database.
- It then `TryToCloneTablesFromCorruptDatabase` (:920-933, :950-1060):
  - For each `moz_*` table: `INSERT INTO main.T SELECT * FROM corrupt.T`, retried as `… ORDER BY rowid DESC` if that fails.
  - **"Recreate the indices. Doing this after data addition is faster."** The indexes are built from the copied table rows,
    never copied.
  - The result is committed and renamed into place, and the `.corrupt` file is deleted.
  - There is no integrity_check of the clone and no comparison of row counts. A successful clone sets status OK (:927-930).
- **Maintenance** (`PlacesDBUtils.sys.mjs`, `integrity()` :1426-1470): `PRAGMA integrity_check`; if not ok, `REINDEX`, then check
  again. If it still fails, it sets the pref `places.database.replaceDatabaseOnStartup` (:108-115), and the next startup replaces
  the database (Database.cpp:608-622). **REINDEX-then-pass is accepted as fixed.** That is the same rule the withdrawn attempt 3
  used, with the same blind spot: in the probe above, the lossy snapshot passes after REINDEX with 40 of 410 rows.
- `.corrupt` files older than 14 days are removed (`PlacesDBUtils.sys.mjs` :9, :1213-1250).

**Bookmark backups** (`PlacesBackups.sys.mjs`):

- These are JSON exports, not database copies, named `bookmarks-<date>_<count>_<hash>.json(lz4)` (filenamesRegex :16; the
  groups are date, **bookmarks count**, contents hash; :120-128).
- `create()` writes a new file only when the hash differs from the most recent backup (:442-445).
- `limitBackups` deletes the oldest files beyond `aMaxBackups` (:28-41). Pruning is by count, and there is no fullness check.
- I found no check of the source database's health before export in `create()`/`saveBookmarksToJSONFile` (:330-397, :413-470).
  UNCONFIRMED that no caller checks it.
- **On a corrupt database**, `PlacesBrowserStartup.sys.mjs` :157-180 restores `getMostRecentBackup()` with `replace: true`.
  That function returns the first `.json(lz4)` file in the list sorted by date, newest first (`PlacesBackups.sys.mjs` :283-294,
  sort :197). The JSON is not checked beyond importing it. With no backup at all, it falls back to bookmarks.html, then to the
  defaults.
- **Manual restore** (`browser/components/places/content/places.js` `populateRestoreMenu` :619-670) lists **every** backup,
  newest first, labelled with date, size and **item count** (`PlacesBackups.getBookmarkCountForFile`, :647-661). The user
  chooses.

**Session store** (`browser/components/sessionstore/SessionFile.sys.mjs`):

- The load order is `["clean", "recovery", "recoveryBackup", "cleanBackup"]`, plus `"upgradeBackup"` (:141-144).
- The loop (:197-370) takes the first file that reads, parses (`JSON.parse`) and has a supported version (:235-294). Each
  failure is marked `corrupted = true` and it moves on to the next file.
- Validity here is structural only.

### Chromium (@ 195c30006270)

- **No choice among several backups.** The `sql/` layer keeps none.
- `sql::Recovery::RecoverIfPossible` (`sql/recovery.cc` :53-) runs only when `ShouldAttemptRecovery`, i.e. when the error is
  catastrophic (`IsErrorCatastrophic`, :35-43).
- It salvages with `sqlite3_recover`:
  - `SQLITE_RECOVER_LOST_AND_FOUND` is set to nullptr (:218), so there is no lost-and-found table.
  - It recovers into a temporary database (:203-262).
  - `ReplaceOriginalWithRecoveredDb` writes that over the original with the backup API (:268-).
  - If recovery fails, it razes the database.
- The contract (`sql/recovery.h` :105-115): "After attempting recovery, the database can be re-opened and assumed to be free of
  corruption … It is not considered an error if some or all of the data cannot be recovered due to database corruption, so it
  is possible that some records could not be salvaged". There is no row-count comparison.
- `Database::FullIntegrityCheck` exists (`sql/database.cc` :2661-), but it is not part of recovery selection.
- UNCONFIRMED: whether any individual Chromium feature keeps its own multi-generation SQLite backups. I surveyed only `sql/`.

### Litestream (main @ f282d0ef, v0.5.17)

- **Restore selection is the newest point.** `CalcRestorePlan` (`replica.go` :1514-1545) takes the latest snapshot at or before
  the target TXID or timestamp, then the LTX files after it. The default target is the latest. Nothing is chosen by content.
- **Post-restore check is opt-in.** `-integrity-check none|quick|full`, default `none` (`cmd/litestream/restore.go` :41,
  :76-84, usage :422-423). `checkIntegrity` (`replica.go` :1331-1365) runs the pragma and reads one row, failing if it is not
  `"ok"`. On failure the restore **deletes the output and returns an error** (:770-779). There is no fallback to an older
  snapshot.
- **Backup-time checks cover Litestream's own files, not SQLite content.** LTX files are decoded and `Verify()`ed (`db.go`
  :686-687). The v0.5 `validation:` block checks LTX "sort order and contiguity", and `verify-compaction` checks TXID
  consistency (https://litestream.io/reference/config/). None of these checks the SQLite source's logical integrity.
- **v0.3.13 `Validate`** (`replica.go` @v0.3.13 :811-): "restores the most recent data from a replica and validates that the
  resulting database matches the current database". It does this by comparing a CRC64 of the restored file with the primary's,
  computed under lock. A mismatch is logged and counted. This proves replica == primary, so **a corrupt primary validates a
  corrupt replica**. The current config page lists `validation-interval` as "Deprecated. Use the `validation:` global config
  block instead."
- Retention is time-based (`snapshot.retention`, default 24h). There is no notion of validity.

## Q3. Refusing to take, or to count, a backup of a source that fails a check

The precedents found:

- **pgBackRest `backup --checksum-page-error`**: refuses to complete a backup of a source whose pages fail validation. It is
  opt-in. The default is to take the backup and **record the bad pages in the manifest**, so the flaw travels with the backup.
- **pgBackRest `expire --checksum-page-error`**: retention refuses to proceed when what it would leave as the oldest retained
  backup carries checksum errors. This is the closest match to "damaged copies must not be what pruning leaves behind".
- **borg prune**: incomplete (checkpoint) archives do not count against `--keep-X`. An incomplete run cannot push a complete
  archive out of retention, and it is removed once a complete archive exists.
- **Firefox Places** keeps the damaged database apart from the backups: at most one `.corrupt` file, aged out after 14 days. Its
  bookmark-backup rotation, though, is a **counter-example**:
  - it is pruned by count with no source check;
  - a new export is written whenever the content hash changes;
  - so a run of exports from a database that lost bookmarks can push out older, fuller exports.
  - The count in the filename is shown to the user but used by nothing automatic.
- **Litestream** and **restic** do not gate retention on validity. Litestream's retention is time-based. restic's forget
  policies I did not read this session (UNCONFIRMED).

I found no surveyed tool that validates **completeness** (rows present versus rows expected) at backup time. Every check found
is structural: page checksums, b-tree consistency, file checksums, parse success.

## Q4. The four selection rules

**(a) Newest snapshot that passes a check**

- **Precedent:** Firefox session store (first in priority order that parses); Litestream (newest only, optional check, no
  fallback, which is stricter); Firefox startup bookmark restore (newest, no check); Firefox maintenance (integrity, then
  REINDEX, then recheck, accepted as fixed).
- **Known failure mode:** every surveyed check measures consistency, not completeness.
  - A consistent but lossy copy passes once its index is rebuilt: probe above, 40/410 rows → `ok`; release measurement, 73 of
    605 passing snapshots.
  - The "newest" ordering then hides an older, fuller copy (P1-1).
  - Retention keyed on recency (claude-mem-lite's newest-3 per tag, Firefox's max_backups) then deletes the fuller copy.

**(b) Newest snapshot whose own pre-REINDEX integrity_check shows no lost-rows signature**

- **Precedent:** none found. No surveyed tool reads the direction of index/table count mismatches to rank backups.
- **SQLite semantics support the signal** (Q1a): "wrong # of entries" with no "missing from index" lines means the index has
  more entries than the table. The xfer copy preserves it into VACUUM INTO snapshots (Q1b, probe).
- **Failure modes, from the source and probe:**
  1. **Error cap.** integrity_check stops at N errors (default 100), and "missing from index" lines come after the count line. A
     result truncated by other errors can look like "no missing lines". Pass a large N, or compare counts directly:
     `count(*) … NOT INDEXED` versus a count through each index.
  2. **Damage on both sides.** If the table lost some rows and the index lost entries for others, "missing from index" lines
     appear and the rule reads it as index damage. The table loss is missed.
  3. **No witness.** A table with no indexes, or a loss covered only by partial indexes (excluded from the count check), leaves
     no count mismatch at all.
  4. **The witness can be erased.** Any REINDEX, or a rebuild from table rows (Firefox-style clone, `.recover`-style salvage),
     before the snapshot removes the signal. A source rebuilt that way and then snapshotted looks intact.
  5. **Loss the product made before the snapshot.** The measurements doc's 6 D#557 snapshots (241 → 200) lost rows when the
     product deleted a damaged log on open, before `delete` took the snapshot. Nothing in the snapshot shows the loss: 6 of the
     79 short-of-store passing snapshots in that population.
  6. **Not every index is covered.** The count check covers ordinary b-tree indexes only. FTS5 shadow tables have their own
     `'integrity-check'` command and are not compared here.
  7. **Damage in the snapshot file itself** after it was written still needs a normal check. (b) is an addition to a check, not
     a replacement for one.

**(c) List every passing snapshot with its row count and let the user choose**

- **Precedent:** Firefox Library "Restore" menu (date, size, item count from the filename); restic `snapshots` Size column
  (≥0.17); pgBackRest `--set`; restic snapshot IDs. These are listed for the human to pick from. None picks automatically by
  count.
- **Known failure modes:**
  1. The user cannot tell a count drop caused by their own deletes from one caused by loss. Firefox only shows the number.
  2. **The count must not come from an index.** On the lossy snapshot, plain `count(*)` returns **410**, answered by the index,
     while the table holds 40 (probe). A listing built on `count(*)` would advertise the lossy snapshot as the fullest one. The
     count has to be taken after REINDEX or with `NOT INDEXED`.
  3. `doctor` output is non-interactive. A list moves the decision to a human who may run the first command printed.

**(d) Verify each snapshot when it is created and only ever name verified ones**

- **Precedent:**
  - pgBackRest `--checksum-page` with the bad-page list kept in the manifest, `--checksum-page-error` to refuse, and
    `expire --checksum-page-error`;
  - borg checkpoint marking excluded from retention counts;
  - Litestream v0.3 `validation-interval`, which compares replica to primary only.
- **Known failure modes:**
  1. **What the verifier checks decides what it catches.** Litestream's check proves only replica == primary, so a corrupt
     primary passes. For the lossy shape, a creation-time integrity_check **without** REINDEX does fail ("wrong # of entries",
     probe on both pragmas). A verifier that REINDEXes first, as attempt 3 did, would mark it verified.
  2. **Damage after creation** (bit rot, a truncated copy) is invisible to creation-time verification. pgBackRest and restic keep
     a separate restore-side `verify`/`check` for that.
  3. **Cost.** Full integrity_check is O(N log N) per the docs, at every snapshot. quick_check is O(N) and still sees the count
     mismatch (Q1a), but not the per-row direction.
  4. **Retention must honour the flag**, or newer unverified snapshots still push out the verified ones. The borg and pgBackRest
     expire precedents exist for exactly that. claude-mem-lite's `pruneSnapshots` (newest 3 per tag) and `enforceBackupBudget`
     (over 256 MB, evict older than 7 days) count every snapshot today, per the brief and the a3 defects doc P1-1. I did not
     re-read lib/db-backup.mjs.
  5. **Snapshots taken before the feature ships** carry no flag.

// Probe: lossy table b-tree + intact index -> VACUUM INTO -> what do the checks say?
import { createRequire } from 'node:module';
import { readFileSync, writeFileSync, rmSync, copyFileSync } from 'node:fs';
import { join } from 'node:path';
const require = createRequire('/home/ai/dev/claude-mem-lite/package.json');
const Database = require('better-sqlite3');
const dir = process.argv[2];
const src = join(dir, 'src.db'), snap = join(dir, 'snap.db'), fixed = join(dir, 'fixed.db');
for (const f of [src, snap, fixed]) rmSync(f, { force: true });
let db = new Database(src);
console.log('sqlite', db.prepare('select sqlite_version() v').get().v);
db.exec("PRAGMA page_size=4096; CREATE TABLE t(id INTEGER PRIMARY KEY, epoch INTEGER, body TEXT); CREATE INDEX t_epoch ON t(epoch);");
const ins = db.prepare('INSERT INTO t(epoch, body) VALUES (?, ?)');
db.transaction(() => { for (let i = 0; i < 410; i++) ins.run(1000 + i, 'x'.repeat(200)); })();
const leaves = db.prepare("SELECT pageno FROM dbstat WHERE name='t' AND pagetype='leaf' ORDER BY pageno").all().map(r => r.pageno);
console.log('table leaf pages', leaves.length);
db.close();
// ncell1 on every table leaf but the first: set the 2-byte cell count at offset 3 to 1
const buf = readFileSync(src);
for (const p of leaves.slice(1)) { const off = (p - 1) * 4096; buf.writeUInt16BE(1, off + 3); }
writeFileSync(src, buf);
const q = (d, sql) => { try { return d.prepare(sql).all().map(r => Object.values(r)[0]); } catch (e) { return ['ERR ' + e.code + ' ' + e.message]; } };
db = new Database(src);
console.log('SRC quick_check', q(db, 'PRAGMA quick_check'));
console.log('SRC integrity_check', q(db, 'PRAGMA integrity_check'));
console.log('SRC count(*) (index-answered)', q(db, 'SELECT count(*) FROM t'));
console.log('SRC count NOT INDEXED', q(db, 'SELECT count(*) FROM t NOT INDEXED'));
try { db.exec(`VACUUM INTO '${snap}'`); console.log('VACUUM INTO ok'); } catch (e) { console.log('VACUUM INTO ERR', e.code, e.message); }
db.close();
db = new Database(snap);
console.log('SNAP quick_check', q(db, 'PRAGMA quick_check'));
console.log('SNAP integrity_check', q(db, 'PRAGMA integrity_check'));
console.log('SNAP count(*)', q(db, 'SELECT count(*) FROM t'), 'NOT INDEXED', q(db, 'SELECT count(*) FROM t NOT INDEXED'));
db.close();
copyFileSync(snap, fixed);
db = new Database(fixed);
db.exec('REINDEX');
console.log('SNAP+REINDEX integrity_check', q(db, 'PRAGMA integrity_check'), 'count', q(db, 'SELECT count(*) FROM t'));
db.close();
// Control: an index that lost entries (the other direction): delete index cells via ncell1 on an index leaf
rmSync(src, { force: true });
db = new Database(src);
db.exec("PRAGMA page_size=4096; CREATE TABLE t(id INTEGER PRIMARY KEY, epoch INTEGER, body TEXT); CREATE INDEX t_epoch ON t(epoch);");
db.transaction(() => { for (let i = 0; i < 2000; i++) ins.run ? db.prepare('INSERT INTO t(epoch, body) VALUES (?, ?)').run(1000 + i, 'y') : 0; })();
const ileaves = db.prepare("SELECT pageno FROM dbstat WHERE name='t_epoch' AND pagetype='leaf' ORDER BY pageno").all().map(r => r.pageno);
db.close();
const b2 = readFileSync(src);
b2.writeUInt16BE(1, (ileaves[1] - 1) * 4096 + 3);
writeFileSync(src, b2);
db = new Database(src);
const ic = q(db, 'PRAGMA integrity_check');
console.log('INDEX-LOST integrity_check', ic.length, 'rows; first 3:', ic.slice(0, 3), 'last:', ic.slice(-1));
const qc = q(db, 'PRAGMA quick_check');
console.log('INDEX-LOST quick_check', qc.length, 'rows; first 3:', qc.slice(0, 3));
db.close();
