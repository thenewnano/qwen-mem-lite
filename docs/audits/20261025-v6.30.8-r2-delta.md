## Findings

### R2-1 · P2 · schema.mjs:1754, 1760, 1796. An opener whose copy another opener's sweep removed fails its open, even when the store is already in place
- **Chain:** opener B's VACUUM INTO finishes. Opener A, for which B's pid is not visible (another PID namespace, the premise of r1 F1), runs a whole move: its first sweep removes B's copy (or its new final sweep does, line 1796), then A links and removes the old files. B's `new Database(copy, { fileMustExist: true })` (or `openSync(copy,'r')` at 1760) throws. Nothing on that path asks `movedElsewhere()`, so B's ensureDb throws although DB_PATH holds the moved store. This breaks contract B.5 (every opener succeeds). No row is lost, and the next open works.
- **Repro:** `scripts/move-probe.mjs <wt> other-moves-after-vacuum` (B's preload spawns A after the real VACUUM INTO; A's preload makes `process.kill(pid,0)` throw ESRCH for other pids).
  - head: B `exit 1 SqliteError: unable to open database file`, A `exit 0`, store holds 5/5 rows, old dir empty.
- **5353ab86:** B exits 0 in this ordering: its reopen makes an empty file, the link gets EEXIST, and B opens A's store. In the reverse ordering, B linking first, 5353ab86 placed the empty store and removed the old files (F1, 0 rows: confirmed above).
- **f3ccd2ff:** no copy, renames only, so this case does not exist there.
- **Assessment:** an accepted trade (fail instead of losing rows). Returning `movedElsewhere()` when the copy is gone would keep both properties. The final sweep that ba781698 adds is a second point where a live opener's copy can be removed.

### R2-2 · P2 · schema.mjs:1735. A data dir that cannot take one more file fails every open, where earlier trees renamed
- **Chain:** `closeSync(openSync(copy, 'wx', 0o600))` sits outside the VACUUM INTO try. An ENOSPC/EDQUOT at create time (inodes used up, or an inode quota) throws out of placeUnhiddenStore and ensureDb, so the v6.30.7 renames never run. That breaks contract B.3 ("the data dir has no room for a copy → renames run") for this form of no room. On one filesystem a rename needs no new inode.
- **Repro:** `scripts/enospc-create.mjs <wt>` (preload: the `wx` open of `.unhidden-move-*` throws ENOSPC).
  - head: exit 1, old store left whole, nothing in the data dir.
- **5353ab86 (code reading, not run):** SQLite's own create inside VACUUM INTO fails, the catch does `return false`, and the rename moves the store.
- **f3ccd2ff:** renames.
- **Note:** a full disk alone rarely triggers this. The data dir's existing directory block takes the entry, so the create needs only a free inode.

### R2-3 · P2 (claim) · lib/db-unusable.mjs:517-519, ba781698 message. "FTS5's docsize table … can tell the two apart" is too general
- **Chain:** docsize is maintained by the triggers and also rewritten by every FTS5 `'rebuild'`. The product runs one on its own: `ensureDbWithWalRecovery`'s FTS-corruption branch calls `rebuildFTS`, which reads the table as it now is. A store whose table lost rows and whose FTS then got rebuilt shows docsize equal to the table count. That is the "index kept a delete's rows" signature.
- **Repro:** `scripts/docsize-shapes.mjs <wt>`, shape C: ncell1 implant, then `rebuildFTS`, then VACUUM INTO → index 410, table 398, docsize 398. Shapes A (410/398/410) and B (420/390/390) confirm the two shapes the message reproduced.
- **Why P2:** the comment records an input to an open decision ("choosing on docsize" was weighed this round). Choosing on docsize alone would call C a delete.
- **Pre-repair trees:** 5353ab86 printed "nothing in the snapshot tells which" (false for A/B, as r1 found). f3ccd2ff has no such check.

### R2-5 · P3 (claim) · schema.mjs:1751-1753. "The switch reads nothing" is the wrong mechanism, and the one file the switch does make is never swept

- **Not reproduced:** a kill forced by a reader's lock lands before the journal exists (the EXCLUSIVE lock is taken first). The window lies inside one statement.
- **Pre-repair trees:** 5353ab86's finally removed `-wal`/`-shm`, never `-journal`, and a kill skips the finally anyway, so nothing changed here. f3ccd2ff: n/a.
