### P1-1: doctor names a snapshot that lost most of its rows, and never checks an older intact one

- **Where:** `lib/db-unusable.mjs:444-449`, where the walk stops at the first `ok`. Also `:463`, and the wording at `:473-476`.
- **Chain:**
  1. A snapshot taken after the store went bad can have the "lost-rows" shape: the table has lost rows that its indexes still list.
  2. After REINDEX it is consistent, so `checkSnapshot` returns `ok` with `listed > observations`.
  3. `dbUnusableRemedy` stops at that first `ok`, newest first. The older intact snapshot is never checked or mentioned.
  4. The restore command copies the lossy snapshot. The sentence calls it a snapshot that "restores cleanly", with "M fewer than its own index lists" appended.
- **How common:** the release's own `docs/audits/20261023-v6.30.6-d558-a3-measurements.md` counts 73 of 605 passing snapshots in this shape, with extremes of 1,495 → 21 and 1,195 → 15. That measurement took one snapshot per sample, so it never asked whether an older snapshot held more.
- **The intact copy does not stay on disk:**
  - After the restore, `pruneSnapshots` in `lib/db-backup.mjs` keeps only the newest 3 per tag, with no age grace.
  - `enforceBackupBudget` evicts any snapshot older than 7 days once the 256 MB budget is exceeded, and one large snapshot exceeds it.
  - So later snapshots of the lossy store can unlink the intact older one. I read this mechanism in the code; I did not run it.
- **Grading:** it follows the stated contract, so it is a design defect. By the rubric it is P1: a user who follows the output ends up with less data than was recoverable.
- **Repro:** `. ./env.sh lostrows && WT=$WT node lostrows.mjs`. The older snapshot holds 400 intact observations; the newest held 410 and was given the lost-rows damage.
  ```
  older alone: {"verdict":"ok","withLog":false,"observations":400}
  restore
   The newest of the 2 backup snapshot(s) beside the database restores cleanly: … holds 3 observation(s), 407 fewer than its own index lists.
   cp …/claude-mem-lite.db.pre-maintain-2026-10-20T00-00-00-000Z-1-2.bak …/claude-mem-lite.db
  ```

### P1-2: the plugin's SessionStart `scripts/setup.sh` still moves a git clone at `~/claude-mem-lite`

- **Where:** `scripts/setup.sh:128-129`, unchanged in the range:
  ```bash
  if [[ -d "$OLD_UNHIDDEN_DIR" && ! -d "$CODE_DIR" ]]; then
    mv "$OLD_UNHIDDEN_DIR" "$CODE_DIR"
  ```
- **Chain:**
  1. In the plugin shape, `hooks/hooks.json` runs `setup.sh` at SessionStart before `hook.mjs`.
  2. `~/.claude-mem-lite` is missing on the first session after a plugin install, or after a user removes it. In that case any directory at `~/claude-mem-lite` is moved whole into its place: a README method 3 clone, or a pre-v0.5 data dir.
  3. The product then writes `runtime/`, and later its store, inside the clone.
- **What it contradicts:** the release contract ("a git clone at ~/claude-mem-lite is never moved"), README lines 216-218 ("Nothing else is moved") and the CHANGELOG. D#561 fixed `schema.mjs` and `install.mjs` and missed this parallel path. `tests/legacy-dir-migration.test.mjs` never runs `setup.sh`.
- **How bytes get destroyed:** the documented uninstall deletes the moved clone, uncommitted work included. README 997 says `uninstall --purge` "Deletes ~/.claude-mem-lite/ and all data"; README 1006 says `rm -rf ~/.claude-mem-lite/`. `syncDataDirFromCache` does not overwrite the clone, because `isDevMode()` sees its `.git`.
- **Not a regression:** 6.30.5 has the same script. Only the release text changed.
- **Repro:** run `CLAUDE_PLUGIN_ROOT=<archive of 1b12ffe2> bash <root>/scripts/setup.sh` with a `git init` clone at `~/claude-mem-lite` holding an uncommitted `MY-UNCOMMITTED-NOTES.txt`:
  ```

  ls -a $HOME → . .. .claude-mem-lite
  ls -a ~/.claude-mem-lite → .git MY-UNCOMMITTED-NOTES.txt hook.mjs package.json runtime
  ```

### P2-1: a snapshot from a newer claude-mem-lite counts as "does not open", and doctor names an older one

- **Where:** `lib/snapshot-probe.mjs:54-55`, then `lib/db-unusable.mjs:256` and `:447`.
- **Chain:**
  1. The probe's `ensureDb` throws `CLAUDE_MEM_SCHEMA_TOO_NEW` (`schema.mjs:505`).
  2. The check returns `bad('open')`.
  3. The walk names an older snapshot. If nothing passes, it falls back to the set-aside command.
  4. The reason is never shown, so the user does not learn that updating would make the newer snapshot restorable.
- **Trigger:** doctor run from an older code home than the one that wrote the store, such as a stale global npm install, or a downgrade.
- **Grading:** the outcome matches the P1 wording. I graded it P2 because it needs version skew, and the newer snapshot stays on disk.
- **Repro:** `. ./env.sh skew && WT=$WT node skew.mjs`. The newer snapshot holds 500 observations; the older one holds 5.
  ```

  restore … the newest one does not restore cleanly (1 does not open); the next one does: … holds 5 observation(s).
  ```

### P2-2: install's own claude-mem backup stops the pre-v0.5 store from moving

This is a regression in outcome against 6.30.5.

- **Where:** `schema.mjs:1673-1674`. The `storeFile` prefix also matches `claude-mem-lite.db.legacy-backup-<ts>`, which `install.mjs:192` writes (called from `:1632`).
- **Who is affected:** pre-v0.5 `install.mjs` copied `~/.claude-mem/claude-mem.db` into `~/claude-mem-lite/` and left the original in place (b71d292b^, install.mjs:427-444). So a pre-v0.5 user who came from claude-mem has both directories.
- **Chain:**
  1. `install` moves the claude-mem DB into the data dir under its `legacy-backup` name.
  2. At the first open, the migration sees that name, returns, and creates a fresh empty store, with no notice.
  3. The pre-v0.5 store stays in `~/claude-mem-lite`, which README 223 tells users to `rm -rf` "after confirming".
- **Comparison:** on 6.30.5 the same sequence moved the store (`Total: 77 observations`), but it also deleted the code dir and the claude-mem backup, which is the D#561 bug. 6.30.6 deletes nothing and no longer moves the store.
- **Repro:** `. ./env.sh legacy1 && unset CLAUDE_MEM_DIR && WT=$WT node legacy-setup.mjs`, then `PATH=<stub>:$PATH CLAUDE_MEM_SKIP_REPOS=1 node $WT/install.mjs install --dev` (exit 0). After that, `node ~/.claude-mem-lite/cli.mjs stats` prints `Total: 0 observations`, while `~/claude-mem-lite/claude-mem-lite.db` still holds its 77 rows.

### P2-3: a read-only snapshot (mode 0444) is rejected, though restoring it gives a working store

- **Where:**
  - `lib/db-unusable.mjs:224`: `copyFileSync` copies the 0444 mode to the private copy.
  - `schema.mjs:1711-1714`: the store is opened before the `chmodSync(…, 0o600)`, so the first open is read-only.
  - `lib/db-unusable.mjs:256`: the result becomes `bad('open')`.
- **Chain:** the first open fails with `SQLITE_READONLY`. `ensureDbWithWalRecovery` does not retry, because this is not a corruption error. So the snapshot is skipped, and the user may be left with only the set-aside command.
- **Why it is restorable:** after a real `cp`, the first `fts-check rebuild` fails with `attempt to write a readonly database` (exit 1), but by then the chmod has run. The second run exits 0, with `integrity_check` ok and 25 observations.
- **Trigger:** a hand-made snapshot that was chmodded, or one restored from read-only media. Product snapshots are 0644. The outcome matches the P1 wording; graded P2 for the trigger.
- **Repro:** `. ./env.sh ro && WT=$WT node ro.mjs` →
  ```
  {"verdict":"bad","why":"open","reason":"SQLITE_READONLY"}
  set-aside  None of the 1 backup snapshot(s) … restores cleanly (1 does not open).
  ```

### P3 findings

- **P3-1. Killing doctor orphans the probe and leaves a full copy** (`lib/db-unusable.mjs:227-232`).
  - On SIGTERM or SIGKILL to doctor, the probe child was reparented to pid 1 and ran to completion with no timeout. Each run left `.snapshot-check-<pid>-*`, 2.1 GB each.
  - On SIGINT to the process group (Ctrl-C), both died and the dir stayed.
  - The next doctor's sweep removed all three dirs (3 → 0), but it can delete files under a probe that is still running.
  - Reasoned, not reproduced: the probe inherits the real HOME. Its retry path runs `migrateUnhiddenStore()` whenever the private `DB_PATH` is missing. A sweep landing between two open attempts could move a `~/claude-mem-lite/` store into a dir that the next sweep deletes.
- **P3-2. doctor is silent during the check** (`install.mjs:3187`). With one 2.16 GB snapshot, `✗ Database` printed at 184 ms and the remedy at 28,810 ms, with nothing in between. A Ctrl-C in that window leads to P3-1.
- **P3-3. The check's own longer path is read as snapshot damage** (`lib/db-unusable.mjs:218`, `:256`).
  - The private copy's path is 32 characters longer than the store's.
  - With a 470-character data dir, the live store opens (`stats` shows 9 observations), but an intact snapshot checks as `bad/open SQLITE_CANTOPEN`, so doctor gives the set-aside command.
  - The trigger (a path that long) is contrived.
- **P3-4. The check writes outside its private dir.**
  - SQLite sort temp files go to `$TMPDIR` and are unlinked at once. I saw `…/tmp/etilqs_… (deleted)` held open, at least 7.6 MB at 0.2 s polling, so that is a lower bound.
  - A full `/tmp` would report as `SQLITE_FULL` against the snapshot's path, which points the user at the wrong disk.
  - The probe wrote nothing else: `find -newer` over HOME, TMPDIR and the data dir listed only the DB.
- **P3-5. A partial run strands the user.**
  - If the named snapshot is gone when the user runs the command, the `mv` steps succeed and `cp` fails.
  - The next doctor run says `⚠ Database: not found (will be created)` and mentions neither the kept file nor the snapshots.
  - Re-running the printed command exits 1 with no message, even after the snapshot is back.
  - If only the last step (`fts-check rebuild`) fails, the indexes the check relied on are never rebuilt, and doctor reports the store healthy (D#562).
  - Minor: the `touch` rewrites the kept `-wal`'s mtime.
- **P3-6. In a tree mixed by a killed update, doctor points at itself.** With the update killed after `lib/db-unusable.mjs` (SOURCE_FILES index 121), the 6.30.5 `install.mjs` prints: "2 backup snapshot(s) exist … `CLAUDE_MEM_DIR=… node …/cli.mjs doctor` checks which one restores cleanly before it gives a command." That is the same doctor, and nothing says the update is incomplete.
- **P3-7. The doctor command in both notices no longer runs in PowerShell, cmd or csh/tcsh** (`lib/db-unusable.mjs:327-329`).
  - `doctorCommand` always prefixes `CLAUDE_MEM_DIR=<dir>`, even for the default dir, and those shells cannot run that prefix. 6.30.5 printed a plain `node <cli> doctor`.
  - README lists Windows as supported (not CI-covered).
  - The restore command's last step carries the same prefix.
- **P3-8. The legacy-dir migration is no longer atomic** (`schema.mjs:1676-1678`).
  - It moves the DB, the `-wal` and the `-shm` in three separate renames; 6.30.5 used one directory rename.
  - A kill between them leaves the DB moved without its WAL.
  - At session start the hook and the MCP server open the store together. A concurrent open inside that microsecond window could have its new `-wal`/`-shm` replaced by the legacy ones. Reasoned, not reproduced.
- **P3-9. The "empty" rule counts only observations.** A snapshot with prompts and summaries but no observations is skipped. The set-aside sentence then says "None … restores cleanly (1 holds no observations)", although that snapshot does restore cleanly.

### Answers to your questions

1. **Does doctor name a bad snapshot, or skip a good one?**
   - **Names a bad one:** I found no case where the named snapshot fails after the printed command. These were all consistent between the check and the restore:
     - 8 truncated snapshots, all `bad/open SQLITE_CORRUPT`, never IOERR;
     - a covering index with a damaged page (`bad/rebuild`; REINDEX fails the same way in the restore);
     - a 2.16 GB snapshot (`ok`, 700,000 observations).
   - **Skips a good one:** yes, see P1-1, P2-1, P2-3 and P3-3.
2. **Can a command or an automatic path destroy, move or overwrite user bytes?**
   - **The printed commands:** quoting held for a data dir named `` da ta'$(touch PWNED)`id` ``. In both dash and bash the restore exited 0, PWNED was not created, and a second run exited 1 with nothing changed.
   - **Automatic paths:**
     - `setup.sh` moves a clone (P1-2).
     - The open's migration deletes nothing, but it is not atomic (P3-8) and is blocked by the claude-mem backup (P2-2).
     - The sweep touches only directories with exactly its own naming pattern, never links.
3. **Does the check write outside its dir, leave it behind, or misclassify its own failures?**
   - **Writes outside:** SQLite temp files in TMPDIR (P3-4).
   - **Leaves it behind:** after SIGINT, SIGTERM or SIGKILL, until the next doctor run (P3-1).
   - **Misclassifies:** CANTOPEN (P3-3) and READONLY (P2-3) are treated as snapshot damage.
   - **Pid reuse:** handled by the 24-hour age limit, as designed.
4. **Neighbouring paths against v6.30.5:**
   - **`fts-check rebuild` on a 2.16 GB store:** runs alternated back to back. 6.30.5 took 18,734 and 18,783 ms; 6.30.6 took 20,203 and 20,217 ms, about 1.45 s (7.8%) more.
   - **`fts-check rebuild` under a held write lock:** both versions exit 1 with `database is locked`.
   - **doctor on a healthy store:** identical output apart from version strings. The sweep removed a planted directory with a dead pid.
   - **SessionStart notice:** with snapshots it prints no command and a doctor command carrying the data dir. Without snapshots it prints the set-aside command.
   - **Mixed tree:** loads at all 169 split points; the behavioural problem is P3-6.
   - **`install --dev`:** exit 0 on both versions.
   - **A real pre-v0.5 store:** it still moves in the plain case (per the suite), but not when the claude-mem backup is present (P2-2).
5. **Cost:** the walk checks one snapshot at a time. Each check has a 10-minute timeout, which does not cover the copy.

   | Snapshot | Check time | Peak size of the private dir |
   |---|---|---|
   | 180 MB, 60,000 observations | 2,163 ms | 241 MB (1.34× the snapshot) |
   | 2.16 GB, 700,000 observations | 28,441 ms | 2.86 GB (1.33× the snapshot) |

   The 2.16 GB check also used at least 7.6 MB of SQLite temp files in TMPDIR, which is a lower bound.
