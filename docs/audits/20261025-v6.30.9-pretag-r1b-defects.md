## 发现

### P1-1　页损坏时 doctor / fts-check rebuild「什么都不写」不成立：读写句柄关闭时把 WAL 检查点进主文件，主文件里能单独读出的好行被毁掉

- 位置：install.mjs:3172 和 install.mjs:3234（两处 `const rwDb = new Database(DB_PATH);`）。schema.mjs:1988 起的 checkStorePages 在这个读写句柄上读库，调用方随后关闭句柄。和这个说法冲突的文字：README.md:964 写 "On damaged pages it writes nothing"，README.md:657 写 fts-check rebuild "writes nothing when they are damaged"；commit 2b8807e0 写 "Damaged pages: a failure with the copy command, nothing written"；D#592 必须满足项 (1) 是 "never write when any line is page-level"。
- 出了什么问题：一个读写连接只要读过库，关闭时就会做 checkpoint，并删除或清空 -wal。损坏在 WAL 帧里的时候，这次 checkpoint 把坏帧写进主文件，覆盖掉主文件里原本完好的页。doctor 自己打印的建议是 "copy the data directory before anything writes to it again"，可它在打印这句之前已经写过了，用户照做时复制到的是写坏以后的状态。只读句柄不会这样（见下面的单步隔离）。
- 影响谁：WAL 里有未检查点的坏帧、又在 session 写入之前先跑了 doctor 或 `fts-check rebuild` 的库，正好是建议所针对的情形（关掉所有 session 再处理）。v6.30.8 的 FTS 步骤也开读写句柄，机制相同，所以这不是回归。但这次改动新写下的保证和 README 文字不成立，新增的完整性步骤又多开了一次读写句柄。没有 observations_fts 的库，在 v6.30.8 上 FTS 步骤不开读写句柄，现在完整性步骤会开，这一点是新增的写入。

### P1-2　库或快照 ≥ 2 GiB 时页检查永远失败（"Out of memory"）：所有重建路径都拒绝，好的快照被判成 bad，doctor 改为建议放弃快照

- 位置：schema.mjs:2006 `const image = db.serialize();`。sqlite3_serialize 用一次 sqlite3_malloc64 申请整个库的大小，而 SQLITE_MAX_ALLOCATION_SIZE 是 2147483391（node_modules/better-sqlite3/deps/sqlite3/sqlite3.c:14734）。超出时 better-sqlite3 抛 `Error("Out of memory")`，这个错误没有 code，于是 schema.mjs:2046 判 `unchecked`。schema.mjs:2077 把 code 记成 null；lib/db-unusable.mjs:196 的 CHECK_OWN_CODE_RE 不认识 null，lib/db-unusable.mjs:303 就判成 `bad('rebuild')`；lib/db-unusable.mjs:524 只在 ok/unchecked 时停下，bad 的快照被跳过。
- 出了什么问题（和 v6.30.8 比是回归）：
  1. doctor：每次运行都输出 "⚠ Database integrity: not checked — Out of memory"。机器上还有 13 GB 空闲内存，这个措辞会误导用户。只坏 FTS 索引时，v6.30.8 会重建修好，候选给出 "✗ FTS5 rebuild: not run — … could not be checked first (Out of memory)"，问题多算一个。
  2. `fts-check rebuild`：v6.30.8 exit 0 并修好；候选 exit 1，什么都不做。
  3. 打开库时 FTS 分支的自愈（schema.mjs:1881）被拒绝。
  4. 快照检查：一个完好的 2.3 GB 快照，v6.30.8 判 `ok`（240 条 observation），候选判 `bad / why: rebuild`。库打不开时，doctor 不再给恢复命令，改说 "None of the 1 backup snapshot(s) … restores cleanly (1 fails the index rebuild)"，并给出把坏文件挪开、下次 session 新建空库的命令。
- 影响谁：库文件或备份快照 ≥ 2 GiB 的用户。阈值没有写进任何文档；db-unusable 的注释还把「第一次尝试读不了 2 GiB 以上的文件」列为它被撤回的原因之一。
- 复现（每项 1 次，结果稳定；建库：`node $B/scripts/e3-make-big.mjs $B/big2 2.1`）：
  ```
  node $B/scripts/e3-check.mjs <2.3GB 副本> pages
  → {"what":"pages","ms":302,"maxRssMB":76,"r":{"state":"unchecked",...,"error":"Out of memory","code":null}}
  doctor（只坏 FTS 的 2.3 GB 库，out/e3-doctor-big2fts-*.txt）：
    v6308: ✓ FTS5 rebuilt: observations_fts, session_summaries_fts, user_prompts_fts, events_fts
    wt:    ✗ FTS5 rebuild: not run — the database's pages could not be checked first (Out of memory)

  checkSnapshot（out/e3-snapshot.txt）：

    v6308 {"verdict":"ok","observations":240,"otherRows":0}
  doctor 恢复建议（坏主文件 + 2.3 GB 好快照，out/snap2-doctor-*.txt）：
    wt:    None of the 1 backup snapshot(s) beside the database restores cleanly (1 fails the index rebuild). ... set the broken file aside so a fresh store is created ...
  ```

  打开库时的分支（按 tests/store-pages-gate.test.mjs 的做法注入一次 SQLITE_CORRUPT_VTAB，`scripts/e3-opener.mjs`）：wt 打印 "FTS rebuild reported: not rebuilt: … (Out of memory)"，v6308 正常重建。
- 一个附带缺陷，不限于 2 GiB：页检查 `unchecked`（任何没有 code 的失败，或者不属于 FULL/IOERR/CANTOPEN 的 code，比如 SQLITE_NOMEM）在快照检查里都会被判成 `bad`，而不是 `unchecked`。

### P2-1　FTS5 'optimize' 和 rebuild 是同一个「先释放页再分配页」的机制，没有任何闸门，会无人值守地覆盖行

### P3-3　措辞和实际状态不符（三处）

- schema.mjs:1894：重建被拒以后，打开库仍然打印 "DB recovered after FTS rebuild"（out 见 e3-opener 的输出：先是 "FTS rebuild reported: not rebuilt: … pages are damaged …"，接着是 "DB recovered after FTS rebuild"）。
- lib/db-unusable.mjs:131：查询时报 FTS 损坏的补救文字仍然说 "the stored observations are intact. Rebuild it losslessly with `fts-check rebuild`"。在页损坏库上，用户照做后得到的是 "Not rebuilt: the database's pages are damaged"（复现 1 次：`cli.mjs search narrative` 然后 `cli.mjs fts-check rebuild`，在 fx/xl-search 上）。

### P3-4　D#592 的必须满足项 (3)、(5) 没有按原文实现

- (3)：schema.mjs:2124 只在 BUSY/LOCKED 时停下，碰到 FULL/NOMEM/IOERR 会继续跑后面的语句。现在每条语句各自 autocommit，(3) 前提里说的「事务被结束」在现有调用方里不成立，所以没有半途的状态。我没能造出「第一条 FTS 语句就 SQLITE_FULL」：max_page_count 复现时只有 REINDEX 报 full。所以这一条是读代码得出的。
- (5)：install.mjs:3254 在完整性检查失败、但重建碰到锁时只给 ⚠，不计入问题数。commit 说这是有意的，但和 (5) "a failed check the rebuild could not act on must be an issue" 的字面意思冲突；此时 DB stats 仍是 ✓，计数可能来自坏索引。

### P3-5　完整性检查失败、但原因不是重建能修的（CHECK、NOT NULL、行内容损坏）时，doctor 每次运行都重建全部索引

- 位置：schema.mjs:2200 在任何失败时都调用 rebuildIndexes。回归集里有 52 个库以 ✗ "not repaired" 结束，细节有 "after the rebuild: CHECK constraint failed in observations"、"NULL value in …" 等，没有给任何下一步。每次重跑都会重写全部 FTS 并 REINDEX。成本：在 875 MB（834 MiB）、28 万条 observation 的库上，doctor 用了 17 s；一个 busy_timeout 500 ms、每 50 ms 写一次的并发写者，301 次写里 17 次得到 SQLITE_BUSY（out/hook-writer-during-doctor.txt）。D#592 (7) 已经提到持锁问题，这次改动没有缓解。

### P3-7　成本：每次 doctor 都把整个库读进内存，重建路径占用约两倍库大小

都是本机测的（Linux，12 核）。数字带基线：
- 557 MB 库：doctor 1.4–2.1 s → 3.3 s，峰值 RSS 80–88 MB → 635 MB（3 次）。
- 875 MB、行很多的库：3.5–5.1 s → 8.0 s，87 MB → 947 MB（2 次）。其中 checkStorePages 1.2 s，checkStoreIntegrity 4.4 s。
- 重建路径：同一个 875 MB 的库峰值 RSS 1,798 MB，没走重建的路径是 937 MB。checkStorePages 在这条路径上跑两次，推断是两次 serialize 的缓冲区同时存活（没单独证明）。
- hook 路径，打开库时的 FTS 分支：1.2 GB 的库增加 1.17 s、1.25 GB RSS（v6.30.8：8 ms / 60 MB）。
- 代码注释写了「577 MB 库多占约 577 MB」，但没写重建路径会到两倍，也没写 2 GiB 上限（见 P1-2）。
