## Findings

### P1-1 — a disk with room for the check's copy and not for its rebuild makes doctor pass over a restorable snapshot and name an older one

`lib/snapshot-probe.mjs:26-29` returns `ftsErrors`; `lib/db-unusable.mjs:229-240` never reads it. `rebuildFTS`
(`schema.mjs`, the per-table `catch (e) { errors.push(...) }`) catches every error, SQLITE_FULL and SQLITE_IOERR included, so
`CHECK_DISK_CODE_RE` (meant to turn the check's own disk faults into `unchecked`) never sees a fault that happens during the
rebuild. The chain: the copy fits → the rebuild's WAL hits ENOSPC → SQLITE_FULL swallowed → the index stays damaged →
`integrity_check` fails → verdict `bad/integrity` → the walk goes on to an older snapshot whose index is intact (its rebuild
fails the same way, leaves the index as it was, and passes) → that one is named.

Reproduce: `~/.cache/tmp/rv-6306-defects/scripts/repro-p1-rebuild-full.sh`. It builds a 200,000-observation snapshot whose search index
is damaged (1 h old) and a sound 150,000-observation one (20 days old), then runs doctor twice: once with no limit, and once
with an LD_PRELOAD shim that makes writes fail with ENOSPC once a `-wal` under a `/.snapshot-check-` directory passes 8 MB.
The shim models a disk whose free space is between one copy and the copy plus the rebuild's WAL. Output:

```
== roomy
  The newest of the 2 backup snapshot(s) beside the database restores cleanly: ... holds 200000 observation(s). => cp .../claude-mem-lite.db.pre-delete-2026-10-22T10-00-00-000Z-1-0.bak
== capped
  Of the 2 backup snapshot(s) beside the database, the newest one does not restore cleanly (1 fails the integrity check); the next one does: ... holds 150000 observation(s). => cp .../claude-mem-lite.db.pre-delete-2026-10-01T10-00-00-000Z-1-0.bak
```

The probe's own line under the same cap (copied into a `.snapshot-check-manual-*` dir, `snapshot-probe.mjs` run by hand):

```
200k-fts: {"opened":true,"integrity":"fts5: corruption found reading blob 1511828488198 from table \"observations_fts\"","observations":200000,"ftsErrors":["observations_fts: database or disk is full"]}
150k:     {"opened":true,"integrity":"ok","observations":150000,"ftsErrors":["observations_fts: database or disk is full"]}
```

How a user gets here: a data-dir disk whose free space is between S and about 1.3 S, where S is the newest snapshot's size
(the measured peak is 1.29-1.32 S, see Cost), the newest snapshot's search index is damaged (the D#558 corpus had 136 of 336
restorable snapshots in this state), and an older snapshot's index is intact. If the user does what the output says, they
restore 150,000 observations when the newest snapshot, which doctor calls not restorable, holds 200,000. The newer `.bak` is
still on disk, but doctor has told them it fails. Two more things:
- The sentence says the named snapshot was "restored and reindexed the way the command does it", but its reindex failed too
  (`ftsErrors` above). The printed command's `fts-check rebuild` would exit 1 on the same disk.
- The CHANGELOG says "when it cannot check a snapshot, doctor says why and gives no command". In this window it gives a
  command for another snapshot.
The same swallow catches SQLITE_IOERR during the rebuild (a failing disk under the copy) and real SQLITE_NOMEM.

### P2-1 — a killed check leaves a full copy of the snapshot in the data dir, and once the store is healthy nothing ever removes it

`lib/db-unusable.mjs:203` creates the private dir in the data dir. Its removal is the `finally` at `:243-249`, which a signal
skips. The only other removal is `sweepSnapshotChecks`, called at `:379`. That call runs only on a broken-store doctor walk
with at least one non-empty snapshot, and only for dirs older than 20 min (`STALE_CHECK_MS`, `:161`, `:273`).

`scripts/killmid.mjs <case> <signal> <doctor|group>` (134 MiB snapshot):

```
SIGTERM to doctor:   residue [.snapshot-check-4130571-QP1uin [claude-mem-lite.db]]   (the probe kept running, orphaned)
SIGINT to the group: residue [.snapshot-check-4130620-WSRQIx [claude-mem-lite.db,claude-mem-lite.db-shm,claude-mem-lite.db-wal]]
SIGKILL to doctor:   residue [.snapshot-check-4130667-JvGzws [claude-mem-lite.db]]
```

How a user gets here: press Ctrl-C during the check, run doctor again within 20 min (the leftover dir is too young to sweep), then run
the printed restore. `scripts/repro-p2-residue.sh`:

```
RUN1 exit=0 out=[mem] Successfully rebuilt: ...      RESULT obs= 200000 ic= ok
after a doctor on the healthy store, residue aged 3 h:
135M  .../p2-residue/data/.snapshot-check-30794-Dx3Pcl
```

What makes Ctrl-C likely: during the checks the human face prints `✗ Database: …` and then nothing (26.5 s for one 1.3 GiB
snapshot, see Cost). The contract says the check leaves no files in the data directory. Also: after SIGTERM to doctor alone
(for example a `timeout` wrapper), the orphaned probe has no timeout, because the 10 min limit is enforced by the parent's
`spawnSync`. A leftover dir also doubles the space the next check needs.

### P2-2 — with the data dir moved only in Claude Code's env, the SessionStart notice sends the user to a doctor that looks somewhere else

`lib/db-unusable.mjs:376` (the hook's `unchecked` note) and the "re-checks" line in `formatDbUnusableNotice` give
`node <cli> doctor` without the data dir. 6.30.5's notice carried the restore command with absolute paths. 6.30.6 removes
it, as the contract requires, and hands off to a doctor invocation that does not name the store. The restore command
itself does name it (`CLAUDE_MEM_DIR=<dir> … fts-check rebuild`). `scripts/repro-p2-reloc.sh`:

```
   .../p2-reloc/reloc-data/claude-mem-lite.db exists but SQLite does not recognise it as a database.
   1 backup snapshot(s) exist beside the database. `node /home/ai/.cache/cml-review-6306/cli.mjs doctor` checks which one restores cleanly before it gives a command.
-- that doctor, from a shell without CLAUDE_MEM_DIR:
  ⚠ Database: not found (will be created)
```

How a user gets here: `CLAUDE_MEM_DIR` set in settings.json `env` (or a launcher) and not in their login shell. The result
is a ⚠ that reads as harmless, and no remedy. 6.30.5's notice, same fixture: `rm -f …-wal …-shm && cp …a.bak …db`.

### P2-3 — after a kept file is moved back, every printed command stops silently

`lib/db-unusable.mjs:325-328`: the kept name comes from the broken file's mtime, and the first two steps are `test ! -e`
guards that print nothing when they stop the chain. `mv` keeps the mtime. So a user who moves `…corrupt-<t>` back to retry
something gets the same `<t>` from every later doctor run, and the `-wal` guard stops the command every time, with exit 1 and
no message. `scripts/repro-p2-moveback.sh`:

```
RUN1 exit=0      LS1 claude-mem-lite.db.corrupt-2026-10-23T19-56-13-068Z:7 claude-mem-lite.db.corrupt-2026-10-23T19-56-13-068Z-wal:8
(mv the kept file back; doctor prints the identical command)
LS0 claude-mem-lite.db:7 claude-mem-lite.db.corrupt-2026-10-23T19-56-13-068Z-wal:8
RUN1 exit=1 out=          LS1 (unchanged)
```

No data is at risk (it fails closed), but the remedy can never succeed and doctor does not say why. The same silent stop
greets anyone re-running a restore whose last step (`fts-check rebuild`) failed, for example `node` not on the shell's PATH
(exit 127): the files were already moved, so the second run stops at the guard and the reindex never happens.

### P3-1 — a private copy that disappears reads as an empty snapshot

`lib/snapshot-probe.mjs:36`: `ensureDbWithWalRecovery()` creates a store when none exists, so a probe whose copy is gone
reports a fresh empty store. The snapshot is then passed over as "holds no observations" and the walk goes on to an older one.
Reproduce with a probe wrapper that removes `$CLAUDE_MEM_DIR` and then runs the real probe (`scripts/vanish-probe.mjs`):
`{"verdict":"empty","withLog":false,"observations":0}` for a 150,000-observation snapshot. The sweep in a second doctor
can cause this: a check dir's mtime is set when the copy file is created, so a copy that takes more than 20 min (a large
store on slow or network storage) is swept while it runs. So can any outside removal.

### P3-2 — the EACCES reason names the snapshot when the data dir is what cannot be written

Data dir `chmod 555`, snapshot readable: `could not be checked (EACCES): <snapshot path>`. That is the same text as an
unreadable snapshot, but the operation that failed was `mkdtempSync` in the data dir (`:203`, reason from `:242`). The same
doctor run also prints `✗ Data directory: … can be read but not written. Fix: chmod u+rwx …`, so the user does get the fix.
6.30.5 printed a restore command here.

### P3-3 — the probe-failure reason is a source location, not the error

`lib/db-unusable.mjs:224` keeps the first stderr line, which for any uncaught Node error is a location:
`probe exited 1: node:internal/modules/esm/resolve:272` (missing import) and
`probe exited 1: file:///…/throw-probe.mjs:1` (throw). The real probe catches everything after its imports, so only an
import-time failure reaches this.

### P3-4 — the schema-family SessionStart note promises a command that doctor never gives

`lib/db-unusable.mjs:376-377` returns the same note for kind `schema`: "… `doctor` checks which one restores cleanly before it
gives a command." For this family doctor gives no command by design (output: "SQLite cannot read the database's schema. The
newest … restores cleanly … It is <path>. Restoring it replaces the database file, so copy the broken file aside first.").

### P3-5 — a swap killed between `lib/db-unusable.mjs` (#121) and `install.mjs` (#150) prints a restore sentence with an empty command

The new kind `unchecked` falls through to 6.30.5's last branch (`v6305/install.mjs:491`). `scripts/mixed.sh 121` (and 122):
`Restore the newest of 1 backup snapshot(s) once every Claude Code session is closed:  — move the broken file aside first if you want to keep it for inspection.`
It cannot be run, and it lasts until the update replays. At split 150 the output is correct. The new `source-files.mjs`
comment says a kill between `db-unusable.mjs` and the probe leaves the check reporting "unchecked". At that split
`install.mjs` is still 6.30.5's and never calls the check, so that state is not reachable.

### P3-6 — fish reads backslashes inside the single quotes `shellWord` emits

Per the fish docs (fishshell.com/docs/current/language.html, "Quotes"): "The only meaningful escape sequences in single
quotes are `\'` … and `\\`". In fish, a data-dir path containing `\\` becomes a different path in every word of the command,
and one containing `\'` is a syntax error, which fails safe. I did not run this: fish is not installed. bash and dash handled
the same paths correctly (below).

### P3-7 — special files named `*.bak`

A directory named `<db>.x.bak` (or a `.bak` symlink to a directory) stops the walk: `could not be checked (EISDIR)`, and an older
sound snapshot is never named. 6.30.5 named it; run here, its `rm -f` ran and `cp` refused with "omitting directory", exit 1, nothing else touched. A FIFO, `/dev/null` or `/dev/zero` symlink
is counted as "1 empty .bak file skipped" (it is not a file). No hang, and nothing was written: the listing was unchanged in
all 7 shapes. A check that times out says `(ETIMEDOUT) … Once that is fixed, run doctor again`, which the user cannot fix.
A store whose check takes over 10 min never gets a command. At the measured rate that is roughly 25-30 GB on this host
(extrapolated, not measured), less on slower disks.

## Answers to the five questions

1. **Named but not sound:** none found. I ran the printed restore end to end and then doctor in bash and dash, on: a 3-snapshot mix
   (index-damaged newest, page-damaged, sound), 4 hostile path families × 2 shells, a schema-v48 snapshot (built from
   `7bc8ba9f^`, migrated by the check: 500 rows, integrity ok after the real restore), and 134 MiB / 1.3 GiB / 150k / 200k
   stores. Every one ended `RESULT … ic= ok` with the observation count the check had printed, and doctor afterwards showed
   `FTS5 integrity: all indexes healthy`. **Rejected but restorable:** yes. P1-1 (a rebuild fault in the check's own
   environment) and P3-1 (vanished copy → empty).
2. **Destroy or overwrite:** none found. bash and dash, data-dir paths with space + `'` + `$HOME` + backticks, `\` and `\\`, a
   backslash before `-`, and a newline. Each ran twice: the first run exit 0 with the broken pair kept, the second exit 1 with the
   listing unchanged. With CLAUDE_MEM_DIR pointing at another store in the shell that ran the command, that store's mtime and
   sha1 were unchanged and the restore went to the doctor-time dir. Session still holding the store: a WAL connection open
   across the file operations, then a new connection writing, then the old one closing. The restored `-wal` stayed
   (49,472 bytes), the new row was visible to a third connection, and integrity was ok after all closed. zsh: not run; by
   reasoning `'\''` never puts `''` inside a quoted string, so RC_QUOTES does not change it. fish: P3-6. Silent guard: P2-3.
3. **Writes outside the private dir:** none seen. A migrating v48 snapshot with CLAUDE_MEM_DEBUG=1, CLAUDE_MEM_CATCH_SAMPLE=1,
   CLAUDE_MEM_RUNTIME_DIR and XDG dirs set: a `find` diff over the whole case dir showed only my own files. 7 special-file
   shapes: listing unchanged. **Left behind:** yes, P2-1. **Misclassified:** P1-1, P3-1, P3-2. **Sweep:** it removes only
   `.snapshot-check-*` entries that `lstat` calls directories (run: a 3 h old symlink `.snapshot-check-999-link` to a directory was left in place and the file in its target kept). It can remove
   a running check's dir only when that check's copy has run for more than 20 min (P3-1).
4. **Neighbouring paths against 6.30.5** (same fixtures run on both trees): an unreadable dir is identical (`not checked — … is not
   accessible`). Empty `.bak` files: reworded, still the set-aside. The schema family names the checked path and still gives no
   command (wording: P3-4). `--json`: the details string equals the human line (`parity true`). Swap order: loads at all 169
   split points; the one mixed state that misreads is P3-5. A relocated data dir regresses (P2-2). Before the check runs,
   doctor's own read-only open creates `<db>-shm` (32,768 bytes) beside a broken DB that has a `-wal`. 6.30.5 does the same,
   so it is not from this change.
5. **Cost** (this host, ext4, so no reflink; `scripts/cost.sh`; peak = summed size of `.snapshot-check-*` sampled every 50 ms):

   | Data dir | doctor wall | peak private bytes |
   |---|---|---|
   | broken DB, no snapshot (set-aside) | 206 ms | 0 |
   | 1 × 134 MiB (200k obs), sound | 3,137 ms | 184,938,224 (1.32 × snapshot) |
   | 5 × 134 MiB, newest 4 page-damaged | 8,557 ms | 184,855,824 (sequential, one at a time) |
   | 1 × 1.30 GiB (2M obs), sound | 26,502 ms | 1,796,235,824 (1.29 × snapshot) |

   For reference, the maintainer's live store is 19.9 MB, with three snapshots of 8.1-15.7 MB (sizes only). The human and
   `--json` faces each run the full walk. The CHANGELOG's "free space beside the snapshots for one copy at a time"
   understates the need by the rebuild's WAL (+29-32 % here), and that gap is P1-1's window.
