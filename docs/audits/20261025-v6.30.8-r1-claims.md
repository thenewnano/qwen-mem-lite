## Findings

**F1 — P1 — FALSE.** The printed sentence at lib/db-unusable.mjs:536 says "…its index still lists rows a delete removed; nothing in the snapshot tells which." The comment at :515-517 and e03270ec's message say "Nothing in a snapshot tells them apart … so doctor chooses by age alone".
- FTS5's per-row record (`observations_fts_docsize`, maintained by the delete triggers on separate pages) separates the two causes. On private copies:
  - Stale index after a normal delete (the Sdel build): count(*) 420, table 390, docsize **390** (agrees with the table).
  - Table that lost rows (an ncell1 implant on an observations leaf, then VACUUM INTO): count(*) 410, table 399, docsize **410** (agrees with the index).
  - The 73 short snapshots of the corpus (`docsize.mjs`): **73/73** have docsize = the index count ≠ the table, the table-loss signature.
- Why P1: this is the deciding premise of the restore-choice design. The sentence tells the user that no evidence exists. In the table-loss shape (the only short shape the corpus has), the default command restores the snapshot that lost the rows (S1/S7: 3 rows, against an older 400).
- Docsize is evidence, not proof: one lost write could hit the FTS pages too. A universal "nothing tells" is still false.

**F2 — P2 — FALSE.** The docblock at lib/db-unusable.mjs:376 says "Every doctor named in a note carries the data directory".
- cliFor (same file) gives the default data dir (CODE_DIR) no `CLAUDE_MEM_DIR=` prefix.
- Rendered with the data dir at `$HOME/.claude-mem-lite`, the SessionStart notice reads "`node …/cli.mjs doctor` checks which one restores cleanly…", and doctor's restore command ends `node …/cli.mjs fts-check rebuild`: neither names the data dir.
- The sentence is new in e03270ec and contradicts cliFor's own docblock.

**F3 — P2 — FALSE as worded.** ebca156b says "Only formatDbUnusableNotice reads a note".
- doctor reads it: install.mjs:510 `if (remedy.kind === 'unknown') return remedy.note;` and :511 for 'schema'. The same is true in v6.30.7's install.mjs:479-480.
- db-unusable.mjs:372-373 itself says "the kind every version's doctor renders as its note".
- True only for the restore remedy's note.

**F4 — P2 — FALSE in a reachable case.** The docblock at install.mjs:187 says "Each copy is written under a private name first, so a killed copy leaves no partial backup". cd50d487 says "a private file a killed copy left is removed first".
- `legacy-kill-probe.mjs`: SIGKILL inside the -wal's copy across filesystems leaves `claude-mem-lite.db.legacy-backup-<ts>` (no -wal backup) plus `.legacy-backup-copy-<pid>-<ts>`.
- The next call returns `{"action":"skip"}` and leaves both, so the backup set stays without its log and the private file is never removed (the skip check at :204 runs before the cleanup at :206).
- The source ~/.claude-mem stays whole, so no row is lost.

**F5 — P2 — FALSE in a reachable case.** 6c28a9bc says "A private copy a killed move left is removed when its process is gone or it is over an hour old."
- `move-kill-probe.mjs`: a SIGKILL right after link(2) leaves `.unhidden-move-<pid>-<hex>`, a second hard link of the live store (link count 2).
- The next open does not sweep it: DB_PATH exists, so migrateUnhiddenStore never runs. The old files also stay.
- Separately, MOVE_COPY_RE (`^\.unhidden-move-(\d+)-[0-9a-f]+$`) does not match the copy's `-wal`, `-shm` or `-journal`, which dc080719's WAL switch can leave on a kill.

**F6 — P3 — FALSE (test comment; the message part was corrected in-range).** dc080719 says the read-only-dir-no-shm case is "a guard for the branch that takes a store SQLite cannot open in place for one another opener moved". The comment at tests/legacy-dir-migration.test.mjs:459, "FAILS IF a store SQLite cannot open in place is taken as moved…", is still there at HEAD. Under mutation S7 that test stays green (claim 10). 5353ab86's message says so but leaves the comment.

**F7 — P3 — count off.** dc080719 gives "about 1 run in 10" and "2 failures in 19 runs before"; the test comment at :383 gives "1 run in 11". My reading at 6c28a9bc: 10/20 (load ≈6–13) and 5/20 (load ≈2.3) = **15/40**. The message and the comment also disagree with each other. The fix holds: 30/30 after.

**F8 — P3 — MISLEADING mechanism.** schema.mjs:1742-1743 says "Closing this handle checkpoints and removes the copy's -wal and -shm." After `pragma journal_mode = WAL` with no read, neither file exists (`walclose-probe.mjs`: none while open, none after close; with a read in between, both appear and close removes them). The end state matches the claim.

**F9 — P3 — stale.** lib/db-unusable.mjs:26 says "the static graph is 10 modules". es-module-lexer closure (`graph.mjs`): 22 modules at f3ccd2ff, **27** at HEAD (the range adds data-paths, schema-skew, record-once, worker-data-dir, cite-recall-path). "Zero package edges" still holds.

**F10 — P3 — MISLEADING.** The SessionStart note (lib/db-unusable.mjs:468-469) says doctor "checks which one restores cleanly before it gives a command". doctor's command can name a snapshot it prints as "restores, but short" (S1, S2, S3, S7, Sdel).

**F11 — P3 — MISLEADING (test helper).** tests/test-helpers.mjs:32 says the 'lost-rows' fixture is "the shape 73 of the D#558 corpus snapshots have". The integrity line is the same, but the fixture's FTS docsize equals the table (3, the stale-index signature; it deletes with the FTS triggers live), while the corpus's 73 have docsize = the index (table loss). Every short-snapshot test models only the stale-index shape.
