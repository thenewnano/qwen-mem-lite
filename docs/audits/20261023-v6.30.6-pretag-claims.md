## P1

### P1-1 (C6) "Kept files are not removed automatically" is false when `~/claude-mem-lite` exists. The first open after the set-aside deletes the kept file, its -wal and every snapshot

**Code:** schema.mjs:1676-1686 (`ensureDb`), unchanged in this range. That path pre-exists in 6.30.5, but this release makes the new claim.

**Mechanism.** `ensureDb` runs `if (existsSync(join(homedir(), 'claude-mem-lite')) && !existsSync(DB_PATH))`. If DB_DIR holds no file ending in `.db`, it runs `rmSync(DB_DIR, { recursive: true, force: true })` and then `renameSync(oldUnhidden, DB_DIR)`. The set-aside command creates exactly that state: no DB_PATH, and nothing ending in `.db` in DB_DIR. The kept file is `…db.corrupt-<time>`, its log is `…-wal`, and the snapshots are `…db.<tag>-<ts>.bak`. The product writes no other `*.db` in the data dir; I grepped the code for `*.db` names.

**Who gets the precondition.** README "Method 3: git clone" says `git clone https://github.com/sdsrss/claude-mem-lite.git && cd claude-mem-lite`. Run from the home directory, that creates exactly `~/claude-mem-lite`.

Reproduced in a sandbox HOME with `~/claude-mem-lite/README.md` and CLAUDE_MEM_DIR unset:
```
before: claude-mem-lite.db (garbage), claude-mem-lite.db-wal, claude-mem-lite.db.pre-delete-2026-10-01T00-00-00-000Z-1-1.bak
6.30.6 doctor remedy: set-aside ("None of the 1 backup snapshot(s) ... restores cleanly (1 fails the integrity check)")
after the printed command (rc 0): claude-mem-lite.db.corrupt-2026-10-23T19-39-32-115Z, ...-wal, the .bak
after one `cli.mjs recent 1` (rc 0, "No recent observations"):
  ~/.claude-mem-lite = README.md + a fresh claude-mem-lite.db; the kept pair and the .bak are gone; ~/claude-mem-lite no longer exists
```
The same run with 6.30.5's set-aside (`mv … db.corrupt`) gives the same result. The CHANGELOG sentence is new, and so is the user's reason to trust it.

Read, not run: with CLAUDE_MEM_DIR unset, the default data dir is also the code home. So the same `rmSync` would also remove the installed code there.

## P2

### P2-1 (C2) The CHANGELOG's account of 6.30.5 leaves out that most rejected snapshots are recoverable without loss by REINDEX. The "still did not open → named again" loop never happened on the 661 snapshots

CHANGELOG.md:13-16.

My variant ruler (tasks/rv/rv.mjs) used the same plants, the same `delete 5 --confirm` and the same snapshots as snapcheck.mjs, with extra arms.

**The 6.30.5 arm.** For each of the 661 snapshots, I ran 6.30.5's own printed restore in a fresh dir with a garbage store, then 6.30.5's `cli.mjs recent 1` and 6.30.5's `install.mjs doctor`:
```
cli recent rc 0 on 661/661 (325/325 of the rejected ones); doctor "Database:" line on 0/661; doctor named the same snapshot again 0/661
restored observation counts on the 325 rejected: 1195 x172, 1495 x117, 241 x32, 1278 x2, 1069, 1076
```
On this population, restoring a rejected snapshot in 6.30.5 gave a store that opens with its rows readable. The loop the CHANGELOG describes does exist, and I reproduced it with a hand-made non-database `.bak`: 6.30.5 doctor names it, the restore runs, and the next doctor names the same file again. But it needs a snapshot that does not open, and none of the 661 product snapshots, all made by VACUUM INTO, is one.

**The REINDEX arm.** I took the 6.30.6 printed restore (which ends with `fts-check rebuild`), then ran `REINDEX` and an FTS rebuild:
```
rejected 325 -> integrity_check ok after REINDEX: 269
  of those 269: observations == population template 196, == the damaged store's own count 192
  first integrity errors among the 269: "wrong # of entries in index ..." / "row N missing from index ..." (all ordinary indexes)
```
So for 269 of 325 rejected snapshots, the damage "put back" is in derived index data that `REINDEX` rebuilds from the tables. That is the same kind of damage the release treats as clean for FTS (C3). In a directory with no other snapshot, 6.30.6 now prints the set-aside instead, which gives a fresh empty store.

Rendered on main21-40 (1195 rows, `row 38 missing from index idx_obs_project_live`):
```
6.30.6: ✗ Database: file is not a database
        None of the 1 backup snapshot(s) beside the database restores cleanly (1 fails the integrity check). ... set the broken file aside so a fresh store is created ...
by hand: cp snapshot + fts-check rebuild -> "row 38 missing from index idx_obs_project_live"; + REINDEX -> ok, obs=1195; doctor: FTS5 healthy
```
This is the shape round-2 P2-4 raised against the first attempt (rejected snapshots presented as damage, without the ones that hold every row). For the defects lens, it is also the P1-1 shape of round 2, carried over from FTS to ordinary indexes: doctor points at an empty store over a snapshot that a REINDEX restores with every row.

### P2-2 (C3) "A snapshot whose only damage is its search index counts as one that restores cleanly" is false, with a counterexample in the release's own corpus

CHANGELOG.md:16-17; lib/snapshot-probe.mjs:25-29 (rebuild errors do not affect the verdict, and integrity_check then fails).

main21-112 is one of the 661. Its snapshot's `observations_fts_config` holds one row `{k: null, v: null}`; the other three FTS configs hold `version 4`. `SELECT count(*) FROM observations NOT INDEXED` gives 1195. The check says `bad/integrity (SQLITE_ERROR)`, the printed command exits 1, and doctor gives that directory the set-aside (row `kind: set-aside`).

On a copy, I removed only that FTS table (virtual table, shadow tables, triggers). `PRAGMA integrity_check` then returns `ok`, and the shipped probe on it returns `{"opened":true,"integrity":"ok","observations":1195}`. So the damage was confined to the search index, and the snapshot was rejected.

The second half of C3 holds: the command ends with `CLAUDE_MEM_DIR=<dir> node <cli.mjs> fts-check rebuild` (lib/db-unusable.mjs:421-424).

### P2-3 (C10, 645de4e2) "A snapshot taken after the damage holds it, so the restore left a store that still did not open, and the next doctor named the same snapshot again"

This is stated without a condition. Per P2-1 it is false for every one of the 661 measured snapshots: 0/661 left a store that did not open under 6.30.5, and 0/661 were named again. The CHANGELOG (C2) at least states this part as a condition.

### P2-4 (C10, 645de4e2) "The directory is removed afterwards; one a killed check left is swept by the next walk"

lib/db-unusable.mjs:248 (finally comment), :161 (`STALE_CHECK_MS` = 20 min) and :261-282 (`sweepSnapshotChecks`).

`sweepSnapshotChecks` removes only directories older than 20 minutes, and it runs only inside a doctor walk, which happens only while the store is still broken and has snapshots. I reproduced a Ctrl-C (SIGINT to doctor and the probe child) during the check of a 593 MiB snapshot:
```
doctor exit 130; left: .snapshot-check-4144632-GL20t4  645M
an immediate second doctor (completes, names the snapshot): the 645M directory is still there
```
The likely sequence is: interrupt, re-run doctor, run the restore. After that the store is healthy, no walk ever runs again, and the copy stays. The function's own docblock ("only those older than any check can run") is accurate. The commit message and the finally comment are not.
