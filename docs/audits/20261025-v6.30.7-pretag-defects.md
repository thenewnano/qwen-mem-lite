  3. The comparison is only between the newest short snapshot and the first non-short one.

- **Evidence:** real check, and the printed commands really run in bash and sh.

## P2-1 — cross-filesystem move: the second opener can place a stale -wal under a store the first one has already checkpointed

Result: a corrupt store, the legacy sources gone, and doctor green.

- **Where:** schema.mjs:1716 (placeUnlessPresent), 1728-1746 (copyAcross), 1742.
- **Chain:**
  1. Two openers, A and B, both find no DB_PATH. Both copy the legacy db and its -wal to private names.
  2. A places the db and the -wal and unlinks both sources. It then opens the store (WAL recovery), writes, and closes. The last close checkpoints and deletes the -wal.
  3. B started its -wal copy before A's unlink, and that copy is still valid. B now places it: `existsSync(dest)` is false again, so the place succeeds.
  4. SQLite replays the old frames over pages A has rewritten.
- **Root cause:** each file's "place unless present" is decided on its own. Nothing ties B placing a -wal to B having placed the db; here the db was A's.
- **Evidence, forced:** both openers start together. A preload (slow-fsync.mjs) delays only B's second fsyncSync, which is its -wal copy; A runs unmodified.

  | B's delay | Corrupt runs |
  |---|---|
  | 0 ms | 0/5 |
  | 25 ms | 3/5 |
  | 50 ms | 2/5 |
  | 100 ms | 0/5 |
  | 200 ms | 4/5 (repro-legacy-move.sh: 4/8) |
  | 400 ms | 3/3 |
  | 1500 ms | 3/3 |

  - In a corrupt run, integrity_check reports "*** in database main *** 2nd reference to page 66".
  - ~/claude-mem-lite then holds no store file, and `stats` exits 0.
  - doctor says "✓ FTS5 integrity: all indexes healthy" and "✓ DB stats: 0.3MB, 50 observations".
- **Evidence, natural (no preload):** 12 of 12 trials clean, with a 47 MB -wal, three CLI openers and the data dir on ext4. So the trigger is narrow: B must lag A by more than A's open-to-close time, and by less than B's own -wal copy time.
- **Same root on one filesystem:** A was paused 3 s between its two renames (slow-rename.mjs).
  - If B opens and closes during the pause, the store is corrupted the same way.
  - If B holds the store open (hold-open.mjs), A leaves its -wal where it is. The data dir has 0 observations and the 50 rows sit alone in ~/claude-mem-lite/claude-mem-lite.db-wal. Nothing reports it.
  - The natural window here is just two consecutive renames.
- **Who is exposed:** only stores written by versions before 2.0.0.
- **v6.30.6:** across filesystems, every open fails with EXDEV and nothing moves: the bytes stay intact and memory is off. On one filesystem, its renames replace a -wal already at the destination.
- **Repro:** `$R/scripts/repro-legacy-move.sh <tree> <tmpfs dir> stale-wal`, run several times.
