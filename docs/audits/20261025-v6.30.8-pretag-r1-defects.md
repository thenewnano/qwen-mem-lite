## Findings

### F-1 (P2): setup.sh places a backup database without its log when its private log disappears partway; install's EXDEV sweep removes a live setup.sh's private files
- scripts/setup.sh:181 `{ [[ ! -f "$TMP-wal" ]] || mv "$TMP-wal" "$BACKUP-wal"; }`. This checks whether the private log exists *now*, not whether the script copied one. If `$TMP-wal` is removed after `cp` wrote it, the brace group returns true and `mv "$TMP" "$BACKUP"` places a backup database without its log. The script logs "backed up to …". From then on that backup closes both guards: setup.sh `has_legacy_backup`, and install's EXDEV skip.
- install.mjs:207-209 removes every `.legacy-backup-copy-*` in the data dir without checking whether its pid is alive. The comment justifies this with "install runs one at a time (install.lock)". setup.sh writes the same prefix, does not take install.lock, and runs at every session start. setup.sh's own sweep checks pid liveness (setup.sh:164-173); install's does not. This breaks the F4 claim that another live session's private files are kept.
- Repro (probes/probeA.sh). HOME is on /dev/shm and CLAUDE_MEM_DIR on ext4, so install takes the EXDEV path. The source is a store with 40 rows that are only in its -wal. A `cp` shim runs the real `migrateLegacyClaudeMemData` from install.mjs at the moment setup.sh starts copying the database:
  ```
  ℹ Legacy ~/.claude-mem/ DB is schema-incompatible; backed up to claude-mem-lite.db.legacy-backup-1792930031 ...
  claude-mem-lite.db.legacy-backup-1792930031 (no -wal): 0 rows        <- setup.sh's, reported as success
  claude-mem-lite.db.legacy-backup-1792930031979 (+ -wal): 40 rows     <- install's
  claude-mem.db (+ -wal): 40 rows                                      <- source
  next session start: no new copy (guard closed)
  ```
- Reach: no data is lost in this interleaving. The source stays, and install made a whole copy beside the incomplete one. The window is the gap between setup.sh's two `cp` calls while an install runs across filesystems. A second way in: setup.sh's own sweep treats `kill -0` EPERM as an exited process (`kill -0 1; echo $?` → 1), so it removes the live private files of another user's session when two users share a DB_DIR. Under Windows/MSYS, `kill -0` on a Node (Windows) pid was not checked.
- Fix shape: remember that the log was copied (`WAL=1`) and then `mv` it unconditionally. Make install's sweep skip live pids the way setup.sh's does.

### F-2 (P2, existed before this change and is not a regression; the consequence is data loss): install's same-filesystem path renames the database before its log. A kill between the two renames leaves a backup without its log, and the stranded log is later deleted
- install.mjs:204 `renameSync(legacyDb, backupPath)` runs first, then :219-221 renames -wal and -shm. Killed between the two renames: the backup holds the main file only, and `~/.claude-mem/claude-mem.db-wal` stays behind. The next install returns `noop` (no legacy db), and setup.sh does nothing (no `$OLD_DIR/claude-mem.db`), so nothing ever finishes the move. This contradicts F1's "both paths: the backup opened as found reads the rows only in its log". v6.30.7 already renamed in this order.
- Repro (renameSync shim, SIGKILL on the 2nd call):
  ```
  exit 137 ; next install: {"action":"noop"}
  ~/.claude-mem: claude-mem.db-wal
  claude-mem-lite.db.legacy-backup-1792930071649 (no -wal): 0 rows
  ```
  If anything later opens a store at the old path (for example a claude-mem that is still installed), SQLite deletes the stranded WAL, and those rows are gone everywhere:
  ```
  src.db renamed away, src.db-wal stranded -> open fresh store at src.db -> dir now: moved.db src.db   (WAL deleted)
  ```
- Severity: by consequence this is P1 (data loss on an unusual path). I graded it P2 because the window is two adjacent renameSync calls and the order predates this change. Fix shape: rename -wal and -shm first and the database last, as the copy path already does. A rerun then has to adopt an orphan `<backup>-wal`.

### F-3 (P3): the new sweep in setup.sh aborts the whole SessionStart pre-hook under `set -e` when `rm -f` fails
- scripts/setup.sh:164-173. `rm -f "$f"` is inside the `then` branch, so errexit applies. An entry with a dead pid that cannot be removed (a DB_DIR that is not writable, or a directory with that name) exits the script at step 3. Steps 4-9 are skipped: the claude-mem.db rename, the runtime dirs, the dependency install and the `.deps-broken` flag, and the markers.
- Repro (probes/probeB.sh): DB_DIR is chmod 555 and holds `claude-mem-lite.db`, `runtime/` and `.legacy-backup-copy-<deadpid>-1600000000`:
  ```
  setup-6.30.7.sh: exit 0; last line: ✓ claude-mem-lite ready
  setup.sh (HEAD): exit 1; last line: rm: cannot remove '.../.legacy-backup-copy-2316869-1600000000': Permission denied
  ```
- Fix shape: `rm -f "$f" 2>/dev/null || true`.

### F-4 (P3): a kill between placing the log and placing the database leaves an orphan `<backup>-wal` (and `-shm`) that nothing ever removes
- install.mjs:216 and setup.sh:181-182. Neither sweep matches `claude-mem-lite.db.legacy-backup-<ts>-wal` (both sweep `.legacy-backup-copy-` only). The orphan is a full copy of the log. The existing test "a copy killed between placing the log and placing the store…" leaves one behind and does not assert on it.
- Repro (renameSync shim, SIGKILL on the 3rd call, EXDEV path):
  ```
  after the next install: claude-mem-lite.db.legacy-backup-1792930098004-wal   <- orphan
                          claude-mem-lite.db.legacy-backup-1792930098047 (+ -wal)
  ```
- setup.sh names backups to the second. A later copy within the same second, from a source that has no log by then, would pair that orphan log with a database it does not belong to. This was not reproduced and needs a same-second rerun.

### F-5 (P3): incomplete backups made by earlier versions still close both guards, and no upgrade note covers them
- setup.sh before v6.30.8 copied the database without its log, or left a truncated copy straight under the backup name when it was killed. HEAD's `has_legacy_backup` and install's EXDEV skip both accept such a file as a backup, so HEAD never makes the whole copy. CHANGELOG/README only tell users to rename the log of an *install*-made backup. The source in ~/.claude-mem still holds the rows.
- Repro (probes/probeG.sh): v6.30.7 setup.sh, then HEAD setup.sh, then HEAD install across filesystems:

  claude-mem-lite.db.legacy-backup-1792930267 (no -wal): 0 rows   (source: 40)

### F-6 (P3): F4's claim "a kill at any point … the next session start makes a whole one" holds only while DB_DIR has no claude-mem-lite.db

So after a killed copy, no later session start copies again, and the user ends up with no backup (the source stays). The setup.sh comment at :151-155 and the test names say otherwise. The tests never let the product open between the two runs.
- Repro (probes/probeH.sh): a `cp` shim kills setup.sh, then `ensureDb()` runs in the sandbox, then setup.sh runs again:

## Questions answered

1. Data loss or an incomplete backup that closes a guard: yes, see F-1 (an incomplete backup that closes a guard, with a whole one beside it) and F-2 (data loss, existed before). Things checked and found sound:
   - two setup.sh running at once (probes/probeF.sh, overlap shown: cp-db starts 0.6 s apart during a 1.5 s copy) → one whole backup with 40 rows and no private files left;
   - setup.sh running while install takes the same-filesystem path: the database is moved before its log, so setup.sh can never copy a database without its log; its cp fails and it warns;
   - a DB_DIR named `da ta [1]*?.x` (probes/probeE.sh) → backup with 40 rows; the guard closes on the 2nd run; a dead pid's private file is swept;
   - every kill point of the EXDEV copy path and of setup.sh leaves no backup database (the tests plus F-4).
2.
