## Findings

### F1. "each by exactly the damaged store's count" is wrong (FALSE, P3)

Claim, from the 3b50d96d body: "73 passing snapshots are short of their own index, each by exactly the damaged store's count."

What is true is different: their index *lists* exactly the damaged store's count. My re-run of `tasks/d558/a3/run.sh 8` on 1b12ffe2 shows:

```
short of index 73
listed==storeObs 73   shortfall==storeObs 0   listed==templateObs 73
shortfall min 3 max 1474, 18 distinct values
```

The other places get it right: 064434d0, a3 doc:51, CHANGELOG.md:26-27 and tests/snapshot-check.test.mjs:99-100 all say "lists" or "listing exactly".

### F2. doctor added nothing to the 661/661 agreement (MISLEADING, P3)

The agreement itself holds (H1), but doctor's part of it could not fail:
- In snapcheck.mjs:173-179, the truth arm keeps only `dbLine`, the first doctor line matching `/Database:/`. Its `ok` never reads `dbLine`.
- doctor prints no `Database:` line when the store passes. It prints none either after restoring a snapshot that then fails sqlite3's integrity_check.
- `dbLine` is `""` in 1322 of 1322 rows (my run plus the archived one). That includes the 31 rejected snapshots whose restore command exited 0 and left a store failing integrity_check. Example: main21-483, `cmdRc=0`, `ic=fail … Rowid 291 out of order`, `dbLine=""`.

Two population limits on the agreement are not stated:
- None of the 661 snapshots had a `-wal`, so the restore command's `&& cp <snap>-wal <db>-wal` step never ran.
- The corpus has one snapshot per case, so walking past a rejected snapshot to an older one was never exercised end to end.

### F3. "about 1.3 times" is low for small stores and unmeasured (FALSE / UNSUPPORTED, P3)

Nothing in the archive measures this figure; `grep "1\.3 times"` matches only CHANGELOG.md:28. I measured the peak size of the private `.snapshot-check-*` directory, polled about every 0.2 ms, while `checkSnapshot` ran. The disk is ext4, so FICLONE falls back to a full copy.

| Snapshot | Size | Peak / size |
|---|---|---|
| ruler `main` template (VACUUM INTO) | 1.98 MiB | 1.61 (db 2.10 MB + wal 1.21 MB) |
| ruler `log` template | 2.41 MiB | 1.57 |
| synthetic, 2k observations | 11.3 MiB | 1.28 |
| synthetic, 20k observations | 109 MiB | 1.26 |
| synthetic, 100k observations | 543 MiB | 1.25 |

Below SQLite's 1000-page autocheckpoint, the WAL holds all four FTS rebuilds plus the REINDEX at once. So "about 1.3" holds for large stores with an FTS share near 23%, and is low for the store shapes the measurement itself used. Not measured: SQLite's temp files in TMPDIR (which is not "beside the snapshots"), and filesystems with reflinks.

Too little space fails safe: "could not be checked (SQLITE_FULL)" and no command.

### F4. Across filesystems the store does not move, and every open fails (FALSE, P2)

At schema.mjs:1677, `renameSync` is called from ensureDb (schema.mjs:1695) with no catch. In a sandbox with HOME on /dev/sda2, CLAUDE_MEM_DIR on tmpfs, and a WAL store in `$HOME/claude-mem-lite`:
- `cli.mjs recent 1` exits 1 with `Cannot open database: EXDEV: cross-device link not permitted, rename '…/claude-mem-lite/claude-mem-lite.db' -> '…/claude-mem-lite.db'`, and fails again on every run.
- `hook.mjs session-start` prints nothing.
- `install.mjs doctor` says `⚠ Database: not found (will be created)`, which is false.

Memory stays off with no notice. The old store stays intact, so no data is lost.

This is not a regression. 3dda02a8 (6.30.5) also throws EXDEV here, after first deleting the data directory (its `runtime/k` was gone). The default same-filesystem layout works (H5).

### F5. "Fewer than the damaged store" was measured through the store's index (MISLEADING, P3)

`storeObs` (snapcheck.mjs:144, 187) is `count(*)`. `EXPLAIN QUERY PLAN` shows SQLite answers it from the covering index `idx_obs_epoch_project`.

I regenerated all 73 damaged stores with the ruler's `richPlants` and counted each on a read-only copy:
- In 73 of 73, the store's own table scan (`NOT INDEXED`) equals the snapshot's row count, and the store's index count equals `storeObs`.
- Every one of the 73 carries an `ncell1` plant: an observations table page's cell count set to 1. 49 have that plant alone; 24 have a second one.
- A raw `VACUUM INTO` of main21-46's damaged store reproduces the shape exactly: `wrong # of entries in index idx_obs_epoch_project`, index count 1195, table scan 15.

So the snapshot lost no rows that the store's table can read. The cause the doc calls "not established" is in the corpus's own plant parameters. The rows the table walk cannot reach sit on orphaned pages of the broken file, which both commands now keep.

The doc also does not state its population. It counts 79 snapshots below the damaged store, but 128 passing snapshots hold fewer rows than the undamaged template. The other 49 are left out because their store count is unreadable (`ERR SQLITE_CORRUPT` in 47, `ERR SQLITE_NOTADB` in 2).

### F7. README method 3 does not say "from ~" (MISLEADING, P3)

README.md:184-190 is `git clone …; cd claude-mem-lite; node install.mjs install`, with no directory. The clone lands at `~/claude-mem-lite` only when it is run from `~`. The claim is repeated in the CHANGELOG, the 98285e20 body, the schema.mjs comment and the test header listed in the table.

### F8. `fts-check check` exits 0 with a broken ordinary index (MISLEADING, P3)

The edited help line now says "the FTS5 indexes and then every other index". On a store with a damaged ordinary index:
- `fts-check check` prints "FTS5 indexes are healthy" and exits 0, while integrity_check reports `wrong # of entries in index idx_obs_branch`.
- `fts-check rebuild` repairs it, and integrity_check then says ok.

The "Exit 0 when every index is healthy" line predates this release, but the edit widened what "index" means.

### F9. The children's sandbox is described wrong (MISLEADING, P3)

snapcheck.mjs:143 gives `cli.mjs delete`, the bash restore and `install.mjs doctor` an explicit env with `HOME=WORK/sc8/<slot>/home`. They do not inherit run.sh's sandbox, and the "0 entries" count does not cover those per-slot homes. Only the probe children and sqlite3 inherit run.sh's environment.

Nothing leaked: each of the 32 per-slot homes holds only the `tmp/` and `proj/` directories snapcheck itself creates.

### F10. "Restores cleanly" covers snapshots that keep 1.3% of their indexed rows (MISLEADING, P3)

The 605 that "restore cleanly" include main21-46 (15 of 1,195 indexed rows) and log23-672 (21 of 1,495): 73 such snapshots in all. Another 55 lack the WAL's rows (D#557).

doctor's own sentence for these is accurate ("holds 21 observation(s), 1474 fewer than its own index lists"). But the walk names the newest passing snapshot however short it is, so an older, fuller snapshot is never named. The headline wording does not hint at this.

### F11. README's `rm -rf ~/claude-mem-lite/` doesn't say to check the database moved first (MISLEADING, P3)

README.md:200 and :214 say the database stays in `~/claude-mem-lite` whenever the data directory already holds any store file. The removal line no longer says what "after confirming" means. In that case the command deletes a pre-v0.5 store that never migrated. The risk is no larger than 6.30.5's "(if not auto-moved)" wording.
