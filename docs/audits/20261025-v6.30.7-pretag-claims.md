### P2-1 — "short of its own index" is printed as "rows its table lost", but the same on-disk shape also comes from an index that kept entries for rows the user deleted
- **Where:**
  - CHANGELOG.md:16-17: "…has lost those rows (a delete removes a row's index entries with it)".
  - The printed doctor sentence, lib/db-unusable.mjs:528: "…, N fewer than its own index lists: rows its table lost".
  - The comment at lib/db-unusable.mjs:503-505: "…so only a table that lost cells leaves them".
  - Commit 1ffd4f6a: "SQLite's own evidence separates the two cases: … while a user's delete removes the index entries too".
  - 6989bfde keeps "rows its table lost".
- **How it happens:**
  1. The user deletes rows normally, so the table and every index both lose them.
  2. One write to an index page is lost: the page goes back to its image from before the delete (a lost write, or a torn checkpoint whose WAL was then deleted).
  3. `idx_obs_epoch_project` now lists the deleted rows, and the table does not have them.
  4. VACUUM INTO copies the table and the index raw, so the snapshot has the same mismatch.
  5. checkSnapshot reads `listed` (count(*) answered by that covering index) as more than `observations` after REINDEX.
  6. doctor prints "rows its table lost", treats the newer snapshot as damaged, and names an older snapshot that is not short and holds more.
  7. Running the command brings back the rows the user deleted and loses what was written after the older snapshot.
- **Evidence (measured):**
  - Raw probe (probe/stale-index-probe.mjs, SQLite 3.53.4):
    - A normal `DELETE` of 29 of 410 rows leaves the page map unchanged, freelist 0→0, integrity ok.
    - Reverting the index's one page gives exactly the survey's lossy-table signature:
      - quick_check and integrity_check both report only "wrong # of entries in index t_epoch";
      - count(*) reads 410 and NOT INDEXED reads 381;
      - VACUUM INTO keeps the mismatch, and REINDEX gives ok with 381.
    - System sqlite3 3.46.1 prints the same single line for both pragmas.
  - Product (probe/stale-doctor.mjs, then a sandboxed `install.mjs doctor`):
    - Setup: S_old taken with 400 obs and intact; 20 obs added; the user deletes 30; the index pages revert; S_new taken by VACUUM INTO; the store breaks.
    - doctor printed: "The newest of the 2 backup snapshot(s) beside the database restores, but short: … holds 390 observation(s), 30 fewer than its own index lists: rows its table lost. The next one that restores and is not short of its own index, …2026-10-01….bak, holds 400 observation(s). The command restores that one, which holds more and lacks what was written after it was taken."
    - Running that printed command in bash exits 0. The restored store has 400 obs and integrity ok, **0 of the 20 rows written after S_old, and 28 of the user's 30 deleted rows back**.
    - The alternative command for S_new is printed and the broken file is kept, so the user can recover.
- **The authors had the second reading:**
  - The survey's own table (docs/audits/20261024-v6.30.7-d570-snapshot-selection-survey.md:52) reads "The table lost cells, **or the index holds stale extras**". The shipped text dropped the second half.
  - The corpus cannot say NO here: all 73 short snapshots carry an ncell1 implant on the observations table (a3 doc line 21), so it holds no damage on the index side.
  - The test fixture `writeStoreSnapshot(..., {damage:'lost-rows'})` (tests/test-helpers.mjs) builds the "lost rows" shape *by a DELETE* with the indexes hidden from the schema. That is the on-disk shape of a delete whose index entries were not removed.
- **v6.30.6, same case:** names the newest non-empty snapshot (S_new) without checking it, with `rm -f -wal -shm && cp`. It gives no count and no cause. The user gets their 390 rows back, and the stale index stays until something rebuilds it.

### P2-2 — CHANGELOG: an unchecked snapshot "stops the walk with the reason and no command" — false once the newest snapshot is short
- **Where:** CHANGELOG.md:14-15. The docblock at lib/db-unusable.mjs:365-368 says the same; the code is at :513-519 and :566-567.
- **How it happens:**
  1. The newest snapshot passes but is short.
  2. A second walk looks for an older snapshot that is complete.
  3. An older snapshot cannot be checked: it is unreadable, the disk fills during its copy, or a newer version wrote it.
  4. The code sets `stopped`, breaks, and returns kind 'restore' with the command naming the short snapshot.
- **Evidence:**
  - A sandboxed doctor run with S_new short and S_old at chmod 000 printed: "…30 fewer than its own index lists: rows its table lost. An older snapshot could not be checked (EACCES): …2026-10-01….bak. Once every Claude Code session is closed, restore it: test -s …2026-10-20….bak && …".
  - tests/snapshot-check.test.mjs:931-943 asserts this behaviour: newest `ok(3, 410)`, middle `unchecked`, oldest `ok(400)`. The command restores the newest snapshot with 3 observations, gives no alternative, and never mentions the oldest. That is the third attempt's P1-1 outcome (3 of 410 named over an intact 400), now reached whenever a middle snapshot cannot be checked. A nearly full disk is one realistic way: it can fit the copy of a small short snapshot and not the larger older one.
  - Commit 1ffd4f6a states this accurately ("An unchecked snapshot stops that search"); the CHANGELOG generalises it wrongly.
- **Contract item 4** ("A snapshot the check cannot run on stops the walk with no command") fails here if read literally. The brief rates a failed contract item P1. I grade the false claim P2 and leave the contract call to the defects reviewer.
- **v6.30.6, same case:** names the same newest non-empty snapshot without any check, and says nothing about the others.
