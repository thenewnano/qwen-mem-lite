## P2

### P2-1 Short CJK saves that differ only in a Latin identifier or number are refused as duplicates
`hash-utils.mjs:27-45` (jaccardOfTokens, cjk=true) used by `lib/save-observation.mjs:299-308`.

Each CJK run adds all of its character bigrams to the token set, while the Latin identifier glued
into the sentence is one whitespace token. In a short sentence the bigrams dominate, so changing the
identifier (the part that distinguishes the two facts) leaves Jaccard above 0.7. v6.27.0 stored both
rows; the English counterpart is stored by both builds. Both faces are affected (shared saveObservation).

Reproduction (fresh sandbox store, same project, within the 5-minute window):
```
save "修复了redis连接池泄漏" --type bugfix      -> Saved #1
save "修复了mysql连接池泄漏" --type bugfix      -> [mem] Skipped: similar to existing #1.   (exit 0)
save "升级到node22之后构建失败" --type bugfix   -> Saved #2
save "升级到node20之后构建失败" --type bugfix   -> [mem] Skipped: similar to existing #2.
save "fixed redis pool leak" / "fixed mysql pool leak" -> both Saved (#3, #4)
v6.27.0, same four CJK saves                   -> Saved #1..#4
MCP mem_save "升级到node22之后构建失败，原因是原生模块没有重新编译" then the node20 variant
  -> "Skipped: similar to existing #1 in project "work--proj". Use mem_get(ids=[1]) to review."
```
Arithmetic for the first pair: tokens {whole-token, 修复, 复了, 连接, 接池, 池泄, 泄漏}, 6 shared of 8
→ 0.75 > 0.70. The skip exits 0 and the MCP text does not mention `force`, so an agent reads it as
handled. (A 2-character negation change, 必须→不必 in a 14-character sentence, was stored.)

## P3

### P3-1 Concurrent first opens append the glued-ASCII runs twice
`schema.mjs:1260-1281` (deferred cleanup `backfill-glued-ascii-runs`). Both SELECTs run outside the
`db.transaction`, so two processes that both see the marker unset (SessionStart + MCP server on the
first session after the update) compute runs from the same pre-cleanup snapshot and both append.
The "a re-run finds each appended run standing alone" idempotency only holds sequentially.
Evidence (big store, 3 processes started together, all exit 0):
```
{"rows":8334,"appendedOnce":0,"appendedTwiceOrMore":8334,...,"sample":"text 0 修复了redis连接池泄漏v0 words redis v0 redis v0"}
single-process control (big1): appendedOnce 8334, appendedTwiceOrMore 0
```
Not reproduced on the live-data copy (3×3 concurrent opens, 2 rows changed, 0 doubled) — the window
is the cleanup's duration (≈1 s at 60k events, ≈3 s at 200k). Effect: duplicated index terms
(BM25 term frequency), no row loss. A second process can also fail its cleanup on
SQLITE_BUSY_SNAPSHOT and leave it for the next open (observed: `"cleanups":0` in one process).

### P3-2 First-open migration time scales with the store; claim holds only for small stores
`schema.mjs:860-866` (IS NULL backfill under BEGIN IMMEDIATE) + `ensureEventsFTS` rebuild +
the deferred cleanup at `schema.mjs:1260`.
```
live copy (6.9k events / 457 obs):   openMs 122   (second open 4.5)
mid  (60k events / 15k obs):         openMs 1934  = initSchema 982 (write lock held) + cleanup 956
big  (200k events / 50k obs):        openMs 6680  = initSchema 3567 + cleanup 3018
```
The live store grows ≈167 events/day (2026-09-05 → 2026-10-16), so a heavy user crosses 60k in about a
year. Within SessionStart's 15 s budget; a peer opener waits on BEGIN IMMEDIATE with busy_timeout 5 s
(server exits FATAL on SQLITE_BUSY at startup, server.mjs:235), so the lock hold would have to pass
5 s (≈280k events by extrapolation) to break a concurrent MCP start — not reached in these trials.
Of the cleanup's 3.0 s on "big", 2.66 s is recomputing eventSearchTerms for every event that the
initSchema backfill computed moments earlier (measured separately: events 2664 ms, obs 145 ms), i.e.
redundant on every v6.27.0 → v6.28.0 upgrade.

### P3-3 Events written by v6.27.0 after the migration stay unsearchable by CJK / glued Latin, permanently
`schema.mjs:854` comment: "Rows a pre-d366 build writes later carry NULL and are filled by the next
full pass." On a migrated store the sentinel is present, so the fast path never runs that pass again,
and the deferred cleanup is already marked done.
```
(migrated live copy) v6.27.0: activity save --title "旧版本事件 kafka消费者卡住" -> id 6914, search_terms NULL
v6.28.0: activity search kafka -> (no events); activity search "旧版本事件" -> only #6915 (the v6.28.0 row)
time-open after further v6.28.0 opens: "nullTerms":1 (unchanged)
v6.27.0 save "… 修复了redis连接池泄漏 …" (#613): v6.28.0 search redis -> No results; search 连接池 -> #613
```
Hits users running two builds side by side (an old session still open, or a downgrade and re-upgrade).

### P3-4 The write-side project check covers save / defer add / mem_save / mem_defer only
`mem-cli.mjs:3860` exempts `activity save`, `import-jsonl`, `verify-apply` from the read note
"left to their own write-side check", but none of them has one (`cli/activity.mjs:46` even resolves
the write in READ mode, pre-existing).
```
activity save --type discovery --title "evt typo" --project claude-mem-lte   -> {"ok":true,"id":1}, exit 0
import-jsonl imp.jsonl --project claude-mem-lte                              -> +1 prompts, exit 0
```
Both created project "claude-mem-lte" next to "dev--claude-mem-lite" with no note. Once such a stray
project has an event or session row, `checkWriteProject` treats it as existing: the next
`mem_save(project:"claude-mem-lte")` was accepted ("Saved as observation #8 … claude-mem-lte"),
where the same call on a clean store is refused.

### P3-5 MCP reads naming an unknown project get no note (CLI-only fix)
`unknownProjectNote` (project-utils.mjs) is imported by mem-cli.mjs only; server.mjs imports
`checkWriteProject` but not it. `mem_search/mem_recent/mem_timeline(project:"otherr-api")` still answer
like an empty real project. Parity gap with 4dfa2946's CLI behaviour.

### P3-6 A full id that differs only in case is written as a new project
`project-utils.mjs:279`: ids containing `--` skip the near-name check.
`save "case row" --project Dev--Claude-Mem-Lite` beside existing `dev--claude-mem-lite` →
`Saved #6 … (new project "Dev--Claude-Mem-Lite")`. similarProjects already compares lower-cased.

### P3-7 `save --file x` is refused with "did you mean --title?"
`mem-cli.mjs:4067` takes the FIRST accepted flag within edit distance 2, not the nearest:
```
save hello --file a.mjs -> [mem] save does not take --file (did you mean --title?) — nothing was written.
```
`--files` is distance 1. /lesson and /bug document `--file <path>` as an argument, so a model mapping
them onto `save` is steered to put the path into --title. (v6.27.0 dropped --file silently; refusing
is an improvement, the hint is wrong.)

### P3-8 `mem_save(lesson_learned: "", lesson: "X")` drops the alias without a word
`server.mjs:1368` applyArgAliases copies only when the canonical key is `undefined`; an empty string
wins. Probe: #12 saved with no lesson_learned. (Both non-empty: canonical wins, as claimed — #11
stored CANONICAL-WINS.)

### P3-9 mem_delete's empty-list error advises omitting a required field
`tool-schemas.mjs:131` MUST_NOT_BE_EMPTY is shared with `ids` (nonoptional):
`mem_delete(ids:"[]")` → "must not be empty: pass a non-empty list, or omit the field at ids".
Omitting it is the required-field error.

### P3-10 The swallowed events_fts rebuild is now on every upgrade path
`schema.mjs:1774-1779` (`/* non-critical — index repopulates lazily on next write */`). Pre-existing
code, but before this release it ran only for a drifted store; now every v6.27.0 store drops and
recreates events_fts. If the rebuild throws (NOMEM, a damaged events row) the empty 5-column index
is committed with its sentinel and the fast path never retries; an external-content index does not
repopulate old rows "lazily". Not triggered in any probe.

### P3-11 A lone numeric positional to `timeline` now anchors instead of searching
`mem-cli.mjs:1148-1177`. `timeline 2024` with an #2024 present centres on that row (any project
when --project is absent) where it used to search "2024". In the probe store ids stopped at 15, so
`timeline 2024` still searched; `timeline 3` from work--proj centred on #3 of mono--api-gateway.
Behaviour change worth a CHANGELOG line, not a defect by itself.

## Unattributed observation (not a finding)

Once, on the "mid" store, two v6.28.0 processes opening concurrently (`ensureDb()` each, both exit 0)
left the events table b-tree damaged:
```
PRAGMA integrity_check: Tree 45 page 6281 cell 2: Offset 24672 out of range 112..4092
NULL value in events.project / event_type / title / created_at_epoch
row 47643 missing from index idx_events_project_created / idx_events_created / idx_events_type / idx_events_project
(tree 45 = table events; the row reads back as id 0 with all-NULL columns)
```
Not reproduced in 60 further trials (41× 2 processes and 5× 3 processes on "mid", 11× 3 processes
on "big", 3× 3 processes on the live copy; all integrity_check ok). The pristine source copy is ok; nothing in the open path writes the
file outside SQLite, no writable_schema/unsafe pragma is used (grep), SQLite 3.53.4 /
better-sqlite3 13.0.3, tmpfs. I cannot attribute it to the reviewed code, and SQL issued through the
API should not be able to damage a page. If the lead wants certainty: repeat the concurrent
first-open stress on disk-backed storage (script shape: copy a v6.27.0 store, start 2–3
`ensureDb()` processes at once, integrity_check), ideally a few hundred trials.

## Claims

1. **"First open of a v6.27.0 store migrates in well under a second and keeps schema 49; v6.27.0 reads
   and writes the migrated store; fts-check passes under both."** — Partly true.
   - Schema stays 49: TRUE (all probes).
   - Well under a second: TRUE for the live copy (122 ms); FALSE at scale (1.93 s at 60k events,
     6.68 s at 200k) — P3-2.
   - v6.27.0 on the migrated store: TRUE — CLI save/search/activity save/activity search, MCP
     mem_search/mem_save/mem_get all worked; v6.27.0 fast path does not touch events_fts, its
     `fts-check rebuild` uses 'rebuild' which works on 5 columns. Caveat P3-3.
   - fts-check: TRUE — `fts-check check` "healthy" under v6.27.0 and v6.28.0, before and after
     old-build writes; integrity_check ok.
2. **"A CJK event is found by a CJK substring query; 修复了redis连接池泄漏 is found by `redis`; rows
   without CJK are indexed as before."** — TRUE for rows written or backfilled by v6.28.0
   (`activity search 消费者|redis|连接池` → #6915; backfilled big store `activity search redis|失败`
   hits; `search redis` finds backfilled observations). Non-CJK rows: 0 non-CJK events got terms,
   2 of 457 observations changed and both contain Han. Caveat P3-3 (rows written by v6.27.0).
3. **"The only additions to any advertised MCP input schema are mem_save `lesson` and mem_timeline
   `id`; `lesson_learned` wins when both are given."** — TRUE. tools/list diff v6.27.0 vs v6.28.0,
   9 listed tools and all 18 with CLAUDE_MEM_ALL_TOOLS=1: only `mem_save.lesson`, `mem_timeline.id`
   added, plus a description change on `mem_search.query`; the preprocess changes on tasks/operations/
   merge_ids/supersedes/closes_deferred/ids render identically. Canonical wins when both are
   non-empty (#11). Caveat P3-8 (empty canonical). mem_timeline: `anchor` beats `id`.
4. **"A write naming a project one or two edits from an existing one is refused with the near names;
   a new name is written and noted."** — TRUE for CLI save / defer add and MCP mem_save / mem_defer
   (`claude-mem-lte`, `api-gatway`, `api-gatewya`, `zebraprj` refused with near names; `brandnew`,
   `zebraproj` written with "(new project …)"; `proj` from work/proj → work--proj). FALSE for
