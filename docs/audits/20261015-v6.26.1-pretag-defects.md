## Findings

### P3-1 A whole answer followed by cut-off trailing text is now discarded

- Where: haiku-client.mjs:704 (direct `stop_reason === 'max_tokens'`), haiku-client.mjs:1167
  (`finish === 'length'`).
- What: both checks discard the reply before anyone parses it. `parseJsonFromLLM` (utils.mjs:558)
  recovers the first balanced object from text with trailing prose, so a reply such as
  `{"scope":"project"}` followed by an explanation that ran into the cap was a usable answer at
  3d975c32. Now it goes to the CLI fallback: a `claude -p` spawn, 8-13 s per the measurements quoted
  in haiku-client.mjs's BG_LLM_TIMEOUT_MS comment, and null when the CLI is unavailable. The
  CHANGELOG's premise "Every caller ... parses a fixed-shape JSON answer" also has one exception:
  `lib/lesson-bridge.mjs:33-36` keeps the FIRST LINE of plain text, so a cut-off reply's first line
  was usable there too (that path has a 2000-token cap and a 2.5 s budget, so it is close to
  unreachable).
- Most exposed callers: hook-optimize.mjs:295 (scope classification, `maxTokens: 60`) and
  rerank.mjs:94 (`maxTokens: 300`, on the mem_search request path).
- Evidence: same probe at both commits, CLI mocked to fail, `callModelJSONAsync('p', 'haiku',
  {maxTokens: 60})`, reply text `{"scope":"project"}\n\nThe memory describes a project-wide
  convention because it`:
  - 3d975c32: `api: {"scope":"project"} | openrouter: {"scope":"project"}`
  - 65582d91: `api: null | openrouter: null`
- Incidence: not measured. For Claude Haiku 5.5 with thinking off and "Return ONLY valid JSON" it is
  probably rare. It is more likely with a user-chosen `OPENROUTER_MODEL` that comments after its
  JSON. A narrower rule would check after parsing: discard only when the cut-off text does not
  parse to the caller's shape. That would need the parse inside the dispatcher, so it is a design
  choice, not a one-line fix.

### P3-2 `us-gov.` cross-region prefix misses the strict body

- Where: haiku-client.mjs:98, `/^(?:[a-z]{2,6}\.)?anthropic\./`.
- What: `[a-z]{2,6}` has no hyphen, so `us-gov.anthropic.claude-haiku-5-5` keeps the old body:
  `temperature: 0` and no `thinking: disabled`. By the CHANGELOG's own account, that body gets a 400
  from Claude Haiku 5.5, so every call on that gateway name goes to the fallback. The CHANGELOG
  scope says "a cross-region prefix such as `us.` or `global.`".
- Evidence (probe body): `direct us-gov.anthropic.claude-haiku-5-5 strict=false temp=0`, against
  `direct us.anthropic.claude-haiku-5-5 strict=true temp=undefined`.
- Unverified: whether Bedrock serves Claude Haiku 5.5 under a `us-gov.` inference profile. The
  claude-api skill lists the `anthropic.` prefix but no cross-region prefixes. `[a-z]{2,6}(?:-[a-z]+)?`
  would admit it.

### P3-3 The golden files do not pin the no-DIAGNOSIS branch of the episode prompt

- Where: hook-llm.mjs:158 (`'DIAGNOSIS: (none — no failing output, ... lesson_learned must be null)'`);
  tests/hook-llm.test.mjs:363-376 (all three golden episodes carry `diag` lines).
- What: an episode with no DIAGNOSIS line sends this string. The test comment says "an edit to it
  must show up as a diff here (D#325)", but this branch's text is not pinned.
- Evidence: mutation `lesson_learned must be null` -> `lesson_learned should be null` (asserted
  applied): all 48 test files that mention hook-llm pass, 1936/1936, under `CI=true`. The only other
  guard on that branch is `tests/episode-input-filter.test.mjs:621`
  `toMatch(/DIAGNOSIS: \(none/)`, which checks only the prefix (a `none` -> `None` mutation was
  caught by that test, nothing after the prefix is).
- Fix shape: add a fourth golden case with `entries` carrying no `diag`.

### P3-4 key-events-input-replay still builds entries from different events and text than the hook (pre-existing)

- Where: benchmark/key-events-input-replay.mjs:151-152 (`response = textOf(part.content)`;
  `if (response.length < 10) continue;`) against hook.mjs:778
  (`if ((!resp || resp.length < 10) && !(tool_name === 'Bash' && bashWrites.length > 0)) return;`,
  where `resp = normalizeToolResponse(tool_response)`).
- What: the ruler reads the text the model was shown; the hook reads `tool_response`. Two
  consequences:
  - A Bash call that printed nothing is `(Bash completed with no output)` in the transcript (31
    characters), so the ruler keeps it as an entry. The hook sees `''` and drops it unless the
    command wrote a file. In this repo's corpus (read 2026-10-15, live) that is 254 silent Bash
    events, 234 with no bashWrites (73 of the 254 on the main thread). Those entries count toward
    EPISODE_BUFFER_SIZE and batching in the ruler but not in the hook. The 20 with writes get a desc
    and diagnosis computed from the placeholder text instead of `''`.
  - Long outputs are cut down in the transcript content but not in `toolUseResult.stdout`, which
    holds what the hook receives. In the 15 newest transcripts, 19 of 2,754 Bash results have
    stdout+stderr more than 100 characters longer than the content, at most 27,649 characters more.
    This is also why the D#332 audit saw the 64 KiB window fire 0 times.
- Not introduced by this range (the `< 10` filter and `textOf` predate 3d975c32), but the release
  note says the ruler "builds its entries the way the hook does". That is true of the fields'
  function and options, not of the input. Reading `toolUseResult` (present in the transcript lines)
  through the hook's `normalizeToolResponse` rules would close both gaps.
