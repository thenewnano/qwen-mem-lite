## Findings

### P1-1: doctor's new rebuild writes into a store whose integrity check reports page-level damage, and destroys rows that 6.30.8 left intact

- **Where:** schema.mjs:2064 (`if (passes(rows)) return { state: 'ok', rows };`). Any other result goes on to
  `BEGIN IMMEDIATE` (2096), then `rebuildIndexes` (2112), then `COMMIT` (2120). install.mjs:3203 calls it whenever the FTS step
  was not busy.
- **What goes wrong:** the rebuild runs on any failed check. That includes lines saying the page structure itself is broken:
  `2nd reference to page N` (a page claimed twice, for example a freelist that lists a page a table still uses), `Page N: never
  used`, `invalid page number`. REINDEX and FTS 'rebuild' free pages and allocate new ones. Once the freelist hands out a live
  page, the new index content overwrites the rows on it. 6.30.8's doctor wrote only when FTS5's own check failed, so it did not
  write on this store at all.
- **Who is affected:** a user whose store took a torn or lost write and who runs `doctor`, the documented diagnostic.
- **Repro:** a production store made by the product opener (`ensureDbWithWalRecovery`) with 400 observations, a dropped table
  for a freelist, and the freelist trunk edited so it lists two observations leaf pages:
  ```

  NOVAC=1 node /home/ai/.cache/tmp/rv-6309-defects/scripts/p1d-vacuumed.mjs $S/data
  (cd /home/ai/.cache/tmp/rv-6309-defects/wt && HOME=$S/home CLAUDE_MEM_DIR=$S/data node cli.mjs doctor)
  node /home/ai/.cache/tmp/rv-6309-defects/scripts/p1d-vacuumed.mjs $S/data report
  ```
  Output:
  - Before doctor: integrity_check reports `Tree 5 page 5 cell 9: 2nd reference to page 71 / Tree 5 page 5 cell 3: 2nd reference to
    page 70 / Page 113: never used / Page 125: never used`, and the observations read back intact: `"observationsIntact":
    "400/400"`.
  - 6.30.9 doctor prints `✓ FTS5 integrity: all indexes healthy`, then `⚠ Database integrity issues detected:` with those lines,
    then `Rebuilding the indexes...`, then `✗ Database integrity: not repaired by rebuilding the indexes` (`Tree 5 page 70 cell 262:
    Rowid 263 out of order`, `Tree 31 page 31 cell 0: 2nd reference to page 71`).
  - After doctor: `"observationsIntact": "382/400"`. 18 observations were overwritten by doctor's own write.
  - The same fixture under 6.30.8's doctor (`git archive 051dd70f` tree, `node cli.mjs doctor`) prints `✓ FTS5 integrity: all
    indexes healthy` and `✓ DB stats: 0.8MB, 400 observations`, and afterwards `"observationsIntact": "400/400"`.
  - Reproduced 4 times: twice on the text face, twice on `--json`, where the levels are `warn`, `fail`. The VACUUMed variant with
    an index fault (`p1d-vacuumed.mjs <dir> index`) behaves the same way: 400/400 before, 382/400 after (see P1-2).

  `node /home/ai/.cache/tmp/rv-6309-defects/scripts/one.mjs log:23:800 log23-696`.
- **Context:** across the whole set, the new step lost 0 truth rows relative to the 6.30.8 step (see "Checked and found as

### P1-2: `PRAGMA integrity_check` is silently partial on VACUUMed and restored stores, so doctor prints "✓ Database integrity: ok" on a store whose freelist lists live observation pages

- **Where:** schema.mjs:2046 (`PRAGMA integrity_check(${limit})`) as read by install.mjs:3203–3205. The cause is upstream
  SQLite behaviour, but the release's new "ok" depends on it.
- **Mechanism (SQLite 3.53.4, `node_modules/better-sqlite3/deps/sqlite3/sqlite3.c`):**
  1. The pragma puts every rowid table's root page into the root array, and virtual tables have root page 0.
  2. `OP_IntegrityCk` passes `&aRoot[1]`. `sqlite3BtreeIntegrityCheck` reads `aRoot[0]==0` as "this is a partial check"
     (line 84393). That sets `bCkFreelist = 0` (84396), so the freelist check at 84434 is skipped, and it skips the "Page N:
     never used" scan (`if( !bPartial )`, 84483).
  3. Whether a virtual table comes first is decided by the schema hash order.
  `EXPLAIN PRAGMA integrity_check` shows the array:
  - A store fresh from the product opener: first root 63, a full check.
  - The same store after one `VACUUM` (what `maintain execute`'s vacuum op runs, lib/maintain-core.mjs:972): first root 0.
  - Any `VACUUM INTO` copy (backups, and so restores): first root 0.
  - The D#546 `869` population after the opener: first root 0.
  - `writeStoreSnapshot` fixtures: first root 0.

  So the release's measurement and tests never exercised the freelist or orphan-page checks on those stores.
- **What goes wrong:** cross-linked freelist damage reads `ok`, and the next ordinary write destroys rows. P1-1's gate cannot
  see the damage either.
- **Repro:**
  ```
  S=/home/ai/.cache/tmp/rv-6309-defects/p1d; mkdir -p $S/home/.claude
  node /home/ai/.cache/tmp/rv-6309-defects/scripts/p1d-vacuumed.mjs $S/data        # VACUUMed store, freelist lists live pages 69, 70
  (cd /home/ai/.cache/tmp/rv-6309-defects/wt && HOME=$S/home CLAUDE_MEM_DIR=$S/data node cli.mjs doctor | grep -E "FTS5|Database|DB stats")
  sqlite3 -readonly $S/data/claude-mem-lite.db "PRAGMA integrity_check(4);"
  ```
  Output:
  - The fixture reports `"partialCheck": true, "integrity": "ok", "observationsIntact": "400/400"`.
  - Doctor prints `✓ FTS5 integrity: all indexes healthy`, `✓ Database integrity: ok`, `✓ DB stats: 0.8MB, 400 observations`.
  - The 3.46.1 CLI, whose hash order puts a real table first, reports on the same file: `Tree 5 page 5 cell 6: 2nd reference to
    page 70`, `Tree 5 page 5 cell 5: 2nd reference to page 69`, `Page 124: never used`, `Page 126: never used`.
  - An ordinary write of 100 observations after doctor's ok leaves `"observationsIntact": "382/400"`.
  - Minimal confirmation: a plain table plus a freelist cross-link, with no virtual table first, is reported by both SQLite
    builds. The p1c fixture (initSchema + VACUUM INTO + dropped table) has the same bytes in both builds: 3.53.4 reports `ok`,
    3.46.1 reports the cross-link.

### P2-1: when SQLITE_FULL, NOMEM or IOERR hits an early rebuild statement, SQLite ends the transaction and the later statements commit one by one, while doctor says "indexes not rebuilt" and the CHANGELOG says "rolled back"

- **Where:**
  - schema.mjs:1966 (`rebuildFTS` keeps looping after an error).
  - schema.mjs:2112–2114 (`stoppedBy` is checked only after all five statements ran).
  - schema.mjs:2088 (`rollback()` returns early once `inTransaction` is false).
  - CHANGELOG: "rebuilds every index … in one transaction" and "A rebuild that meets the lock or a disk or memory error is rolled
    back".
- **What goes wrong:** the FTS 'rebuild' INSERT has no statement journal, so SQLITE_FULL on it rolls back the whole
  transaction (`inTransaction` false). The remaining three FTS rebuilds and the REINDEX then autocommit. `checkStoreIntegrity`
  returns `unrebuilt`, and doctor prints `⚠ Database integrity: indexes not rebuilt — observations_fts: database or disk is full`.
  Some indexes were in fact rebuilt and committed, and the `fell` counts for them are never taken. The test
  "rolls the rebuild back when the disk fills (+0/+1 pages)" covers FULL only on the last statement (REINDEX).
- **Repro:** `node /home/ai/.cache/tmp/rv-6309-defects/scripts/p3b-full.mjs` (2,000 observations, observations_fts leaf rows
  deleted, one events index damaged, `max_page_count = page_count + k`). Output:
  - At `+0`, `+2`, `+5`, `+10`, `+20`, `+40` pages: `state=unrebuilt committedSomething=true inTx=false
    errors=["observations_fts: database or disk is full"]`. `committedSomething` means another connection's `PRAGMA
    data_version` changed.
  - Stepwise: `observations_fts rebuild: SQLITE_FULL | inTransaction after it: false`.
  - integrity_check before: `row 1 missing from index idx_events_created | fts5: corruption found …`. After
    `checkStoreIntegrity` returned `unrebuilt`, only the fts5 line remains, so the REINDEX committed.
- No row is lost: the rebuild statements write indexes only.

### P2-2: an integrity failure doctor could not act on is ⚠ only, so doctor exits 0 on a store whose check failed

- **Where:** install.mjs:3224–3228 (`unrebuilt` → `dwarn`, no `issues++`) and schema.mjs:2099. A `BEGIN IMMEDIATE` that fails
  with a code outside `REBUILD_STOPPED_RE`, for example SQLITE_CORRUPT, also lands in `unrebuilt`.
- **What goes wrong:** the store failed `integrity_check`, and doctor printed its lines under `⚠ Database integrity issues
  detected:`. The rebuild then stopped on disk full, read-only, IOERR, NOMEM, CANTOPEN or a non-classified BEGIN error, and
  the only verdict is a second ⚠. A script that reads doctor's exit code or `issues` sees a store with known damage as passing.
  For the lock case, "run again in a moment" is a fair ⚠. For the other codes, the damage is known and stays unrepaired.
- **Repro (function level):** the release's own test cases `+0` and `+1` (`rolls the rebuild back when the disk fills`) return
  `state: 'unrebuilt'` with `rows` matching `missing from index`. install.mjs maps that state to `dwarn` only. A disk-full or
  read-only filesystem was not driven end to end through `cli.mjs doctor` (see NOT CHECKED).

### P2-3: the before-count inside the transaction blocks the repair it describes, so doctor says "not repaired by rebuilding the indexes" on a store that `fts-check rebuild` repairs

- **Where:** schema.mjs:2111 (`counts(tables)` inside `BEGIN IMMEDIATE`). `count(*)` on observations walks
  `idx_obs_epoch_project` (`SCAN observations USING COVERING INDEX idx_obs_epoch_project`). When that index has a damaged
  page, the count throws SQLITE_CORRUPT. The catch returns null, but the error poisons the transaction: every later statement
  fails with "malformed" and so does COMMIT.
- **Repro:** `/home/ai/.cache/tmp/rv-6309-defects/scripts/p5e-doctor.sh` (3,000 observations, a leaf of `idx_obs_epoch_project`
  with its cell count zeroed). Output:
  ```

    ✓ FTS5 integrity: all indexes healthy
    ⚠ Database integrity issues detected:
        database disk image is malformed

    ✓ Database integrity: ok
  ```

  Attribution, the same transaction with and without the count:
  - `BEGIN; count(*); rebuildIndexes; COMMIT` → `count: SQLITE_CORRUPT`, `errors 5`, `commit SQLITE_CORRUPT`, integrity still

  - `BEGIN; rebuildIndexes; COMMIT` → `errors 0`, `commit ok`, `integrity after: ok`.
- **Who is affected:** the user is told rebuilding does not repair the store, the ✗ has no remedy line, and README says doctor

### P3-5: cost on a large store

Synthetic store with 200,000 observations, 100,000 events and 100,000 prompts (577 MB), from `scripts/p4-cost.mjs 200000` and
`scripts/p4b-lock.mjs`:

- The integrity check on a sound store takes 2,418 ms and is added to every doctor run.
- The rebuild path takes 8,089 ms in total. Measured separately, it holds the write lock for 5,123 ms.
- A hook-like writer with `busy_timeout = 5000`, the hooks' ceiling (`DB_BUSY_TIMEOUT_MS`), committed after 4,936 ms. That is
  just inside the ceiling. A UserPromptSubmit-face writer waits only 500 ms (`UPS_DB_BUSY_TIMEOUT_MS`), so its write would fail
  for the duration.
- At 145 MB (50,000 observations): 568 ms for the check, 1,586 ms for the rebuild path.
- The rebuild runs only after a failed check.

## Checked and found as claimed

- **No rows lost by the new step on the D#546 set:** my ruler, `scripts/ruler.mjs`, covers all 2,769 plants and 2,755 that open.
  It used `plants.mjs readable()` over every ordinary table, not only observations, and compared against truth rowids and
  values. Truth rows that read correctly after 6.30.8's step and wrongly after 6.30.9's: 0. Nine of the ten flagged plants were
  checked one by one against truth and none was a loss; the tenth (`main21-113`) was a row the 6.30.8 step had already
  garbled. One search loss is reported above (log23-696).
- **No partial FTS rebuild is committed after SQLITE_CORRUPT mid-scan.** Any SQLITE_CORRUPT inside the transaction (page damage
  or record damage, from a rebuild statement or a plain SELECT) makes every later statement and the COMMIT fail, and SQLite
  rolls back. Probes: `scripts/p1-partial-fts.mjs`, `scripts/p1b-steps.mjs`.
- No transaction is left open on the handle: 0/2,755. Nothing threw.
- Text and `--json` faces agree, including levels and details, on six shapes: null, index, fts-order, lost-rows, page,
  fts-config (`scripts/faces.mjs`).
- A5 (`fts-config` → `not checked — invalid fts5 file format`), A6 (schema v99 → not checked, file not rebuilt) and A7 (lock held
  → both lines "not checked", no "Rebuilding") behave as specified in the release's tests, which pass.
- Classification:
  - `CHECK_DAMAGE_CODE_RE` matches SQLITE_CORRUPT_VTAB, so an FTS5 corruption from the check is taken as damage.
  - SQLITE_ERROR (FTS5 config) gives `unchecked`.
  - BUSY on BEGIN gives `unrebuilt` with busy. This is consistent with `isFtsCorruptionError` routing VTAB corruption to a
    rebuild.
- Doctor runs integrity_check on a read-write handle, which also verifies CHECK constraints; a read-only handle does not. The 3
  "damaged" plants whose read-only re-check says ok (main21-82, two22-206, two22-212) carry `CHECK constraint failed in
  observations` (a garbled `type`), so ✗ is correct there.
- No production code path writes rows that violate CHECK or NOT NULL (no `ignore_check_constraints` or `writable_schema` outside
  tests), and no index uses an application-defined function or collation. Sound stores therefore have no obvious
  false-positive source.
