# Blind claims review: commit 1b23dcc2 (D#550, doctor integrity check + README "Damaged database")

## Verdict

Most of the claims hold when the experiments are re-run. Every number in the README and the measurements file reproduces
(1,643 / 102 / 49 / 53 / 1,541 / 157 / 3,285; doctor 286/286 with 0 false greens; the cost delta). doctor wrote nothing to
any of the 1,643 failing plants. The English and Chinese sections say the same thing.

Two P0 findings and one P1 finding stand against the change:

- **P0-1 (reproduced end to end).** doctor can name a 0-byte file as "the newest" backup snapshot. Following the README's
  snapshot-restore block with that path replaces the store with 0 bytes, and doctor then prints `✓ Database integrity: ok`.
  The 0-byte file comes from `snapshotDb`: when the store is damaged, its `VACUUM INTO` fails and leaves the empty
  canonically named `.bak` behind. One ordinary product `delete --confirm` (MCP `mem_delete` runs the same
  `deleteObservations`) left such a file on 638 of the 1,643 failing plants. The root cause is in `lib/db-backup.mjs`, which
  this diff does not touch. The new remedy line and the README section are what send the user to that file.
- **P0-2 (reproduced on constructed stores, real-world reach SUSPECTED).** A CHECK constraint that cannot be evaluated
  ("no such column" or "no such function" after damaged schema text) makes doctor print `✓ Database integrity: ok` plus a ⚠
  line, and then run the read-write FTS check anyway. That connection's close folds the damaged log frame into the main file
  and deletes the log, which is the D#541 hazard the change exists to prevent. A read-write `PRAGMA integrity_check` reports
  SQLITE_CORRUPT on every such store. 103 of 4,139 8-byte-fill offsets inside the five CHECK tables' schema text produce this
  layout. None of the 2,769 measured plants does.
- **P1-1.** "Restore the newest snapshot ... loses what was saved after it" is false when that snapshot was taken after the
  damage. Of 663 non-empty post-damage snapshots, 463 fail the check, 170 lack 12,803 rows of the undamaged store, and 55 pass
  the check while lacking rows.

The P3 findings are wording and archive-script issues (see Claims).

## Claims

### 1. doctor checks read-only, changes nothing, prints `✗ Database integrity:`, the database still opens

**HOLDS.**
- 869 plants (archived `doctor.mjs`, 8 workers): 286 fail. ✗ printed on all 286 (240 `Database integrity`, 46 `Database`),
  ✗ on 0 passing plants, false greens 0, failing stores changed 0, passing stores changed 583 (by the existing read-write
  FTS check). This matches the measurements file exactly.
- Rich populations (`docrich.mjs`): 1,357 failing plants, ✗ on all 1,357 (1,344 integrity, 13 `Database:`). The SHA of the
  main file changed on 0 and the SHA of the log on 0.
- A read-only open and check (`e1.mjs`) never changes the main file or the log. It creates an empty `-wal` and a `-shm` when
  they are absent, which is file creation, not a content change.
- "Still opens": of the 1,643 failing plants, doctor reaches the integrity line on 1,584. The other 59 fail doctor's own
  read-only open and print `✗ Database:`. On those 1,584, `cli.mjs recent 3` works on 1,571, `search alpha` works on 1,226,
  and both fail on 13 (`prodopen.mjs`).
- Comment check: a read-write open, query and close of p20-v7 folds the damaged frame into the main file and deletes the log
  (main file alone: ok before, `Tree 20 page 20 ... out of range` after). A read-only open leaves both untouched. The comment
  holds.
- The install.mjs comment says "v6.30.2 printed no ✗ while this check failed on 114 of 869". This **holds** under the
  archived ruler's definition (verdict on the store doctor left behind): main's doctor, with the archived `doctor.mjs`, gives
  114 false greens and changed 197 failing stores. With the verdict taken before doctor it is 153 (91 all ✓, 62 with ⚠).
  v6.30.2 and main differ only in remedy wording (`git diff v6.30.2 main -- install.mjs`).

### 2. CHECK constraints evaluated, NULL passes, unevaluable ones reported as not evaluated

**PARTLY FALSIFIED: P0-2.**
- HOLDS for evaluable constraints (`e4.mjs`). A read-only `integrity_check` reads `ok` while the read-write one reads
  `CHECK constraint failed in t`, and `checkIntegrity` matches the read-write verdict on all 9 realistic cases: plain, NULL
  only (NULL passes), WITHOUT ROWID, two clauses, NOCASE, affinity, typeof, a `--` comment holding `(` inside the CHECK, and
  an IPK reference. On the plants, the read-only check failed nowhere the read-write `integrity_check` passed except p61-v10
  (an FTS definition, as documented), and passed nowhere the read-write check failed (0/2,769, `indep.mjs`).
- FALSIFIED for unevaluable constraints. `checkConstraints` puts any non-CORRUPT error (SQLITE_ERROR "no such column",
  "no such function") into `unchecked`, and `readIntegrity` then returns `ok: true`. doctor prints `✓ Database integrity: ok`
  and `⚠ ... CHECK constraints not evaluated for observations (no such column: tyqe)`, sets `integrityPassed = true`, and
  runs the read-write FTS check. SQLite itself calls these stores damaged: a read-write `integrity_check` throws
  `SQLITE_CORRUPT: malformed database schema (observations) - no such column: tyqe`, and every INSERT fails the same way.
  - `e6.mjs` reproduces it. The main file is intact and checkpointed (alone: ok), and the log holds one later schema frame
    with `CHECK(tyqe IN ...`. doctor printed ✓ + ⚠ + `✗ FTS5 rebuild errors`. Afterwards the log was 0 bytes and the main
    file alone held the damaged schema (`unchecked: observations (no such column: tyqe)`), so the intact older schema page
    is gone.
  - Reach (`e7.mjs`): an 8-byte 0x41 fill (the 869 sweep's `[*, 8, 0x41]` variants) at every offset of the stored CREATE
    text gives this layout at 103 of 4,139 offsets: observations 13/1,638, events 35/758, deferred_work 3/676, search_runs
    19/494, search_results 33/573. The read-write check fails on all 103. Examples: `CHECK(AAAAAAAAN ('open'...` (no such
    function), and a damaged column name with an intact CHECK (no such column: type). The same damage shape occurred
    naturally in the 869 sweep on an FTS definition (p61-v10, `no such column: T.AAAAAAAAed`).
  - The output does flag something (⚠, and here ✗ FTS5 rebuild errors), but the write happens first. Under the scale this
    is "doctor writes to a damaged store". A suggested fix: do not set `integrityPassed` when `unchecked` is non-empty, or
    classify a prepare error of a stored CHECK expression as damage.
- P3: `checkClauses` tokenizes differently from SQLite. SQLite counts every character ≥ 0x80 as an identifier character,
  but the walker splits on non-letters such as `—`. So `a VARCHAR—CHECK(0)` (a valid type name) is read as `CHECK(0)` and
  reported as damage on a sound store. This is contrived; the product schema never has it.

### 3. Remedy names the README section and the newest snapshot with its time; no move/replace command; FTS check skipped

**Literally HOLDS; FALSIFIED in effect by P0-1 and P1-1.**
- The doctor output on a failing store was read in full (dm0). It holds the README URL `#damaged-database` (the only such
  heading in README.md) and "the newest of 2 is <path>, from <ISO>: what was saved after it is lost". No command moves or
  replaces the store. The output then shows `⚠ FTS5 integrity: not checked — ... did not pass the integrity check above`.
  The "did not run" message branch was checked by reading the code.
- **P0-1, end to end (`snap-e2e.sh`, plant 869/p20-v7).** The setup is a good older snapshot (2 MB, 2026-10-01) and a store
  with a damaged log frame.
  1. `cli.mjs delete 5 --confirm` printed "Deleted 1 observation(s)" and left
     `claude-mem-lite.db.pre-delete-<now>.bak` at **0 bytes**.
  2. doctor printed "the newest of 2 is ...pre-delete-...bak".
  3. Running README block 3 with that path gave a store of 0 bytes.
  4. doctor then printed `✓ Database integrity: ok` and `⚠ DB stats: no such table: observations`.

  Reach (`zerobak.mjs`): on all 1,643 failing plants, one `delete 5 --confirm` exited 0 on 1,187, left a `.bak` on 1,301,
  and left a **0-byte** `.bak` on 638, all of which still fail the check. Daily auto-maintain (`hook.mjs`, `pre-maintain`)
  and `maintain` purge take the same `snapshotDb` path. Each failed attempt adds another 0-byte file with a newer stamp.
  `pruneSnapshots` runs only after a successful snapshot. The README's mitigation is optional ("Copy the database as above
  first if you want to keep it"). The pre-existing `✗ Database:` remedy (`lib/db-unusable.mjs`) picks the newest snapshot
  by mtime with the same blindness.
- **P1-1 (`zb2.mjs`).** The 663 plants where `VACUUM INTO` succeeded on the damaged store (snapshot taken after the damage,
  then named by doctor as the newest): 463 snapshots fail `checkIntegrity` themselves, 503 hold changed values, 170 lack
  12,803 rows of the undamaged truth, and 55 pass the check while lacking rows. doctor would be green after restoring
  those 55. Both doctor and the README say only "what was saved after it is lost".

### zerobak.mjs

```javascript
// node zerobak.mjs <population> <k> <K> <out> [limit]: for each plant failing checkIntegrity, on a copy, run the product's
// `delete 5 --confirm` (snapshotDb 'pre-delete' runs first in deleteObservations) and record whether a .bak was left,
// its size, and whether a later checkIntegrity-failing store then has a 0-byte newest snapshot (what doctor would name).
import { spawnSync } from 'node:child_process';
import { appendFileSync, mkdirSync, readdirSync, statSync } from 'node:fs';
import { join } from 'node:path';
import { WORK, build869, copyPair, plant869, plants869, richPlants } from '/home/ai/.cache/tmp/d550-rv-claims-yiHo/tree/tasks/d546/ruler/plants.mjs';
import { checkIntegrity } from '/home/ai/.cache/tmp/d550-rv-claims-yiHo/tree/lib/db-integrity.mjs';
const TREE = '/home/ai/.cache/tmp/d550-rv-claims-yiHo/tree';
const [pop, kS, KS, out] = process.argv.slice(2);
const k = Number(kS), K = Number(KS), slot = `zb${k}`;
let plants;
if (pop === '869') { build869(); plants = plants869().map((x) => ({ id: x.id, make: (d) => plant869(d, x) })); }
else { const [v, s, c] = pop.split(':'); plants = richPlants(v, Number(c), Number(s), slot).plants; }
const home = join(WORK, 'zb', slot, 'home');
mkdirSync(join(home, 'tmp'), { recursive: true });
mkdirSync(join(home, 'proj'), { recursive: true });
for (let i = 0; i < plants.length; i++) {
  if (i % K !== k) continue;
  const pl = plants[i];
  const p = pl.make(join(WORK, 'zb', slot, 'cur'));
  const ic = checkIntegrity(copyPair(p, join(WORK, 'zb', slot, 'ic')));
  if (ic.ok || ic.notChecked) continue;
  const dir = join(WORK, 'zb', slot, 'run');
  copyPair(p, dir);
  const env = { ...process.env, HOME: home, TMPDIR: join(home, 'tmp'), CLAUDE_PROJECT_DIR: join(home, 'proj'), CLAUDE_MEM_DIR: dir };
  const r = spawnSync(process.execPath, [join(TREE, 'cli.mjs'), 'delete', '5', '--confirm'], { env, cwd: join(home, 'proj'), encoding: 'utf8', timeout: 60000 });
  const baks = readdirSync(dir).filter((n) => n.endsWith('.bak')).map((n) => ({ n, size: statSync(join(dir, n)).size }));
  const after = checkIntegrity(copyPair(join(dir, 'claude-mem-lite.db'), join(WORK, 'zb', slot, 'ic2')));
  appendFileSync(out, JSON.stringify({ id: pl.id, rc: r.status, out: (r.stdout + r.stderr).trim().split('\n').at(-1)?.slice(0, 100), baks, stillFails: !after.ok && !after.notChecked }) + '\n');
}
```
