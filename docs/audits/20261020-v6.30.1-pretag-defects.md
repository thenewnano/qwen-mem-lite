### P1-1 secret-scrub.mjs:626-628, 645 — carried blank runs make scrubSecrets quadratic from pass 2 on (regression introduced by D#500, 5882eb90)

`blankRunAt` records a run (even an empty one, `starts.length === 0`) for every distinct line start a
reading skips from, stores `suffix: text.slice(s)` (line 645), and on every later pass of the same call
validates the carried run with `text.startsWith(run.suffix, s)` (line 628), which compares the WHOLE
rest of the text whenever it is unchanged — the common case, since a pass scrubs a value before the runs.
k BEGINs that each reach a blank line give k runs, so each pass from the second costs about k·L/2
character compares. Any scrubbed value starts a second pass; the CHAIN prefix the D#130 suite uses drives 32.

Shape: `CHAIN + ' ' + '-----BEGIN PRIVATE KEY-----\n\nword\n'.repeat(N/34)` (each BEGIN is read, reaches
one blank line, then stops at `word`; nothing is scrubbed, so the BEGINs survive into every pass).

Measured back to back, same machine, ratio = time / benign text of the same length (the D#130 ruler):

|---|---|---|---|
| 25k, CHAIN | 13.8 ms (2.3x) | — | 182 ms (29.4x) |
| 50k, CHAIN | 25.2 ms (2.1x) | — | 1,456 ms (120.6x) |
| 100k, CHAIN | 47.4 ms (1.9x) | — | 7,303 ms (304x) |

Attribution: the same tree with only `carriedRuns = new Map()` changed to `carriedRuns = null`
(`$S/nocarry`) reads 57.5 ms (2.4x) at 100k. Stop's hook timeout is 5 s; at 100k chars the release takes
7.3 s where v6.30.0 took 47 ms. The four D#500 shapes added to tests/secret-scrub-linear.test.mjs do not
contain this shape, so the suite stays green.

Repro: `node $S/probes/perf-chain.mjs $S/new 100000` vs `node $S/probes/perf-chain.mjs $S/old 100000`;
in vitest: `cd $S/tree && npx vitest run tests/zz-review-probe.test.mjs`.

Fix direction (not applied): a run depends only on the text from its first line to the end of the line
that ends it (plus the CONCAT lookahead), and its positions relative to `s` are invariant under the
offset-from-end key, so validating that span (or a length + hash of it) instead of the whole suffix keeps
the check exact at O(run length); and an empty run need not be carried at all.

### P3-1 schema.mjs:1702-1713 (pre-existing, outside the diff) — ensureDb leaks its handle when a pragma throws, so D#495's "keeps its WAL" holds only until the process exits

`new Database(DB_PATH)` and the four `db.pragma(...)` calls sit before the `try` whose `catch` closes the
handle; "malformed database schema" is thrown by `db.pragma('journal_mode = WAL')`, so each failed attempt
leaks an open connection. At process exit better-sqlite3 closes it, and as the last connection it
checkpoints the WAL into the main file and deletes the WAL.

Evidence (sandbox store, `$S/sbx-wal`, release tree):
- after ensureDbWithWalRecovery throws, then SIGKILL (no cleanup): WAL 16,512 bytes, kept;
- same, normal exit: WAL missing, and a fresh read-only open of the main file now fails with
  `malformed database schema (tq) - near "~": syntax error` — the unparseable row moved into the main file.
No commits are lost (they are checkpointed), and with another connection open the close-time checkpoint
cannot take its lock, so the D#495 motivating case still holds. But the CHANGELOG sentence "the -wal/-shm
files are no longer deleted" is not what is on disk after a hook exits with no other connection open.
tests/wal-recovery.test.mjs:550 reads the WAL size inside the same process before exit, so it cannot see
this. The same leak is why v6.30.0's WAL-delete arm failed in-process: with the D#495 line removed, the
test's own fixture ends `{"error":"disk I/O error", "walSize":0}` (deleted WAL, no recovery).

### P3-2 schema.mjs:1879-1882 + CHANGELOG D#495 — the premise "this is not a damaged frame" is false; no regression results from it

A WAL frame damaged before it was checksummed (a writer-side fault; this dev host has one, D#424) gives the
message. `$S/probes/wal-forge.mjs` writes `CREATE TABLE tq(x TEXT)` into the WAL, changes `)` to `~` in the
sqlite_master frame and recomputes every frame checksum: opening gives
`SQLITE_CORRUPT: malformed database schema (tq) - near "~": syntax error`; with the WAL removed the same
file opens (`names: ["base"]`). So the 600 byte flips measured only post-checksum damage, which SQLite drops.
Consequence vs v6.30.0: none found — v6.30.0 failed in-process anyway (P3-1) and its leaked handle then
checkpointed the "deleted" WAL into the main file (second process: malformed schema in both versions).
The code comment and CHANGELOG should not say the message never comes from a WAL frame.

### P3-5 secret-scrub.mjs:412 — isDerKeyStart's second arm matches every SubjectPublicKeyInfo, not only encrypted PKCS#8

`b[o] === 0x30 && … === 0x06` is SEQUENCE { SEQUENCE { OID … } }, the start of every SPKI public key.
Next to PRIVATE KEY markers these are now erased where v6.30.0 kept them (`node $S/probes/der-pub.mjs $S/old $S/new`):
- `-----BEGIN PRIVATE KEY-----\nMFkwEwYHKoZIzj0CAQYIKoZIzj0D\nnotes follow` (P-256 public) → `***PEM_KEY***\nnotes follow`
- `-----BEGIN EC PRIVATE KEY-----\nMCowBQYDK2VwAyEAGb9ECWmEzf6F\n…` (Ed25519 public) → erased
- `MHYwEAYHKoZIzj0CAQYFK4EEACID\n-----END PRIVATE KEY----- is the marker named in the docs` → `***PEM_KEY*** is the marker named in the docs` (END marker text erased too).
Errs toward erasure and needs a PRIVATE KEY marker beside the line; the docblock and CHANGELOG
("an encrypted key's SEQUENCE and OID") understate what it matches.

## Answers by question

   reverted alone (mutation runs); it also erases SPKI public keys beside PRIVATE KEY markers (P3-5).

   checkpoints and deletes it at exit (P3-1, pre-existing). A WAL-only schema fault: v6.30.0 did not recover
   in-process either (disk I/O error), so no lost recovery in-process; premise wording P3-2.

   subdirectory, outside git, cwd opt-out, root opt-out, MEM_NO_AUTO_ADOPT=1, `$HOME` as work-tree top, a

   disagreements are pre-existing and not managed-only specific: `.git` present but `git rev-parse` failing
